## 🧠 Monitoring Architecture Options

```
OPTION 1: STACK MONITORING (Built-in)
  Metricbeat → monitoring cluster (separate ES) → Kibana Stack Monitoring UI
  OR
  Self-monitoring (legacy) → .monitoring-* indices in same cluster

OPTION 2: AUTOOPS (Elastic Cloud / Self-Managed)
  ES emits metrics → AutoOps service → Analysis + Recommendations
  Free since February 2026 for all deployments

OPTION 3: PROMETHEUS + GRAFANA
  elasticsearch_exporter → Prometheus → Grafana dashboards
  Good for: multi-cluster, existing Prometheus infrastructure

OPTION 4: HEALTH API (Built-in v8+)
  GET _health_report → structured health status per feature
  No external tools needed

BEST PRACTICE: Use Stack Monitoring + AutoOps + Kibana Alerting
```

## 📊 Part 2 - Stack Monitoring Setup

### Method 1: Metricbeat (Recommended)

```yaml
# metricbeat.yml — on monitoring host
# Collects from: production cluster
# Sends to: monitoring cluster

# Elasticsearch module
- module: elasticsearch
  xpack.enabled: true
  period: 10s
  hosts: ["https://prod-es:9200"]
  username: "remote_monitoring_user"
  password: "${REMOTE_MONITORING_PASSWORD}"
  ssl:
    enabled: true
    certificate_authorities: ["/etc/metricbeat/certs/ca.crt"]
  metricsets:
    - cluster_stats
    - node
    - node_stats
    - index
    - index_recovery
    - index_summary
    - shard
    - ml_job
    - enrich

# Kibana module
- module: kibana
  xpack.enabled: true
  period: 10s
  hosts: ["http://prod-kibana:5601"]
  username: "remote_monitoring_user"
  password: "${REMOTE_MONITORING_PASSWORD}"
  metricsets:
    - stats
    - cluster_rules
    - cluster_actions
    - node_rules
    - node_actions
    - settings

# Logstash module
- module: logstash
  xpack.enabled: true
  period: 10s
  hosts: ["http://prod-logstash:9600"]
  metricsets: [node, node_stats]

# Send to MONITORING cluster (not production!)
output.elasticsearch:
  hosts: ["https://monitoring-es:9200"]
  username: "elastic"
  password: "${MONITORING_ES_PASSWORD}"
  ssl:
    certificate_authorities: ["/etc/metricbeat/certs/monitoring-ca.crt"]
```

```bash
  }
```

## 🤖 Part 3 - AutoOps

### What AutoOps Does

```
AutoOps = Elastic's automated cluster health management

Samples 100+ metrics every 10 seconds:
  → Shard allocation issues
  → Disk watermark violations (BEFORE they cause problems)
  → Indexing rejections
  → Slow queries + hot shards
  → Memory pressure + GC issues
  → ILM failures
  → Repository issues
  → Missing index patterns

Provides:
  → Automatic diagnosis
  → Recommended actions
  → Historical trend analysis
  → Predictive capacity warnings

Free since: February 2026 (all self-managed, ECE, ECK deployments)
Not available: air-gapped environments
```

### Enable AutoOps

```bash
# Via Kibana UI:
# Stack Management → AutoOps → Connect

# Via API:
POST _cloud/autoops/_enable
{
  "cloud_id": "my-deployment-cloud-id",
  "api_key": "cloud-api-key"
}

# Check AutoOps status
GET _cloud/autoops/_status

# AutoOps recommendations
GET _cloud/autoops/_recommendations
```

## 🔔 Part 5 - Production Alerting Rules

### Kibana Stack Rules for Monitoring

```bash
# Rule 1: Cluster RED Alert
POST kbn:/api/alerting/rule
{
  "name": "Cluster Status RED",
  "rule_type_id": "monitoring_alert_cluster_health",
  "consumer": "monitoring",
  "schedule": { "interval": "1m" },
  "params": {
    "threshold": "red"
  },
  "actions": [
    {
      "id": "pagerduty-connector",
      "group": "default",
      "params": {
        "severity": "critical",
        "summary": "Elasticsearch cluster is RED - immediate action required"
      }
    }
  ]
}

# Rule 2: CPU Usage Alert
POST kbn:/api/alerting/rule
{
  "name": "Node CPU > 90%",
  "rule_type_id": "monitoring_alert_cpu_usage",
  "consumer": "monitoring",
  "schedule": { "interval": "5m" },
  "params": {
    "threshold": 90,
    "duration": "5m"
  },
  "actions": [
    {
      "id": "slack-connector",
      "group": "default",
      "params": {
        "message": "Node CPU is above 90%: {{context.nodeName}} = {{context.cpuUsage}}%"
      }
    }
  ]
}
```

### ES|QL-Based Custom Alerts

```bash
# Alert: Disk watermark approaching (>80%)
POST kbn:/api/alerting/rule
{
  "name": "Disk Usage > 80%",
  "rule_type_id": ".es-query",
  "consumer": "alerts",
  "schedule": { "interval": "5m" },
  "params": {
    "searchType": "esqlQuery",
    "esqlQuery": {
      "esql": """
        FROM .monitoring-es-8-*
        | WHERE @timestamp >= NOW() - 5 MINUTES
        | WHERE type == "node_stats"
        | STATS
            max_disk = MAX(node_stats.fs.total.available_in_bytes),
            total_disk = MAX(node_stats.fs.total.total_in_bytes)
          BY node_stats.node_master_name
        | EVAL disk_used_pct = (1 - max_disk / total_disk) * 100
        | WHERE disk_used_pct > 80
        | STATS count = COUNT(*)
      """
    },
    "threshold": [1],
    "thresholdComparator": ">="
  }
}

# Alert: Indexing rejections
POST kbn:/api/alerting/rule
{
  "name": "Indexing Rejections Detected",
  "rule_type_id": ".es-query",
  "schedule": { "interval": "1m" },
  "params": {
    "searchType": "esqlQuery",
    "esqlQuery": {
      "esql": """
        FROM .monitoring-es-8-*
        | WHERE @timestamp >= NOW() - 5 MINUTES
        | WHERE type == "node_stats"
        | STATS rejections = SUM(node_stats.thread_pool.write.rejected)
        | WHERE rejections > 0
      """
    },
    "threshold": [0],
    "thresholdComparator": ">"
  }
}
```

## 📋 Part 6 - Key Metrics to Monitor

### Critical Metrics Dashboard

```bash
# 1. Cluster health
GET _cluster/health

# 2. Node-level overview
GET _cat/nodes?v&h=name,node.role,heap.percent,ram.percent,cpu,disk.used_percent,load_1m

# 3. Shard allocation
GET _cat/shards?v&h=index,shard,prirep,state,node&s=state

# 4. Thread pool (rejections!)
GET _cat/thread_pool?v&h=name,active,rejected,queue&s=rejected:desc

# 5. Indexing performance
GET _nodes/stats/indices/indexing
# → indexing_is_throttled
# → index_failed
# → index_time_in_millis / index_total = avg indexing time

# 6. Search performance
GET _nodes/stats/indices/search
# → query_time_in_millis / query_total = avg query time
# → fetch_time_in_millis / fetch_total = avg fetch time

# 7. JVM memory
GET _nodes/stats/jvm
# → mem.heap_used_percent > 75% = Warning
# → gc.collectors.old.collection_count increasing = GC pressure

# 8. Disk watermarks
GET _cat/allocation?v
# Used% > 85% = high watermark hit (no new shards)
# Used% > 90% = flood stage (all indices read-only!)

# 9. Merge stats
GET _nodes/stats/indices/merges
# High merge time = too many small segments or heavy write load

# 10. Cache efficiency
GET _nodes/stats/indices/query_cache,request_cache,fielddata
# High eviction rate = cache too small
```

### Alerting Thresholds Reference

```
CRITICAL (page immediately):
  Cluster status: RED
  Unassigned primary shards: > 0
  Disk used: > 90% (flood stage)
  Heap used: > 90%
  JVM old GC time: > 5 min in last 10 min

WARNING (page during business hours):
  Cluster status: YELLOW
  Disk used: > 85% (high watermark)
  Heap used: > 75%
  CPU: > 90% for > 5 min
  Indexing rejections: > 0 per minute
  Search rejections: > 0 per minute

INFORMATIONAL:
  Disk used: > 75%
  Heap used: > 65%
  Old GC count increasing trend
  Segment count > 5 per shard (needs forcemerge)
```

## 📈 Part 7 - Performance Baselines

### Establishing Baselines

```bash
# Capture baseline metrics during normal operation
# Compare against these during incidents

# Indexing throughput baseline
GET _nodes/stats/indices/indexing
# Record: index_total per minute, index_time_in_millis / index_total (ms/doc)

# Search latency baseline
GET _nodes/stats/indices/search
# Record: query_total per minute, query_time_in_millis / query_total (ms/query)

# Cache hit rates
GET _nodes/stats/indices/query_cache,request_cache
# Record: hit_count / (hit_count + miss_count) for each cache

# GC baseline
GET _nodes/stats/jvm
# Record: gc.collectors.old.collection_time_in_millis (should be < 100ms total per 5min)
# Record: gc.collectors.young.collection_time_in_millis

# Script for ongoing baseline collection:
# Store in Elasticsearch itself every 5 minutes
# Alert when metric deviates > 2 standard deviations from baseline
```

## 🛠️ Part 8 - Monitoring Best Practices

### Separate Monitoring Cluster

```
PRODUCTION CLUSTER          MONITORING CLUSTER
    │                             │
    │  Metricbeat ──────────────▶ │  .monitoring-es-8-*
    │  (ship metrics)             │  .monitoring-kibana-8-*
    │                             │  .monitoring-logstash-8-*
    │                             │
    │                        Kibana → Stack Monitoring UI
    │                        (connected to monitoring cluster)

WHY SEPARATE CLUSTER?
  ✅ Monitoring cluster failure doesn't affect production
  ✅ Production cluster not burdened by monitoring overhead
  ✅ Can monitor production cluster even when it's degraded
  ✅ Historical data retained independently
```

### Monitoring Retention

```bash
# Stack Monitoring default retention: 7 days
# Adjust via cluster settings on monitoring cluster:
PUT _cluster/settings
{
  "persistent": {
    "xpack.monitoring.history.duration": "14d"
  }
}

# Or via ILM policy on .monitoring-* indices
PUT _ilm/policy/monitoring-retention
{
  "policy": {
    "phases": {
      "delete": {
        "min_age": "14d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Self-monitoring in same cluster | Can't monitor when cluster is down | Use dedicated monitoring cluster |
| No alerts on disk watermarks | Cluster goes read-only without warning | Alert at 75% disk, critical at 85% |
| Monitoring with elastic superuser | Security risk | Create dedicated remote_monitoring_user |
| Alert thresholds too aggressive | Alert fatigue | Start conservative, tune based on incidents |
| No baseline established | Can't detect anomalies | Record metrics during normal operation |
| Missing JVM old GC alerts | OOM kills nodes | Alert on GC time > 5min/10min window |
| Not monitoring ILM failures | Indices grow forever | Alert on ILM error status |
| Metricbeat too high frequency | Monitoring overhead | 10s for node stats, 60s for index stats |
| Ignoring AutoOps recommendations | Known issues persist | Act on AutoOps within 24 hours |
| No capacity planning process | Surprise disk full | Monthly trend review + 6-month projection |

## 💡 Key Principles

```
1. Separate monitoring cluster for production
   → Never self-monitor production with same cluster

2. Health API is the fastest health check
   → GET _health_report beats manual metric assembly

3. AutoOps is free — enable it immediately
   → Free since Feb 2026, saves hours of manual monitoring

4. Alert on leading indicators not lagging ones
   → Disk at 75% (warning) not 90% (too late)
   → Heap at 75% not 90% (OOM imminent at 90%)

5. Thread pool rejections = cluster overwhelmed
   → Alert at first rejection, not when queue is full

6. JVM old GC = the most critical JVM metric
   → Old GC pause = cluster unresponsive = impact on search

7. Establish baselines during normal operation
   → Can't detect anomalies without normal reference

8. Metricbeat > self-monitoring in every case
   → Metricbeat continues when ES struggles

9. Stack Monitoring + Prometheus = belt and suspenders
   → Stack Monitoring for ES-specific, Prometheus for cross-stack

10. Monthly capacity review prevents surprises
    → 6-month disk/shard projections based on growth trends
```
