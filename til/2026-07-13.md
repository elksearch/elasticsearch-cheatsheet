## 🐳 Part 1 — Fleet + Elastic Agent on Docker (9.2.7)

### Architecture

```
practice-logs/*.log
        ↓
Elastic Agent (managed)
        ↓  enrolls via
Fleet Server (port 8220)
        ↓  registers with
Kibana ←→ Elasticsearch
```

### Critical Lessons Learned (Do NOT Forget!)

```
FLEET_ENROLL=1          ← CRITICAL — without this agent NEVER enrolls
                           This is the #1 mistake — env vars exist but
                           agent ignores them without this flag

FLEET_FORCE_ENROLL=true ← clears stale state from previous failed attempts
FLEET_INSECURE=true     ← required since no SSL in local/dev setup

elastic-agent image:    ← docker.elastic.co/elastic-agent/elastic-agent
                           NOT docker.elastic.co/beats/elastic-agent
                           (beats/ path doesn't exist in 9.x)

[\s\S]*                 ← matches newlines in grok patterns
                           (?s) flag NOT supported in ES grok engine
```

### Startup Order (Dependencies Matter!)

```
elasticsearch     → healthy       (~30s)
kibana_settings   → completed     (sets kibana_system password)
kibana            → healthy       (~60s)
fleet_kibana_init → completed     (POST /api/fleet/setup)
fleet-server      → healthy       (~90s — slowest, be patient)
elastic-agent     → running       (enrolls + starts collecting)

Total cold start: ~4 minutes
```

### Fleet Server — Why It Gets Stuck

```
"Waiting on default policy with Fleet Server integration"

Root cause: Fleet Server starts before Kibana Fleet is initialized
Fix: Add fleet_kibana_init service that calls:
     POST /api/fleet/setup
     POST /api/fleet/agent_policies (create Fleet Server Policy)
     BEFORE fleet-server starts
```

### Token Management

```
After docker compose up -d (first time):
1. Go to Kibana → Fleet → Enrollment tokens
2. Copy token for your policy (NOT Fleet Server Policy)
3. Update FLEET_ENROLLMENT_TOKEN in docker-compose.yml
4. docker compose up -d --force-recreate elastic-agent

On fresh start (docker compose down -v):
→ New tokens generated → must update token again
→ Token is tied to the policy, not the cluster
→ Each docker compose down -v = new tokens
```

## 📋 Part 2 — Multiline Logs with Filestream

### Why Multiline Exists

```
Normal single line log:
  2024-01-15 ERROR Something failed
  → 1 line = 1 document ✅ easy

Java exception log:
  2024-01-15 ERROR Payment failed
      at com.myapp.PaymentService.java:142
      at com.myapp.OrderController.java:89
      Caused by: java.net.ConnectException

  WITHOUT multiline → 4 separate useless documents ❌
  WITH multiline    → 1 complete document with full stack trace ✅
```

### Multiline Pattern — How It Works

```
Pattern: ^\d{4}-\d{2}-\d{2}
= "line starting with YYYY-MM-DD is a NEW log event"

2024-01-15 10:30:00 ERROR Payment failed     ← MATCHES → new event
    at com.myapp.PaymentService.java:142     ← no match → belongs to above
    at com.myapp.OrderController.java:89     ← no match → belongs to above
    Caused by: java.net.ConnectException     ← no match → belongs to above
2024-01-15 10:30:05 INFO  Order created     ← MATCHES → new event starts
```

### Parsers Config (Kibana Fleet → Integration → Parsers field)

```yaml
- multiline:
    type: pattern
    pattern: '^\d{4}-\d{2}-\d{2}'
    negate: true
    match: after
```

### Key Parameters Explained

```
type: pattern      → use regex to detect new event boundary
pattern            → regex to identify START of new log event
negate: true       → lines NOT matching pattern = continuation lines
match: after       → attach continuation lines AFTER the matching line

IMPORTANT: This is filestream syntax (9.x)
Wrap under parsers: not multiline.type (that's old filebeat syntax)
```

## 🔧 Part 3 — Ingest Pipeline for Java Logs

### Key Insight — [\s\S]* for Multiline Grok

```
Problem: GREEDYDATA in grok does NOT match newlines by default
         It stops at first \n

Wrong attempt 1: (?s).* → NOT supported in ES grok engine
Wrong attempt 2: multiline_mode: true → doesn't exist in ES grok

Correct solution: custom pattern_definitions using [\s\S]*

\s  = whitespace (space, tab, \n, \r)
\S  = non-whitespace
[\s\S] = ANYTHING including newlines
*   = zero or more times

Result: captures full stack trace across all newlines ✅
```

### Working Ingest Pipeline

```json
PUT _ingest/pipeline/java-log-pipeline
{
  "description": "Parse Java multiline logs",
  "processors": [
    {
      "grok": {
        "field": "message",
        "patterns": [
          "%{YEAR}-%{MONTHNUM}-%{MONTHDAY} %{TIME},%{INT} %{LOGLEVEL:log_level}%{SPACE}\\[%{DATA:service_name}\\] %{MULTILINE:log_message}"
        ],
        "pattern_definitions": {
          "MULTILINE": "[\\s\\S]*"
        },
        "ignore_failure": true
      }
    },
    {
      "set": {
        "if": "ctx.message != null && ctx.message.contains('Caused by')",
        "field": "has_exception",
        "value": true
      }
    },
    {
      "set": {
        "if": "ctx.message != null && ctx.message.contains('Caused by')",
        "field": "error_type",
        "value": "exception"
      }
    },
    {
      "uppercase": {
        "field": "log_level",
        "ignore_missing": true
      }
    }
  ]
}
```

## 🧠 Part 4 — APM Deep Dive

### Is APM Server Mandatory?

```
NO — APM Server is NOT mandatory in 8.x/9.x

Architecture 1 (Classic):
  App (APM Agent) → APM Server → Elasticsearch

Architecture 2 (Modern — ES 8.x+):
  App (APM Agent) → Elasticsearch directly
  ES has built-in APM intake endpoint natively

Architecture 3 (Fleet Managed — Recommended):
  App (APM Agent) → Elastic Agent (APM integration) → Elasticsearch
```

### Why APM Server STILL Matters — Tail-Based Sampling

```
This is the REAL reason APM Server exists beyond load buffering.

Head-Based Sampling (basic):
  Request arrives → COIN FLIP at START → record or drop
  Problem: might drop the FAILING request → useless

Tail-Based Sampling (smart — APM Server only):
  Request arrives → Record EVERYTHING temporarily in memory
        ↓
  Full distributed trace COMPLETES (across all microservices)
        ↓
  NOW decide: was this interesting?
  → Error?      → KEEP
  → Slow trace? → KEEP
  → Healthy?    → Keep small % (configurable), drop rest

WHY ES CANNOT DO THIS ALONE:
  Requires holding partial traces in memory waiting for completion
  Requires waiting for ALL services in distributed trace to respond
  ES is a storage/search engine — not designed for stateful buffering

REAL WORLD IMPACT:
  1,000,000 requests/day
  999,000 healthy, 1,000 have errors

  No sampling:       store 1,000,000  → expensive
  Head-based 10%:    store 100,000    → might miss ALL 1,000 errors!
  Tail-based:        store ~1,000     → captures EVERY error ✅
```

### APM Architecture Decision Table

```
Use direct ES endpoint when:
  → Small setup
  → Simple infra
  → Using Elastic Cloud/Serverless

Use APM Server when:
  → High scale (thousands of agents)
  → Need tail-based sampling
  → Need heavy write buffering

Use Fleet + Elastic Agent when:
  → Modern 9.x setup (recommended)
  → APM Server runs as integration inside Elastic Agent
  → Central management via Kibana Fleet
```

## 🔬 Part 5 — Analyzers Deep Dive

### Three Components — With Standard Analyzer Example

```
Input: "The Quick Brown FOX jumped over the <b>lazy</b> dog's fence!"

Step 1: Character Filter
  Standard analyzer has NONE
  Input passes through unchanged
  (html_strip would remove <b> tags — that's custom analyzer)

Step 2: Tokenizer
  Standard tokenizer splits on whitespace + punctuation:
  ["The","Quick","Brown","FOX","jumped","over","the","b","lazy","b","dog's","fence"]
  Note: <b> → angle brackets removed, b kept as token
  Note: ! removed (punctuation)
  Note: dog's kept as one token

Step 3: Token Filter
  Standard applies: lowercase + stopword removal
  ["the","quick","brown","fox","jumped","over","the","b","lazy","b","dog's","fence"]
  → lowercase applied
  → stopwords (the, over) removed
  → ["quick","brown","fox","jumped","b","lazy","dog's","fence"]

Final tokens in inverted index:
  ["quick","brown","fox","jumped","b","lazy","dog's","fence"]
```

### NGram vs Edge NGram

```
Word: "elastic"

NGram (min=2, max=4) — ALL positions:
  Size 2: el, la, as, st, ti, ic
  Size 3: ela, las, ast, sti, tic
  Size 4: elas, last, asti, stic
  Use case: search from MIDDLE of word (contains search)
  "ast" matches "elastic" ✅

Edge NGram (min=2, max=4) — START only:
  el
  ela
  elas
  Use case: AUTOCOMPLETE / search-as-you-type
  User types "ela" → matches "elastic" instantly ✅

Custom Analyzer for Autocomplete:
  {
    "tokenizer": "edge_ngram_tokenizer",
    "filter": ["lowercase"]
  }

KEY RULE:
  Index time  → edge_ngram_analyzer (generates prefixes)
  Search time → standard analyzer (exact term lookup)
  → Different analyzers at index vs search time = correct autocomplete
```

## 🏛️ Part 6 — Master Election Deep Dive (9.x)

### Evolution of Discovery

```
ES 6.x and below — Zen Discovery (Manual, Error Prone):
  discovery.zen.ping.unicast.hosts: ["node1","node2","node3"]
  discovery.zen.minimum_master_nodes: 2   ← manual quorum!
  Problem: add/remove nodes → recalculate manually → humans make mistakes

ES 7.x → 9.x — Raft-based (Automatic, Safe):
  cluster.initial_master_nodes: ["node1","node2","node3"]  ← bootstrap only
  discovery.seed_hosts: ["node1","node2","node3"]          ← node discovery
  Quorum: automatic, no manual setting needed
```

### Quorum Formula — Automatic Calculation

```
Formula: (n/2) + 1  where n = master eligible nodes

3 masters → quorum = 2 → can tolerate 1 failure
5 masters → quorum = 3 → can tolerate 2 failures
7 masters → quorum = 4 → can tolerate 3 failures

ALWAYS use ODD numbers!
2 masters → quorum = 2 → ZERO fault tolerance (both must be up)
4 masters → quorum = 3 → 1 failure tolerance (same as 3 masters, wastes a node)
```

### cluster.initial_master_nodes — Lifecycle

```
FIRST BOOTSTRAP ONLY:
  cluster.initial_master_nodes: ["node1","node2","node3"]

After cluster forms successfully:
  → REMOVE this setting from all nodes
  → Elastic recommends this explicitly
  → Leaving it risks accidental re-bootstrapping

DANGER: If someone copies yml with this setting to new nodes
  → ES could treat it as fresh cluster formation
  → Creates a SECOND cluster with same name
  → TRUE split brain — the only way to get it in 9.x!
```

### discovery.seed_hosts — Rules

```
Add: ONLY master eligible nodes
Why: They maintain cluster state, can respond to discovery

Do NOT add:
  ❌ Data nodes    → store data, know nothing about cluster topology
  ❌ Ingest nodes  → transform data, no cluster state
  ❌ Coordinating  → route requests, no cluster state

Add ALL master eligible nodes (not just minimum):
  → If some are down during restart, others provide connectivity
  → 3 masters but only 2 in seed_hosts → if those 2 down, node can't find cluster
  → Always list ALL for maximum resilience

Update when nodes change:
  → Not strictly required (cluster state persists on disk)
  → But best practice for clean configuration
  → Prevents confusing connection attempts to dead nodes
```

### Split Brain in 9.x

```
Classic split brain (two simultaneous masters): ELIMINATED ✅
Mechanism: Raft quorum prevents any side without majority from electing

What CAN still happen:
  1. Accidental dual bootstrap (see above) → TRUE split brain
  2. Network partition → writes blocked, NOT data corruption
  3. 2 master eligible nodes → total outage (not split brain)
  4. Old master steps down gracefully when isolated → no data loss

Network partition behavior:
  Node1 alone    → 1 vote → no quorum → steps down → writes rejected
  Node2 + Node3  → 2 votes → quorum → one elected master → writes continue
  Result: availability sacrifice for consistency (correct behavior)
```

## 🆕 Part 7 — Columnar Mode (ES 9.5 — New!)

### What is Columnar Mode

```
Biggest architectural change to ES this decade.
Ships as Technical Preview in 9.5, GA in 9.6

The Problem Today:
  ES stores data MULTIPLE TIMES for each field:
  1. _source          → original JSON document
  2. Inverted index   → for full-text search
  3. Doc values       → for aggregations/sorting

  For logs/metrics (write once, rarely read):
  → Paying for 3x storage is wasteful
  → You don't need all 3 for every field
```

### How Columnar Mode Changes Storage

```
Standard Mode (today):
  Every field → inverted index + doc values + _source
  Cost: high storage, high write overhead

Columnar Mode (9.5):
  Data stored ONCE → in doc values (columnar)
  Inverted index → ONLY where needed (message field for text search)
  _source → REGENERATED on demand from columns (not stored separately)

Result:
  6.6x less storage (from related ES metrics article)
  160x faster analytical queries
  Smaller storage footprint from day one
```

### Two Flavours

```
Columnar Logs:
  → Keeps inverted index on message field (for grep/text search)
  → Right defaults for time-ordered log data
  → Best for: logs, observability

Pure Columnar Mode:
  → Drops string field indexes entirely
  → Maximum storage savings
  → Best for: pure analytics, metrics, business data
```

### What Doesn't Change

```
✅ Same REST APIs
✅ Same Kibana dashboards
✅ Same ES|QL queries
✅ Same Fleet/Agent integrations
✅ Same ILM policies
✅ Existing document-mode indices untouched

NOT a migration — it's a NEW index mode you opt into
Applied per-index via index settings
```

### Connection to Doc Values (What We Learned)

```
We covered in Q15 that doc_values are:
  → Columnar on-disk structure
  → Available after REFRESH (not flush)
  → Used for aggregations and sorting
  → Enabled by default on keyword, numeric, date

Columnar Mode makes doc_values the PRIMARY storage
instead of a secondary optimization.
This is the natural evolution of what was always there under the hood.
```

## 🎯 Interview Questions Covered Today

**Q: Is APM Server mandatory in 9.x?**
> No. ES 8.x+ has a native APM intake endpoint so agents can send directly. APM Server's real value is tail-based sampling — intelligently deciding after a full distributed trace completes whether to keep it. ES alone cannot do this as it requires stateful buffering across microservices.

**Q: What is tail-based sampling and why does it matter?**
> Head-based sampling decides at request start — may miss all failures. Tail-based waits for full distributed trace to complete, then keeps errors + slow traces + small % of healthy ones. Captures every failure while dramatically reducing storage cost.

**Q: What is the difference between NGram and Edge NGram?**
> NGram generates all possible character chunks from any position — good for contains/infix search. Edge NGram generates chunks only from the start — perfect for autocomplete. At index time use edge_ngram analyzer; at search time use standard analyzer.

**Q: Is split brain possible in ES 9.x?**
> Classic split brain (two simultaneous masters) is eliminated by Raft-based quorum. The only way to get true split brain in 9.x is accidental dual bootstrap — someone running cluster.initial_master_nodes on an existing cluster. Network partitions cause write unavailability (correct behavior) not data corruption.

**Q: What is Columnar Mode in ES 9.5?**
> New index mode that stores data once in doc values (columnar format) instead of three redundant copies. Inverted indexes only built where needed. Reduces storage 6x+ and speeds up analytical queries 160x for log/metric workloads. Same APIs, same dashboards — just a new index setting.

**Q: What goes in discovery.seed_hosts?**
> Only master eligible nodes. They maintain cluster state and can respond to discovery requests. Data, ingest, coordinating and ML nodes have no role in cluster formation. List ALL master eligible nodes for maximum resilience.

   doc_values was always there — now it becomes the primary storage mode

5. Tail-based sampling is APM Server's most important unique feature
   Not just load buffering — intelligent sampling after trace completion

6. Split brain in 9.x = practically impossible with correct setup
   Only risk: accidental cluster.initial_master_nodes on existing cluster
   Always remove it after bootstrap!
