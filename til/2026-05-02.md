## 🚦 First Response Protocol — Run These FIRST Always

```bash
# 1. Overall cluster status (first thing every time)
GET _cluster/health?pretty

# 2. Node health & resources
GET _cat/nodes?v&h=name,node.role,heap.percent,ram.percent,cpu,disk.used_percent,load_1m&s=name

# 3. Any unassigned shards?
GET _cat/shards?v&h=index,shard,prirep,state,node,reason&s=state

# 4. Any pending tasks?
GET _cluster/pending_tasks

# 5. Recent logs (on each node)
# tail -f /var/log/elasticsearch/my-cluster.log

# 6. What's running right now?
GET _tasks?detailed=true&actions=*search*,*write*,*reindex*
```

## 🔴 Part 1 — Cluster RED Status

### What RED Means

```
GREEN  = All primary + replica shards assigned ✅
YELLOW = All primary shards assigned, some replicas unassigned ⚠️
RED    = One or more PRIMARY shards unassigned ❌
         → Some data is UNAVAILABLE
         → Indexing/search on affected indices FAILS
```

### Step-by-Step RED Diagnosis

```bash
# Step 1: Which index is RED?
GET _cluster/health?level=indices&pretty
# Find indices with status: "red"

# Step 2: Which shard?
GET _cat/shards?v&h=index,shard,prirep,state,node,reason&s=state
# Look for state: UNASSIGNED with prirep: p (primary)

# Step 3: WHY is it unassigned? (most important command)
GET _cluster/allocation/explain
# OR for specific shard:
GET _cluster/allocation/explain
{
  "index": "my-index",
  "shard": 0,
  "primary": true
}

# Common explain responses and meanings:
# "no_valid_shard_copy" → ALL copies of shard data are gone
# "node_left"           → node holding shard left cluster
# "allocation_failed"   → previous allocation attempt failed
# "max_retries_exceeded" → too many allocation failures
# "disk_exceeded"       → disk watermark breach
# "no_attempt"          → not attempted yet
```

### Fix: Retry Failed Allocation

```bash
# Step 1: Retry allocation (safe — try this first)
POST _cluster/reroute?retry_failed=true

# Step 2: Check if resolved
GET _cluster/health?pretty
```

### Fix: Node Rejoining Cluster

```bash
# If node left and came back, shards should auto-assign
# If not, check why node left:
GET _cat/nodes?v&s=name

# Check pending cluster tasks
GET _cluster/pending_tasks

# Manually move shard to available node
POST _cluster/reroute
{
  "commands": [
    {
      "move": {
        "index": "my-index",
        "shard": 0,
        "from_node": "bad-node",
        "to_node": "good-node"
      }
    }
  ]
}
```

### Fix: Force Allocate Stale Primary (LAST RESORT — DATA LOSS!)

```bash
# Use ONLY when:
# 1. Node is permanently gone
# 2. No other copies of shard exist
# 3. You accept potential data loss

GET _cluster/allocation/explain
# Verify: "no_valid_shard_copy" in explanation

# Then force allocate (will lose data not yet replicated)
POST _cluster/reroute
{
  "commands": [
    {
      "allocate_stale_primary": {
        "index": "my-index",
        "shard": 0,
        "node": "available-node",
        "accept_data_loss": true
      }
    }
  ]
}
```

### Fix: Disk Watermark Causing RED

```bash
# Check disk usage
GET _cat/allocation?v

# If disk is full, temporary fix:
PUT _cluster/settings
{
  "transient": {
    "cluster.routing.allocation.disk.watermark.low": "90%",
    "cluster.routing.allocation.disk.watermark.high": "95%",
    "cluster.routing.allocation.disk.watermark.flood_stage": "97%"
  }
}

# Permanent fix: free up disk space OR add nodes
# Delete old indices after freeing space:
DELETE old-index-2024.01.*

# Then restore normal watermark settings:
PUT _cluster/settings
{
  "transient": {
    "cluster.routing.allocation.disk.watermark.low": null,
    "cluster.routing.allocation.disk.watermark.high": null,
    "cluster.routing.allocation.disk.watermark.flood_stage": null
  }
}
```

## 🟡 Part 2 — Cluster YELLOW Status

### What Causes YELLOW

```
1. Single-node cluster with replicas > 0
   → Can't assign replica to same node as primary
   → Fix: set replicas to 0 for dev

2. New node joining — shards being rebalanced
   → Normal — wait for rebalancing to complete
   → Monitor: GET _cat/recovery?v&active_only=true

3. Node left cluster — replicas were on that node
   → Wait for delayed allocation (default 1 min)
   → Or force allocation

4. Disk watermark breach
   → New replica allocation blocked
```

### Fix: Single-Node Dev Cluster

```bash
# Set replicas to 0 for all indices
PUT */_settings
{
  "number_of_replicas": 0
}

# Or set as cluster default for new indices
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.max_shards_per_node": 1000
  }
}

# Template for dev: always 0 replicas
PUT _index_template/dev-settings
{
  "index_patterns": ["*"],
  "priority": 1,
  "template": {
    "settings": { "number_of_replicas": 0 }
  }
}
```

### Delayed Shard Allocation

```bash
# Default: ES waits 1 min before reassigning shards from missing node
# This is good — node might just be rebooting

# Check current delay setting
GET _cluster/settings?filter_path=**.delayed_timeout

# Increase delay (give node more time to come back)
PUT _cluster/settings
{
  "transient": {
    "cluster.routing.allocation.node_left.delayed_timeout": "5m"
  }
}

# Cancel delay (reassign now — if you know node won't come back)
PUT _cluster/settings
{
  "transient": {
    "cluster.routing.allocation.node_left.delayed_timeout": "0"
  }
}
```

## 💾 Part 3 — Out of Memory (OOM) / Heap Issues

### Diagnose Heap Problems

```bash
# Check heap usage on all nodes
GET _cat/nodes?v&h=name,heap.current,heap.max,heap.percent&s=heap.percent:desc

# Heap > 75% = Warning
# Heap > 85% = Danger — GC pressure likely
# Heap > 90% = Critical — OOM imminent

# Detailed JVM stats
GET _nodes/stats/jvm

# Response shows:
# jvm.mem.heap_used_percent
# jvm.gc.collectors.young.collection_count
# jvm.gc.collectors.young.collection_time_in_millis
# jvm.gc.collectors.old.collection_count  ← old gen GC = problem

# Hot threads (what's consuming CPU/memory right now)
GET _nodes/hot_threads?interval=5s&snapshots=3&type=cpu
```

### Common Memory Hogs

```bash
# 1. Field data cache (text field aggregations)
GET _nodes/stats/indices/fielddata
# If fielddata.memory_size_in_bytes is large:
POST _cache/clear?fielddata=true

# Set field data limit
PUT _cluster/settings
{
  "persistent": {
    "indices.fielddata.cache.size": "20%"
  }
}

# 2. Query cache
GET _nodes/stats/indices/query_cache
POST _cache/clear?query=true

# 3. Segments memory (too many small segments)
GET _cat/segments?v&h=index,shard,segment,size,memory&s=memory:desc
# Fix: forcemerge indices with many segments
POST old-index/_forcemerge?max_num_segments=1

# 4. Circuit breakers
GET _nodes/stats/breaker
# If tripped: fielddata, request, in_flight_requests breakers
```

### Circuit Breaker Errors

```bash
# Error: "Data too large, data for [field] would be ..."

# Check circuit breaker stats
GET _nodes/stats/breaker

# Increase limits (carefully — can cause OOM)
PUT _cluster/settings
{
  "persistent": {
    "indices.breaker.fielddata.limit": "40%",
    "indices.breaker.request.limit": "40%",
    "indices.breaker.total.limit": "70%"
  }
}

# Better fix: avoid fielddata (use .keyword instead of .text for aggs)
# Or increase heap size on nodes
```

### Fix OOM — JVM Heap Tuning

```bash
# Rule: heap = 50% of RAM, max 30GB per node

# In jvm.options or ES_JAVA_OPTS:
-Xms16g
-Xmx16g
# ALWAYS set Xms = Xmx (prevents heap resizing)

# Check effective heap
GET _nodes?filter_path=nodes.*.jvm.mem.heap_max_in_bytes

# Enable GC logging (helps diagnose GC pressure):
-Xlog:gc*,gc+age=trace,safepoint:file=/var/log/elasticsearch/gc.log:utctime,pid,tags:filecount=32,filesize=64m
```

## 🐌 Part 4 — Slow Queries & Search Performance

### Enable Slow Log

```bash
# Per-index slow log settings
PUT logs-nginx-production/_settings
{
  "index.search.slowlog.threshold.query.warn": "10s",
  "index.search.slowlog.threshold.query.info": "5s",
  "index.search.slowlog.threshold.query.debug": "2s",
  "index.search.slowlog.threshold.query.trace": "500ms",
  "index.search.slowlog.threshold.fetch.warn": "1s",
  "index.search.slowlog.threshold.fetch.info": "500ms",
  "index.indexing.slowlog.threshold.index.warn": "10s",
  "index.indexing.slowlog.threshold.index.info": "5s",
  "index.search.slowlog.include.user": true
}

# Set for ALL indices (index template)
PUT _index_template/slowlog-settings
{
  "index_patterns": ["*"],
  "priority": 1,
  "template": {
    "settings": {
      "index.search.slowlog.threshold.query.warn": "5s",
      "index.search.slowlog.threshold.query.info": "2s",
      "index.indexing.slowlog.threshold.index.warn": "5s"
    }
  }
}
```

### Find Slow Queries in Real Time

```bash
# Find running slow queries (threshold: longer than 5s)
GET _tasks?detailed=true&actions=*search*&filter_path=nodes.*.tasks
# Look for running_time_in_nanos > 5000000000

# Cancel a slow query
POST _tasks/NODE_ID:TASK_ID/_cancel

# Find all long-running tasks
GET _tasks?detailed=true&timeout=30s&wait_for_completion=false
```

### Profile a Query (understand what's slow)

```bash
GET logs-nginx-production/_search
{
  "profile": true,
  "query": {
    "bool": {
      "must": [
        { "match": { "message": "error connection timeout" } },
        { "range": { "@timestamp": { "gte": "now-1h" } } }
      ]
    }
  }
}

# Profile output shows:
# shards[].searches[].query[].time_in_nanos → where time is spent
# shards[].aggregations[].time_in_nanos     → agg time
# shards[].searches[].collector             → score calculation time
```

### Common Slow Query Causes & Fixes

```bash
# 1. Wildcard / regex on text fields (VERY SLOW)
# BAD:
{ "wildcard": { "url.path": "*payment*" } }
# GOOD:
{ "match": { "url.path": "payment" } }
# OR use wildcard field type in mapping

# 2. Deep pagination
# BAD: from: 10000, size: 10
# GOOD: Use search_after
GET logs-nginx-production/_search
{
  "size": 10,
  "sort": [{ "@timestamp": "desc" }, { "_id": "asc" }],
  "search_after": ["2026-04-27T10:00:00Z", "last_doc_id"]
}

# 3. Aggregating on high-cardinality text field
# BAD:
{ "terms": { "field": "message" } }
# GOOD: map as keyword or use .keyword subfield
{ "terms": { "field": "url.path.keyword" } }

# 4. Script in query (slow — runs on every doc)
# BAD:
{ "script": { "source": "doc['field'].value > 100" } }
# GOOD: compute at index time, filter on stored value

# 5. Large result sets
# BAD: size: 10000
# GOOD: Scroll or search_after for large exports
```

### Scroll API (for large data exports)

```bash
# Initial request
GET logs-nginx-production/_search?scroll=2m
{
  "size": 1000,
  "sort": [{ "@timestamp": "desc" }],
  "query": { "range": { "@timestamp": { "gte": "now-7d" } } }
}
# Returns: _scroll_id

# Continue scrolling
POST _search/scroll
{
  "scroll": "2m",
  "scroll_id": "DXF1ZXJ5QW5kRmV0Y2gBAAAAAAABCGEWN..."
}

# Clear scroll when done
DELETE _search/scroll
{
  "scroll_id": "DXF1ZXJ5QW5kRmV0Y2gBAAAAAAABCGEWN..."
}
```

## 📨 Part 5 — Indexing Rejection Errors

### What Are Rejections?

```
ES uses thread pools for different operations:
  write  → indexing/bulk operations
  search → query operations

Each thread pool has a QUEUE.
When queue is full → REJECTED (HTTP 429)

Signs:
  "rejected execution of org.elasticsearch.transport.TransportService"
  HTTP 429 Too Many Requests
  "EsRejectedExecutionException"
```

### Diagnose Rejections

```bash
# Check thread pool stats — look for rejected > 0
GET _cat/thread_pool?v&h=name,type,active,rejected,queue,completed&s=rejected:desc

# Detailed stats per node
GET _nodes/stats/thread_pool

# Which indices are getting rejections?
GET _nodes/stats/indices/indexing?filter_path=nodes.*.indices.indexing.index_failed
```

### Fix Indexing Rejections

```bash
# 1. Slow down bulk indexing (reduce concurrency in client)
# 2. Increase queue size (temporary — masks the real problem)
PUT _cluster/settings
{
  "transient": {
    "thread_pool.write.queue_size": 2000
  }
}

# 3. Optimize bulk request size
# Target: 5-15MB per bulk request, 1000-5000 docs
# Test with different sizes and measure throughput

# 4. Increase refresh_interval during bulk load
PUT my-index/_settings
{
  "refresh_interval": "30s"
}

# 5. Disable replicas during bulk load (restore after)
PUT my-index/_settings
{
  "number_of_replicas": 0
}
# Re-enable after load:
PUT my-index/_settings
{
  "number_of_replicas": 1
}
```

## 🗂️ Part 6 — Shard Issues

### Too Many Shards

```bash
# Check total shard count per node
GET _cat/nodes?v&h=name,shards&s=shards:desc

# Rule: max 1000 shards per non-frozen data node
# Per GB of heap: flexible in new versions (old rule was 20/GB)

# List indices with too many shards
GET _cat/indices?v&h=index,pri,rep,docs.count&s=pri:desc

# Fix: Shrink index (reduces primary shard count)
# Step 1: Move all shards to one node
PUT too-many-shards-index/_settings
{
  "index.routing.allocation.require._name": "target-node",
  "index.blocks.write": true
}

# Step 2: Shrink
POST too-many-shards-index/_shrink/shrunk-index
{
  "settings": {
    "index.number_of_shards": 1,
    "index.number_of_replicas": 1,
    "index.routing.allocation.require._name": null,
    "index.blocks.write": null
  }
}

# Step 3: Verify shrunk index
GET shrunk-index/_count

# Step 4: Delete original
DELETE too-many-shards-index

# Step 5: Alias if needed
POST _aliases
{
  "actions": [
    { "add": { "index": "shrunk-index", "alias": "too-many-shards-index" } }
  ]
}
```

### Shard Rebalancing Issues

```bash
# Check shard distribution
GET _cat/shards?v&h=index,shard,prirep,state,node&s=node

# Check allocation settings
GET _cluster/settings?filter_path=**.allocation

# Enable/disable allocation
PUT _cluster/settings
{
  "transient": {
    "cluster.routing.allocation.enable": "all"
  }
}
# Values: all, primaries, new_primaries, none

# Rebalance shards manually
POST _cluster/reroute
{
  "commands": [
    {
      "move": {
        "index": "my-index",
        "shard": 0,
        "from_node": "overloaded-node",
        "to_node": "underloaded-node"
      }
    }
  ]
}

# Check hot shards (which shards are being written to most)
GET _cat/shards?v&h=index,shard,prirep,node,indexing.index_total&s=indexing.index_total:desc
```

### Shard Store / Recovery Issues

```bash
# Check shard store info (which nodes have copies)
GET _shard_stores?status=red,yellow

# Active recoveries
GET _cat/recovery?v&active_only=true

# Recovery stats
GET _recovery?human=true&detailed=true

# Throttle recovery speed (reduce impact on production)
PUT _cluster/settings
{
  "transient": {
    "indices.recovery.max_bytes_per_sec": "50mb"
  }
}
```

## 🔍 Part 7 — Master Node Issues

### Master Node Problems

```bash
# Who is current master?
GET _cat/master?v

# Master election logs (in ES logs)
# Look for: "master node changed"
# Look for: "ClusterApplierService" warnings

# Pending tasks (master processes these)
GET _cluster/pending_tasks

# If pending_tasks is large + growing = master overloaded

# Check master node heap (master needs memory for cluster state)
GET _nodes/master/stats/jvm

# Master CPU + load
GET _cat/nodes?v&h=name,master,cpu,load_1m,heap.percent&s=master:desc
```

### Split Brain Prevention

```bash
# In elasticsearch.yml — CRITICAL for multi-node clusters
discovery.zen.minimum_master_nodes: 2   # for ES < 7.x

# ES 7+ uses Raft-based consensus — no split brain possible
# But still need dedicated master nodes (3 minimum!)
node.roles: [master]   # dedicated master node config

# Check voting configuration
GET _cluster/voting_config_exclusions
```

## ❌ Part 9 — Common Mistakes & Fixes

| Problem | Symptoms | Fix |
|---|---|---|
| Too many shards | Heap pressure, slow master | Shrink/delete indices, increase heap |
| Fielddata on text fields | Heap spike, OOM | Use `.keyword`, set fielddata limit |
| Deep pagination | Timeout, high memory | Use `search_after` instead of `from/size` |
| No retry_failed after recovery | RED stuck after fix | `POST _cluster/reroute?retry_failed=true` |
| Watermark on wrong node role | Can't assign cold tier | Check `_cat/allocation`, fix disk space |
| All nodes eligible for master | Split brain risk | Dedicate 3 nodes as master-only |
| Replica count = 0 in prod | No redundancy | Set replicas ≥ 1 for prod |
| Large bulk request | Rejections, OOM | Target 5-15MB per request |
| Missing `min_doc_count: 0` | Missing time gaps | Add to date_histogram |
| No circuit breaker monitoring | Silent OOM | Alert on breaker trip count |
| Slow log not enabled | Can't find slow queries | Enable on all indices via template |

## 💡 Key Principles — Summary

```
1. Always start with _cluster/health and _cat/nodes
   → These tell you 80% of what's wrong in 30 seconds

2. _cluster/allocation/explain is your best friend for RED
   → Never guess why a shard is unassigned — ask Elasticsearch

3. allocate_stale_primary is last resort only
   → Always try retry_failed and move first

4. Heap > 75% = investigate immediately
   → 85% = you're in trouble, 90% = OOM likely

5. Fielddata = heap killer
   → Never aggregate on text fields, always use .keyword

6. Slow queries → profile first, optimize after
   → Use "profile": true to find exactly where time is spent

7. Rejections = ES is overwhelmed
   → Fix the root cause (reduce load), not just increase queue

8. Too many shards = #1 cause of cluster instability
   → Monitor shards/node, keep < 1000 per non-frozen data node

9. 3 dedicated master nodes minimum in production
   → Never mix master + data roles on same nodes in production

10. Enable slow logs in all environments
    → You can't debug what you can't see
```
