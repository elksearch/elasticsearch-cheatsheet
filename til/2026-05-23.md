## Multi-tenancy Patterns in Elasticsearch
### Index-per-Tenant, Shared Index, Spaces, DLS, Cost Isolation, Production Architecture

> Multi-tenancy means serving multiple customers/teams from one Elasticsearch cluster.
> The wrong pattern causes data leaks, performance issues, or cost explosion.
> This document covers every pattern with trade-offs and production implementation.

## 🧠 Three Multi-tenancy Patterns

```
PATTERN 1: INDEX PER TENANT
  Each tenant → separate index/data stream
  logs-tenant-a-production
  logs-tenant-b-production

  ✅ Complete data isolation
  ✅ Per-tenant index settings (shards, retention)
  ✅ Per-tenant performance isolation
  ✅ Easy to delete tenant data
  ❌ Many indices → master node pressure
  ❌ Hard to cross-tenant query
  ❌ Resource waste for small tenants

PATTERN 2: SHARED INDEX WITH TENANT FIELD
  All tenants → same index, filtered by field
  logs-production (tenant_id field)

  ✅ Few indices → low master overhead
  ✅ Easy cross-tenant analytics (admin)
  ✅ Efficient for many small tenants
  ❌ Resource contention between tenants
  ❌ One tenant's bad query hurts others
  ❌ Tenant deletion = delete_by_query (slow)
  ❌ Data isolation requires DLS (complex)

PATTERN 3: HYBRID (Recommended for Production)
  Large tenants → dedicated index
  Small tenants → shared index

  ✅ Best of both worlds
  ✅ Tier tenants by size/tier
  ✅ Cost effective
  ❌ More complex routing logic

PATTERN 4: CLUSTER PER TENANT (Enterprise)
  Dedicated cluster per large tenant
  ✅ Maximum isolation
  ❌ Very expensive
  ❌ Hard to manage at scale
```

## 🗂️ Part 1 — Index Per Tenant Pattern

### Setup

```bash
# Index template for per-tenant indices
PUT _index_template/tenant-logs-template
{
  "index_patterns": ["logs-tenant-*"],
  "data_stream": {},
  "priority": 500,
  "template": {
    "settings": {
      "number_of_shards": 1,
      "number_of_replicas": 1,
      "index.lifecycle.name": "tenant-logs-policy"
    },
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "tenant_id": { "type": "keyword" },
        "message": { "type": "text" },
        "log.level": { "type": "keyword" },
        "service.name": { "type": "keyword" }
      }
    }
  }
}

# Create data stream per tenant (auto-created on first write)
PUT _data_stream/logs-tenant-acme-production
PUT _data_stream/logs-tenant-globex-production
PUT _data_stream/logs-tenant-initech-production

# Per-tenant ILM (different retention per tenant plan)
PUT _ilm/policy/tenant-logs-basic-policy
{
  "policy": {
    "phases": {
      "hot": { "actions": { "rollover": { "max_age": "1d" } } },
      "delete": { "min_age": "30d", "actions": { "delete": {} } }
    }
  }
}

PUT _ilm/policy/tenant-logs-enterprise-policy
{
  "policy": {
    "phases": {
      "hot": { "actions": { "rollover": { "max_age": "1d" } } },
      "warm": { "min_age": "7d", "actions": { "shrink": { "number_of_shards": 1 } } },
      "delete": { "min_age": "365d", "actions": { "delete": {} } }
    }
  }
}
```

### Per-Tenant RBAC

```bash
# Role for Tenant ACME — only sees their index
PUT _security/role/tenant-acme-role
{
  "cluster": ["monitor"],
  "indices": [
    {
      "names": ["logs-tenant-acme-*", "metrics-tenant-acme-*"],
      "privileges": ["read", "view_index_metadata"]
    }
  ],
  "applications": [
    {
      "application": "kibana-.kibana",
      "privileges": ["space_all"],
      "resources": ["space:acme"]   # only ACME's Kibana space
    }
  ]
}

# Create tenant user
POST _security/user/acme-admin
{
  "password": "SecurePassword123!",
  "roles": ["tenant-acme-role"],
  "full_name": "ACME Admin"
}

# Scoped API key for ACME's application
POST _security/api_key
{
  "name": "acme-api-key",
  "expiration": "90d",
  "role_descriptors": {
    "acme-writer": {
      "cluster": ["monitor"],
      "indices": [
        {
          "names": ["logs-tenant-acme-*"],
          "privileges": ["write", "create", "create_index", "manage"]
        }
      ]
    }
  },
  "metadata": { "tenant": "acme", "created": "2026-05-23" }
}
```

### Index Naming Convention

```
{type}-tenant-{tenant_id}-{namespace}
  logs-tenant-acme-production
  logs-tenant-acme-staging
  metrics-tenant-acme-production
  traces-tenant-acme-production

{type}-{tier}-tenant-{tenant_id}
  logs-hot-tenant-acme
  logs-warm-tenant-acme

RULES:
  → lowercase only
  → no spaces (use hyphens)
  → tenant_id: alphanumeric + hyphens
  → max 255 characters
  → avoid leading underscore (reserved for .hidden indices)
```

## 🔀 Part 2 — Shared Index with DLS

### Setup Shared Index

```bash
# Single index for all tenants
PUT _index_template/shared-logs-template
{
  "index_patterns": ["shared-logs-*"],
  "data_stream": {},
  "template": {
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "tenant_id": { "type": "keyword" },
        "message": { "type": "text" },
        "log.level": { "type": "keyword" }
      }
    }
  }
}

# Write documents with tenant_id
POST shared-logs-production/_doc
{
  "@timestamp": "2026-05-23T10:00:00Z",
  "tenant_id": "acme",
  "message": "ACME application started",
  "log.level": "INFO"
}

POST shared-logs-production/_doc
{
  "@timestamp": "2026-05-23T10:00:01Z",
  "tenant_id": "globex",
  "message": "Globex request received",
  "log.level": "INFO"
}
```

### Document Level Security (DLS) per Tenant

```bash
# Role with DLS — user only sees their tenant's docs
PUT _security/role/tenant-acme-shared-role
{
  "indices": [
    {
      "names": ["shared-logs-*", "shared-metrics-*"],
      "privileges": ["read"],
      "query": {
        "term": {
          "tenant_id": "acme"      # ← only ACME documents visible
        }
      },
      "field_security": {
        "grant": ["@timestamp", "message", "log.level", "service.*"],
        "except": []
      }
    }
  ]
}

# Dynamic DLS using username template
PUT _security/role/tenant-user-role
{
  "indices": [
    {
      "names": ["shared-logs-*"],
      "privileges": ["read"],
      "query": {
        "template": {
          "source": {
            "term": {
              "tenant_id": "{{_user.metadata.tenant_id}}"
            }
          }
        }
      }
    }
  ]
}

# Create user with tenant metadata
POST _security/user/acme-user
{
  "password": "password",
  "roles": ["tenant-user-role"],
  "metadata": {
    "tenant_id": "acme"           # ← used in DLS template
  }
}
# When acme-user searches → DLS automatically filters to tenant_id=acme
# When globex-user searches → DLS filters to tenant_id=globex
```

### Delete Tenant Data (Shared Index)

```bash
# Delete tenant's data from shared index (slow for large tenants)
POST shared-logs-production/_delete_by_query?wait_for_completion=false
{
  "query": {
    "term": { "tenant_id": "acme" }
  }
}

# Monitor deletion
GET _tasks?actions=*delete*&detailed=true
```

## 🏗️ Part 4 — Hybrid Pattern (Production Recommended)

### Tenant Tiering

```
TIER 1 (Enterprise — Large):
  → Dedicated index/data stream
  → Custom ILM policy
  → Dedicated Kibana space
  → Dedicated API keys
  → SLA: 99.9% uptime, 1 year retention

TIER 2 (Professional — Medium):
  → Dedicated index per type
  → Shared ILM policy
  → Shared Kibana space with DLS
  → Shared API keys
  → SLA: 99.5% uptime, 90 day retention

TIER 3 (Basic — Small):
  → Shared index with DLS
  → Common ILM policy
  → Shared Kibana space with DLS
  → Single shared API key
  → SLA: 99% uptime, 30 day retention

ROUTING LOGIC:
  At ingest time: route based on tenant tier
  → Enterprise → logs-tenant-{id}-production (dedicated)
  → Professional → logs-pro-{id}-production (semi-dedicated)
  → Basic → logs-shared-production (shared)
```

### Implementation

```python
# Python routing example
class TenantRouter:
    TIERS = {
        "enterprise": {"index_pattern": "logs-tenant-{tenant_id}-production"},
        "professional": {"index_pattern": "logs-pro-{tenant_id}-production"},
        "basic": {"index_pattern": "logs-shared-production"}
    }

    def __init__(self, es_client):
        self.es = es_client
        self.tenant_tiers = {}  # cache from database

    def get_index(self, tenant_id: str) -> str:
        tier = self.tenant_tiers.get(tenant_id, "basic")
        pattern = self.TIERS[tier]["index_pattern"]
        return pattern.format(tenant_id=tenant_id)

    def index_document(self, tenant_id: str, document: dict):
        index = self.get_index(tenant_id)
        document["tenant_id"] = tenant_id
        document["tenant_tier"] = self.tenant_tiers.get(tenant_id, "basic")
        return self.es.index(index=index, document=document)

    def search(self, tenant_id: str, query: dict):
        tier = self.tenant_tiers.get(tenant_id, "basic")

        if tier == "enterprise":
            # Search dedicated index
            index = f"logs-tenant-{tenant_id}-production"
        elif tier in ["professional", "basic"]:
            # Search shared index with tenant filter
            index = "logs-shared-production"
            query["query"] = {
                "bool": {
                    "must": [query.get("query", {"match_all": {}})],
                    "filter": [{"term": {"tenant_id": tenant_id}}]
                }
            }

        return self.es.search(index=index, body=query)
```

## 📊 Part 5 — Resource Isolation & Fairness

### Rate Limiting per Tenant

```bash
# Use search throttling per user/role
PUT _security/role/tenant-acme-role
{
  "indices": [
    {
      "names": ["logs-tenant-acme-*"],
      "privileges": ["read"]
    }
  ],
  "cluster": ["monitor"]
}

# Watcher or external rate limiter needed for request rate limiting
# ES doesn't have built-in per-tenant rate limiting
# Pattern: API gateway (nginx/Kong) with per-tenant rate limits
# → Kong: rate-limit plugin per consumer
# → nginx: limit_req_zone by $http_authorization
```

### Cost Attribution

```bash
# Track per-tenant resource usage
# Use ES index stats filtered by tenant index pattern

GET logs-tenant-acme-*/_stats/store,docs,indexing,search

# Response:
# _all.total.store.size_in_bytes → storage cost
# _all.total.indexing.index_total → write operations
# _all.total.search.query_total → read operations

# Create cost report
GET _all/_stats/store,docs?filter_path=indices.*.total.store,indices.*.total.docs
# Process output to calculate per-tenant costs
```

### Shard Budget per Tenant

```bash
# Prevent one tenant from creating too many shards
# Index template with conservative shard count
PUT _index_template/tenant-basic-template
{
  "index_patterns": ["logs-tenant-*"],
  "template": {
    "settings": {
      "number_of_shards": 1,          # single shard per index
      "number_of_replicas": 1,
      "index.lifecycle.name": "tenant-basic-policy"
    }
  }
}

# Monitor shard count per tenant
GET _cat/shards?v&h=index,shard,prirep,state&s=index | grep tenant-acme | wc -l

# Alert when tenant exceeds shard budget
# 30 days × 1 shard per day × 2 (replica) = 60 shards per tenant
# Alert when > 70 shards for a single tenant
```

## 🔐 Part 6 — Security Patterns

### Defense in Depth

```
LAYER 1: Network
  → Separate endpoint per tenant (tenant.myservice.com)
  → API Gateway (Kong/nginx) validates tenant token
  → Rate limiting at gateway level

LAYER 2: Authentication
  → Per-tenant API keys (ES)
  → Short expiry (90 days)
  → Scoped to tenant's indices only

LAYER 3: Authorization (RBAC)
  → Per-tenant roles
  → Index pattern restriction
  → Field-level security for sensitive fields

LAYER 4: Data Isolation (DLS)
  → Document-level filter on tenant_id
  → Even if RBAC bypassed, DLS is server-side

LAYER 5: Audit Logging
  → All access logged
  → Per-tenant audit trail
  → Alert on cross-tenant access attempts
```

### Audit Configuration per Tenant

```bash
# Enable audit logging for cross-tenant access
PUT _cluster/settings
{
  "persistent": {
    "xpack.security.audit.enabled": true,
    "xpack.security.audit.logfile.events.include": [
      "access_denied",
      "authentication_failed",
      "access_granted"
    ]
  }
}

# Search audit logs for tenant violations
GET .security-audit-*/_search
{
  "query": {
    "bool": {
      "must": [
        { "term": { "event.type": "access_denied" } }
      ],
      "filter": [
        { "range": { "@timestamp": { "gte": "now-24h" } } }
      ]
    }
  }
}
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| No tenant_id in shared index | Can't filter per tenant | Always add tenant_id to every document |
| DLS without testing | Data leaks between tenants | Test DLS with each tenant user explicitly |
| Too many dedicated indices for small tenants | Shard explosion | Use shared index for tenants with < 1GB/day |
| Same API key for all tenants | One breach = all data exposed | Unique API key per tenant |
| No shard budget per tenant | One tenant creates 10k shards | ILM + single shard per index |
| No rate limiting | One tenant starves others | API gateway rate limiting per tenant |
| Kibana space without data view restriction | Cross-tenant data visible | Restrict data views to tenant pattern |
| DLS performance impact | Slow queries | DLS adds overhead — benchmark first |
| Not testing tenant isolation | Assumes isolation works | Test cross-tenant query with each tenant credential |
| No tenant audit trail | Can't prove compliance | Enable audit logging from day 1 |

## 💡 Key Principles

```
1. Choose pattern based on tenant count and size
   < 100 tenants, large data → index per tenant
   > 1000 tenants, small data → shared index with DLS
   Mix → hybrid (tier-based)

2. DLS is server-side and reliable
   → Client-side tenant filtering is not enough
   → Always enforce with DLS for security

3. Unique API key per tenant
   → One breach = one tenant affected, not all

4. Shard budget planning prevents surprises
   → 1 shard per daily index × 365 days × 100 tenants = 36,500 shards
   → Plan for scale before deploying

5. Kibana Spaces = UI isolation
   → Each tenant's Kibana space is completely separate

6. Rate limiting at API gateway level
   → Elasticsearch doesn't have per-user rate limits built-in

7. Audit logs prove compliance
   → GDPR/SOC2 requires proof of data isolation

8. Test isolation with tenant credentials
   → Never assume DLS works — test every tenant combination

9. Offboarding process must be documented
   → Delete data, revoke access, remove billing — all automated

10. Tenant metadata in documents
    → tenant_id, tenant_tier, subscription_plan — always indexed
```
