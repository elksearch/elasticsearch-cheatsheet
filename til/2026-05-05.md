## Mappings Deep Dive
### Field Types, Dynamic Mapping, Runtime Fields, Nested vs Object, Mapping Explosion

> Mappings define how documents and their fields are stored and indexed.
> Wrong mappings = wrong search results, huge storage costs, or complete failure to index.
> Mappings cannot be changed on existing fields — getting them right the first time matters.

## 🧠 Core Concepts

```
MAPPING = Schema definition for an Elasticsearch index

Without mapping: ES guesses types (dynamic mapping)
With mapping:    ES enforces types (explicit mapping)

KEY RULE: You CANNOT change a field's type after indexing
  → Change field type = reindex required (full data copy)
  → Adding new fields = always allowed
  → Removing fields = only via reindex

TWO TYPES:
  Dynamic mapping  → ES infers types from first document seen
  Explicit mapping → You define types in advance
```

        "type": "date",

      "duration_ms":     { "type": "long" },

### Network & Geo Types

```bash
{
  "properties": {
    "source_ip": { "type": "ip" },
    "location":  { "type": "geo_point" },
    "region":    { "type": "geo_shape" },
    "version":   { "type": "version" }
  }
}

# geo_point: lat/lon point
# geo_shape: polygons, lines, complex shapes

# geo_point input formats (all accepted):
# { "lat": 19.07, "lon": 72.87 }
# "19.07,72.87"
# [72.87, 19.07]   ← NOTE: lon,lat order for arrays!
# "u09tvqx"        ← geohash
```

## 🔄 Part 2 — Dynamic Mapping

### How Dynamic Mapping Works

```
First document with a new field → ES infers type:

JSON type          → Elasticsearch type
─────────────────────────────────────────
string             → text + keyword (multi-field)
number (no dot)    → long
number (with dot)  → float
boolean            → boolean
date string        → date (if matches date_detection formats)
object {}          → object (nested fields mapped recursively)
array []           → type of first element

PROBLEM: Once mapped, cannot change!
  → "200" in first doc → keyword
  → Next doc sends 200 (integer) → INDEX FAILURE
```

### Dynamic Mapping Modes

```bash
PUT my-index
{
  "mappings": {
    "dynamic": "strict"
  }
}

# "true"   → auto-create fields for unknown types (DEFAULT)
# "false"  → ignore unknown fields (not indexed, not stored)
# "strict" → reject documents with unknown fields (exception)
# "runtime"→ map new fields as runtime fields

# Best practice for production: "strict" on core fields
# Use "false" or "runtime" for dynamic/unknown fields
```

### Dynamic Templates — Control Auto-Mapping

```bash
PUT my-index
{
  "mappings": {
    "dynamic_templates": [
      {
        "strings_as_keyword": {
          "match_mapping_type": "string",
          "mapping": {
            "type": "keyword"
          }
        }
      },
      {
        "message_as_text": {
          "match": "message",
          "match_mapping_type": "string",
          "mapping": {
            "type": "text",
            "fields": {
              "keyword": {
                "type": "keyword",
                "ignore_above": 1024
              }
            }
          }
        }
      },
      {
        "longs_as_integers": {
          "match_mapping_type": "long",
          "mapping": {
            "type": "integer"
          }
        }
      },
      {
        "all_ip_fields": {
          "match": "*_ip",
          "mapping": { "type": "ip" }
        }
      },
      {
        "location_fields": {
          "path_match": "*.geo.location",
          "mapping": { "type": "geo_point" }
        }
      }
    ]
  }
}
```

### Numeric Detection & Date Detection

```bash
PUT my-index
{
  "mappings": {
    "numeric_detection": true,
    "date_detection": true,
    "dynamic_date_formats": [
      "strict_date_optional_time",
      "yyyy/MM/dd HH:mm:ss",
      "yyyy/MM/dd"
    ]
  }
}
# numeric_detection: "100" string → mapped as long (not text)
# date_detection: "2026-04-27" → mapped as date (not text)
# Warning: can cause issues if first value looks like date but isn't
# Recommendation: disable date_detection, map @timestamp explicitly
```

## 🏗️ Part 3 — Object vs Nested Fields

### Object Type (Default for JSON objects)

```bash
# Document:
{
  "user": {
    "name": "Vinay Patel",
    "age": 35,
    "city": "Mumbai"
  }
}

# Mapping:
{
  "properties": {
    "user": {
      "type": "object",       ← default, can omit "type"
      "dynamic": false,
      "properties": {
        "name": { "type": "keyword" },
        "age":  { "type": "integer" },
        "city": { "type": "keyword" }
      }
    }
  }
}

# Internally stored as flat:
# user.name = "Vinay Patel"
# user.age  = 35
# user.city = "Mumbai"
```

### The Object Array Problem

```bash
# Document with array of objects:
{
  "tags": [
    { "name": "elasticsearch", "weight": 5 },
    { "name": "kibana", "weight": 3 }
  ]
}

# Internally flattened to:
# tags.name   = ["elasticsearch", "kibana"]
# tags.weight = [5, 3]

# PROBLEM: Relationship between name and weight is LOST!
# Query: find docs where tags.name=elasticsearch AND tags.weight=5
GET my-index/_search
{
  "query": {
    "bool": {
      "must": [
        { "term": { "tags.name": "elasticsearch" } },
        { "term": { "tags.weight": 3 } }      ← weight 3, not 5!
      ]
    }
  }
}
# This MATCHES — because name and weight checked independently
# WRONG RESULT — elasticsearch has weight 5, not 3!

# FIX: Use nested type
```

### Nested Type (preserves object array relationships)

```bash
PUT my-index
{
  "mappings": {
    "properties": {
      "tags": {
        "type": "nested",
        "properties": {
          "name":   { "type": "keyword" },
          "weight": { "type": "integer" }
        }
      }
    }
  }
}

# Query nested objects correctly:
GET my-index/_search
{
  "query": {
    "nested": {
      "path": "tags",
      "query": {
        "bool": {
          "must": [
            { "term": { "tags.name":   "elasticsearch" } },
            { "term": { "tags.weight": 5 } }
          ]
        }
      },
      "score_mode": "avg"
    }
  }
}
# Correctly finds: elasticsearch with weight=5 (not 3)

# Nested aggs:
GET my-index/_search
{
  "size": 0,
  "aggs": {
    "all_tags": {
      "nested": { "path": "tags" },
      "aggs": {
        "tag_names": {
          "terms": { "field": "tags.name" }
        }
      }
    }
  }
}
```

### Object vs Nested — Decision Guide

```
USE OBJECT when:
  ✅ Array of objects is NOT in the data (single object only)
  ✅ You don't need to query field combinations within same array element
  ✅ Performance matters (nested = separate hidden documents)

USE NESTED when:
  ✅ Array of objects where field relationships matter
  ✅ Need to query "tag X has weight Y" not just "has tag X" and "has weight Y"
  ✅ Line items in orders, tags with attributes, events in a timeline

PERFORMANCE NOTE:
  Each nested object = hidden Lucene document
  100 nested objects = 101 documents internally
  → Nested queries are slower than object queries
  → Nested updates = full re-index of parent document
```

## 🗜️ Part 4 — Flattened Field Type

### What is Flattened?

```
Flattened type maps an entire JSON object as a single field.
All leaf values → indexed as keywords.
Great for: logging metadata, labels, arbitrary key-value pairs.

Solves the MAPPING EXPLOSION problem.
```

```bash
# Without flattened — mapping explosion risk:
{
  "labels": {
    "app": "nginx",
    "environment": "prod",
    "team": "platform",
    "region": "ap-south-1",
    "unknown_key_xyz": "value"   ← each new key = new mapping field!
  }
}

# With flattened — all values as one field:
PUT my-index
{
  "mappings": {
    "properties": {
      "labels": { "type": "flattened" }
    }
  }
}

# Query flattened field:
GET my-index/_search
{
  "query": {
    "term": { "labels.environment": "prod" }
  }
}

# Limitations:
# → Only supports keyword-type queries (no range, no full-text)
# → No sub-field aggregations (can agg on labels itself, not labels.*)
```

## 🧮 Part 5 — Runtime Fields

### What Are Runtime Fields?

```
Runtime fields are computed at query time — NOT stored in index.
Great for:
  → Fixing wrong field types without reindexing
  → Adding computed fields on the fly
  → Experimenting before committing to mapping change

Trade-off:
  → Slower queries (computed per document, no inverted index)
  → No doc_values (can't sort efficiently)
  → Great for low-frequency exploratory queries
```

### Define Runtime Fields in Mapping

```bash
PUT my-index
{
  "mappings": {
    "runtime": {
      "day_of_week": {
        "type": "keyword",
        "script": {
          "source": """
            emit(doc['@timestamp'].value.dayOfWeekEnum.getDisplayName(
              TextStyle.FULL, Locale.ROOT
            ));
          """
        }
      },
      "response_time_seconds": {
        "type": "double",
        "script": {
          "source": "emit(doc['event.duration'].value / 1000.0)"
        }
      },
      "is_error": {
        "type": "boolean",
        "script": {
          "source": """
            emit(doc['http.response.status_code'].value >= 500)
          """
        }
      }
    },
    "properties": {
      "@timestamp": { "type": "date" },
      "event.duration": { "type": "long" },
      "http.response.status_code": { "type": "integer" }
    }
  }
}

# Use runtime field in query
GET my-index/_search
{
  "query": {
    "term": { "day_of_week": "Monday" }
  },
  "fields": ["day_of_week", "response_time_seconds"]
}

# Aggregate on runtime field
GET my-index/_search
{
  "size": 0,
  "aggs": {
    "by_day": {
      "terms": { "field": "day_of_week" }
    }
  }
}
```

### Runtime Fields at Query Time (without mapping change)

```bash
# Define runtime field only for this query — no mapping change!
GET my-index/_search
{
  "runtime_mappings": {
    "price_with_tax": {
      "type": "double",
      "script": {
        "source": "emit(doc['price'].value * 1.18)"
      }
    }
  },
  "query": {
    "range": {
      "price_with_tax": { "gte": 1000 }
    }
  },
  "fields": ["price", "price_with_tax"]
}
```

## 💥 Part 6 — Mapping Explosion Prevention

### What is Mapping Explosion?

```
Mapping explosion = too many fields in mapping → Master node OOM

Causes:
  → Dynamic mapping + unpredictable field names
  → User-generated keys: {"label_xyz": 1, "label_abc": 2}
  → Log messages parsed as structured JSON with random keys
  → Kibana shows "field count limit exceeded" error

Default limit: 1000 fields per index
              (configurable via index.mapping.total_fields.limit)
```

### Prevention Strategies

```bash
# Strategy 1: Set strict total fields limit
PUT _index_template/my-template
{
  "template": {
    "settings": {
      "index.mapping.total_fields.limit": 2000,
      "index.mapping.depth.limit": 20,
      "index.mapping.nested_fields.limit": 50,
      "index.mapping.nested_objects.limit": 10000,
      "index.mapping.field_name_length.limit": 200
    }
  }
}

# Strategy 2: Use flattened for dynamic key-value data
{
  "properties": {
    "labels":      { "type": "flattened" },
    "user_attrs":  { "type": "flattened" },
    "custom_tags": { "type": "flattened" }
  }
}

# Strategy 3: dynamic: false for catch-all objects
{
  "properties": {
    "metadata": {
      "type": "object",
      "dynamic": false
    }
  }
}

# Strategy 4: dynamic: "strict" at index level
{
  "mappings": {
    "dynamic": "strict",
    "properties": { ... }
  }
}

# Check current field count
GET my-index/_mapping | python3 -c "
import json,sys
m = json.load(sys.stdin)
fields = 0
def count(d):
    global fields
    if 'properties' in d:
        fields += len(d['properties'])
        for v in d['properties'].values():
            count(v)
count(list(m.values())[0]['mappings'])
print(f'Field count: {fields}')
"
```

## 🔧 Part 7 — Mapping Parameters

### Important Parameters for Every Field

```bash
{
  "my_field": {
    "type": "keyword",

    # INDEXING CONTROL
    "index": true,           # false = not searchable (saves disk)
    "doc_values": true,      # false = no sorting/agg (saves disk)
    "store": false,          # true = stored separately from _source

    # NULL HANDLING
    "null_value": "N/A",     # substitute for null values in index
    "ignore_above": 256,     # strings longer than this = not indexed

    # FIELD CONTROL
    "copy_to": "all_fields", # copy value to another field

    # EAGER LOADING
    "eager_global_ordinals": true   # for high-cardinality terms aggs

  }
}

{
  "my_text_field": {
    "type": "text",

    # ANALYSIS
    "analyzer": "standard",
    "search_analyzer": "standard",
    "search_quote_analyzer": "standard",

    # SCORING
    "index_options": "positions",  # docs, freqs, positions, offsets
    "similarity": "BM25",

    # TERM VECTORS (for highlighting, more-like-this)
    "term_vector": "with_positions_offsets",

    # PERFORMANCE
    "norms": true,           # false = don't factor field length into score
    "fielddata": false       # true = enable (AVOID — heap killer!)
  }
}
```

## 🔄 Part 8 — Reindexing for Mapping Changes

### When Reindex is Required

```
Reindex REQUIRED for:
  ✅ Changing a field's TYPE (text → keyword)
  ✅ Changing analyzer on a field
  ✅ Enabling/disabling doc_values on existing field
  ✅ Removing dynamic: true (already dynamically mapped fields stay)

Reindex NOT required for:
  ✅ Adding new fields
  ✅ Adding new analyzers
  ✅ Changing index.number_of_replicas
  ✅ Updating most index settings
  ✅ Adding runtime fields
```

### Safe Reindex Process

```bash
# Step 1: Create new index with correct mapping
PUT my-index-v2
{
  "mappings": {
    "properties": {
      "status": { "type": "keyword" }
    }
  }
}

# Step 2: Reindex data
POST _reindex?wait_for_completion=false
{
  "source": {
    "index": "my-index",
    "query": { "match_all": {} },
    "size": 5000
  },
  "dest": {
    "index": "my-index-v2"
  }
}

# Check reindex task progress
GET _tasks?actions=*reindex&detailed=true

# Step 3: Verify count matches
GET my-index/_count
GET my-index-v2/_count

# Step 4: Switch alias atomically (zero downtime)
POST _aliases
{
  "actions": [
    { "remove": { "index": "my-index",    "alias": "my-alias" } },
    { "add":    { "index": "my-index-v2", "alias": "my-alias" } }
  ]
}

# Step 5: Delete old index (after verifying all good)
DELETE my-index
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Term query on text field | Never matches | Use match query or map as keyword |
| Aggregation on text field | Fielddata heap pressure | Use `.keyword` subfield |
| Not using multi-fields | Can't both search and aggregate | Add `.keyword` sub-field to text |
| Dynamic mapping on user-input keys | Mapping explosion | Use flattened or disable dynamic |
| Wrong date format | Date not indexed as date | Always specify format explicitly |
| Nested for single objects | Unnecessary overhead | Use object type for single objects |
| Changing field type on live index | Mapping error | Reindex to new index |
| No null_value on important fields | Nulls not queryable | Set `null_value` for critical fields |
| store: true on all fields | 2x disk usage | Only store fields not in _source |
| fielddata: true on text fields | OOM risk | Use keyword subfield instead |

## 💡 Key Principles

```
1. Map @timestamp explicitly always
   → Never rely on dynamic date detection

2. Text + keyword multi-field is the standard
   → message: text (for search) + message.keyword: keyword (for agg)

3. Use keyword for anything you'll filter/aggregate
   → status, level, service.name, environment = keyword

4. Dynamic mapping in production = mapping explosion risk
   → Set dynamic: strict for known fields, flattened for unknown

5. Nested only when you need per-array-element query accuracy
   → Cost: each nested object = hidden Lucene document

6. Runtime fields = schema flexibility without reindex
   → Use for experimentation, fixing wrong types, computed fields

7. Cannot change field type without reindex
   → Get mappings right before going to production

8. ignore_above: 256 on keywords
   → Prevents indexing of massive string values

9. Set total_fields.limit explicitly
   → Default 1000 is often too low for complex logs

10. ECS (Elastic Common Schema) = standard field naming
    → Always use ECS field names for interoperability
```
