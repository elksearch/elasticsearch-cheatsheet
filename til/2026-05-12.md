## Vector Search & AI
### Dense Vectors, KNN, Semantic Search, Hybrid Search, RAG, RRF

> Vector search transforms Elasticsearch from keyword search to meaning-based search.
> Combined with LLMs, it powers Retrieval Augmented Generation (RAG) — the foundation of enterprise AI.
> This document covers the complete vector search stack from embeddings to production RAG.

## 🧠 Core Concepts

```
EMBEDDINGS = numerical representations of meaning
  → Text → dense_vector (e.g., 384 or 1536 dimensions)
  → Similar meaning = similar vectors (close in space)
  → "timeout" and "not responding" are near in vector space
  → "cat" and "dog" are near, "cat" and "database" are far

KNN SEARCH = find K nearest neighbors in vector space
  → "Show me the 10 most semantically similar documents"
  → Uses HNSW (Hierarchical Navigable Small World) index
  → Approximate (ANN) — not exact — trades accuracy for speed

HYBRID SEARCH = BM25 (keywords) + KNN (meaning)
  → Best of both worlds
  → Exact matches (BM25) + semantic matches (KNN) combined via RRF

RRF = Reciprocal Rank Fusion
  → Combines rankings from multiple retrievers
  → Score = Σ 1/(k + rank_i)  where k=60 (constant)
  → No score normalization needed
  → The go-to method for combining BM25 + vector results

RAG = Retrieval Augmented Generation
  → Use ES to retrieve relevant context
  → Pass context + question to LLM
  → LLM generates answer grounded in your data
  → Prevents LLM hallucinations
```

## 🗺️ Part 1 - Dense Vector Field Setup

### Mapping with dense_vector

```bash
PUT knowledge-base
{
  "mappings": {
    "properties": {
      "title": { "type": "text" },
      "content": { "type": "text" },
      "category": { "type": "keyword" },
      "@timestamp": { "type": "date" },

      # Dense vector field
      "content_embedding": {
        "type": "dense_vector",
        "dims": 384,          # must match embedding model output dimensions
        "index": true,        # true = HNSW index built (enables KNN search)
        "similarity": "cosine",  # cosine, dot_product, l2_norm, max_inner_product

        # HNSW index parameters
        "index_options": {
          "type": "hnsw",
          "m": 16,            # connections per node (higher = slower build, better recall)
          "ef_construction": 100  # candidates during build (higher = better recall, slower)
        }
      }
    }
  },
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 1
  }
}
```

### Similarity Functions

```
cosine          → angle between vectors (normalized dot product)
                  Best for: text embeddings (most common)
                  Range: -1 to 1

dot_product     → raw dot product (vectors must be normalized!)
                  Best for: unit-normalized embeddings (slightly faster)
                  Range: unbounded

l2_norm         → Euclidean distance (inverted)
                  Best for: image embeddings, spatial data
                  Range: 0 to ∞ (inverted to score)

max_inner_product → maximum inner product (ColBERT-style)
                  Best for: late interaction models
```

### Embedding Models & Dimensions

```
MODEL                              DIMS    USE CASE
───────────────────────────────────────────────────
ELSER v2 (Elastic)                 sparse  English semantic search
E5-small-multilingual (HuggingFace) 384    Multilingual semantic
all-MiniLM-L6-v2 (HuggingFace)    384     Fast English semantic
text-embedding-3-small (OpenAI)   1536    High quality English
text-embedding-3-large (OpenAI)   3072    Best quality (expensive)
embed-english-v3 (Cohere)         1024    Good English semantic
embed-multilingual-v3 (Cohere)    1024    Multilingual
nomic-embed-text-v1               768     Open source, strong
```

## 🔍 Part 2 - KNN Search

### Basic KNN Search

```bash
# Find 10 most semantically similar documents
GET knowledge-base/_search
{
  "knn": {
    "field": "content_embedding",
    "query_vector": [0.12, -0.45, 0.78, ...],  # 384 dims
    "k": 10,
    "num_candidates": 100
  },
  "_source": ["title", "content", "category"]
}

# k:              number of results to return
# num_candidates: candidates per shard before global sort
#                 higher = better accuracy, more compute
#                 recommended: min(10*k, 10000)
```

### KNN with Query Vector Generation (Inference API)

```bash
# Let ES generate the embedding at query time
GET knowledge-base/_search
{
  "knn": {
    "field": "content_embedding",
    "query_vector_builder": {
      "text_embedding": {
        "model_id": "my-e5-model",
        "model_text": "how to fix database connection timeout"
      }
    },
    "k": 10,
    "num_candidates": 100
  }
}
```

### KNN with Filters (Pre-filter)

```bash
# Filter BEFORE KNN (reduces search space)
GET knowledge-base/_search
{
  "knn": {
    "field": "content_embedding",
    "query_vector": [...],
    "k": 10,
    "num_candidates": 100,
    "filter": [
      { "term": { "category": "elasticsearch" } },
      { "range": { "@timestamp": { "gte": "now-90d" } } }
    ]
  }
}
```

### KNN Similarity Score Filter

```bash
# Only return results above minimum similarity threshold
GET knowledge-base/_search
{
  "knn": {
    "field": "content_embedding",
    "query_vector": [...],
    "k": 10,
    "num_candidates": 100,
    "similarity": 0.8   # minimum cosine similarity score
  }
}
```

## 🔀 Part 3 - Hybrid Search

### Method 1: bool + knn (Simple)

```bash
GET knowledge-base/_search
{
  "query": {
    "bool": {
      "should": [
        {
          "match": {
            "content": {
              "query": "database connection timeout",
              "boost": 1.0
            }
          }
        }
      ]
    }
  },
  "knn": {
    "field": "content_embedding",
    "query_vector_builder": {
      "text_embedding": {
        "model_id": "my-e5-model",
        "model_text": "database connection timeout"
      }
    },
    "k": 10,
    "num_candidates": 50,
    "boost": 2.0
  },
  "size": 10
}
# Scores are combined: bool_score + knn_score (boosted)
# Problem: scores have different scales → boost tuning required
```

### Method 2: RRF Retriever (Recommended!)

```bash
GET knowledge-base/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        {
          "standard": {
            "query": {
              "match": {
                "content": "database connection timeout"
              }
            }
          }
        },
        {
          "knn": {
            "field": "content_embedding",
            "query_vector_builder": {
              "text_embedding": {
                "model_id": "my-e5-model",
                "model_text": "database connection timeout"
              }
            },
            "k": 10,
            "num_candidates": 50
          }
        }
      ],
      "rank_constant": 60,      # RRF constant (default 60)
      "rank_window_size": 100   # candidates before final ranking
    }
  },
  "size": 10
}
# RRF normalizes ranks, not scores → no boost tuning needed!
# This is the PREFERRED approach for hybrid search
```

### Method 3: Multiple KNN + RRF

```bash
# Combine multiple embedding models for better recall
GET knowledge-base/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        {
          "knn": {
            "field": "content_embedding_e5",
            "query_vector_builder": {
              "text_embedding": {
                "model_id": "e5-small",
                "model_text": "database timeout"
              }
            },
            "k": 20,
            "num_candidates": 100
          }
        },
        {
          "knn": {
            "field": "content_embedding_elser",
            "inference_id": "my-elser-endpoint",
            "query": "database timeout"
          }
        },
        {
          "standard": {
            "query": {
              "multi_match": {
                "query": "database timeout",
                "fields": ["title^2", "content"]
              }
            }
          }
        }
      ],
      "rank_constant": 60,
      "rank_window_size": 200
    }
  }
}
```

## 🏗️ Part 4 - Production Vector Search Setup

### Step 1: Set Up Inference Endpoint

```bash
# Using Cohere for embeddings
PUT _inference/text_embedding/cohere-embeddings
{
  "service": "cohere",
  "service_settings": {
    "api_key": "${COHERE_API_KEY}",
    "model_id": "embed-english-v3.0",
    "embedding_type": "float"
  },
  "task_settings": {
    "input_type": "search_document",
    "truncate": "END"
  }
}
```

### Step 2: Create Index with semantic_text (Easiest Path)

```bash
# semantic_text handles everything automatically
PUT production-knowledge-base
{
  "mappings": {
    "properties": {
      "title": { "type": "text" },
      "content": { "type": "text" },
      "category": { "type": "keyword" },
      "source_url": { "type": "keyword" },
      "@timestamp": { "type": "date" },

      # semantic_text auto-generates and stores embeddings
      "content_semantic": {
        "type": "semantic_text",
        "inference_id": "cohere-embeddings"
      }
    }
  }
}
```

### Step 3: Ingest Documents (Embedding Auto-Generated)

```bash
# Embedding generated at index time automatically
POST production-knowledge-base/_doc
{
  "title": "Elasticsearch Connection Timeout Troubleshooting",
  "content": "Connection timeouts occur when Elasticsearch cannot establish a connection within the configured timeout period. Common causes include network issues, cluster overload, and misconfigured settings.",
  "content_semantic": "Connection timeouts occur when Elasticsearch cannot establish a connection within the configured timeout period. Common causes include network issues, cluster overload, and misconfigured settings.",
  "category": "troubleshooting",
  "source_url": "https://docs.elastic.co/...",
  "@timestamp": "2026-05-12T10:00:00Z"
}

# Bulk ingest for large datasets
POST production-knowledge-base/_bulk
{ "index": {} }
{ "title": "...", "content": "...", "content_semantic": "..." }
{ "index": {} }
{ "title": "...", "content": "...", "content_semantic": "..." }
```

### Step 4: Semantic Search at Query Time

```bash

{
  "retriever": {
    "rrf": {
      "retrievers": [
        {
          "standard": {
            "query": {
              "semantic": {
                "field": "content_semantic",
                "query": "elasticsearch not connecting to database"
              }
            }
          }
        },
        {
          "standard": {
            "query": {
              "match": {
                "content": "elasticsearch not connecting to database"
              }
            }
          }
        }
      ]
    }
  },
```

## 🤖 Part 5 - RAG (Retrieval Augmented Generation)

### RAG Architecture

```
User Question
     │
     ▼
Generate Embedding (query)
     │
     ▼
KNN/Semantic Search in Elasticsearch
     │
     ▼
Top-K Relevant Documents (context)
     │
     ▼
Prompt = Question + Context
     │
     ▼
LLM (GPT-4, Claude, Llama)
     │
     ▼
Grounded Answer (based on your data)
```

### RAG with Elasticsearch + LLM

```python
from elasticsearch import Elasticsearch
from anthropic import Anthropic

es = Elasticsearch("https://my-es:9200", api_key="...")
llm = Anthropic(api_key="...")

def rag_search(question: str, top_k: int = 5) -> str:
    # Step 1: Retrieve relevant context from ES
    results = es.search(
        index="production-knowledge-base",
        body={
            "retriever": {
                "rrf": {
                    "retrievers": [
                        {
                            "standard": {
                                "query": {
                                    "semantic": {
                                        "field": "content_semantic",
                                        "query": question
                                    }
                                }
                            }
                        },
                        {
                            "standard": {
                                "query": {
                                    "match": {"content": question}
                                }
                            }
                        }
                    ]
                }
            },
            "_source": ["title", "content", "source_url"],
            "size": top_k
        }
    )

    # Step 2: Build context from search results
    context_parts = []
    for hit in results["hits"]["hits"]:
        src = hit["_source"]
        context_parts.append(
            f"Title: {src['title']}\n"
            f"Content: {src['content']}\n"
            f"Source: {src.get('source_url', 'N/A')}"
        )
    context = "\n\n---\n\n".join(context_parts)

    # Step 3: Generate answer using LLM
    prompt = f"""You are an Elasticsearch expert assistant.
Answer the question based ONLY on the provided context.
If the answer is not in the context, say "I don't have information about this."

Context:
{context}

Question: {question}

Answer:"""

    response = llm.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=1024,
        messages=[{"role": "user", "content": prompt}]
    )

    return response.content[0].text

# Use it
answer = rag_search("How do I fix Elasticsearch connection timeout errors?")
print(answer)
```

### ES|QL for RAG Context Retrieval

```sql
-- Retrieve relevant context for RAG
FROM production-knowledge-base
| WHERE content_semantic LIKE "connection timeout troubleshooting"  -- semantic search
| KEEP title, content, source_url
| LIMIT 5
```

## 📊 Part 6 - HNSW Tuning

### HNSW Parameters

```bash
# HNSW (Hierarchical Navigable Small World) = index structure for ANN search

# m: max connections per node
#   Default: 16
#   Range: 4-100
#   Higher m → better recall, more memory, slower indexing
#   For production: 16-32 is usually optimal

# ef_construction: candidate list size during index build
#   Default: 100
#   Range: 4-3000
#   Higher ef_construction → better recall, slower indexing
#   For production: 100-200

# num_candidates (at query time):
#   How many candidates per shard before global ranking
#   Higher → better recall, more compute
#   Recommended: min(10 * k, 10000)

PUT knowledge-base/_mapping
{
  "properties": {
    "content_embedding": {
      "type": "dense_vector",
      "dims": 768,
      "index": true,
      "similarity": "cosine",
      "index_options": {
        "type": "hnsw",
        "m": 32,               # for higher recall requirement
        "ef_construction": 200  # for higher recall requirement
      }
    }
  }
}
```

### Recall vs Speed Tradeoff

```
HIGHER RECALL:
  → Increase num_candidates (at query time)
  → Increase m and ef_construction (at index time)
  → Use exact KNN (small indices only)
  → Trade-off: slower queries + more memory

HIGHER SPEED:
  → Decrease num_candidates
  → Smaller m and ef_construction
  → Pre-filter with bool filters to reduce search space
  → Use quantization (int8 quantization for dense vectors)
  → Trade-off: lower recall (miss some relevant results)

Typical production target: >95% recall at <100ms
```

### Int8 Quantization (Memory Savings)

```bash
# Quantize float32 vectors to int8 → 4x memory reduction
PUT knowledge-base
{
  "mappings": {
    "properties": {
      "content_embedding": {
        "type": "dense_vector",
        "dims": 384,
        "index": true,
        "similarity": "cosine",
        "index_options": {
          "type": "int8_hnsw",   # ← int8 quantization
          "m": 16,
          "ef_construction": 100,
          "confidence_interval": 0.9   # fraction of vectors used for calibration
        }
      }
    }
  }
}
# Memory reduction: 4x (float32 → int8)
# Recall impact: minimal (~1-2% recall loss)
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Wrong `dims` in mapping | Index fails to build | Must exactly match embedding model output |
| No `index: true` | KNN search fails | Set `index: true` for KNN-enabled fields |
| Embedding at query time without inference endpoint | Manual embedding required | Set up inference endpoint, use query_vector_builder |
| Using score boost to combine BM25+KNN | Boost tuning nightmare | Use RRF retriever instead |
| `num_candidates` too low | Poor recall | Use min(10*k, 10000) |
| Embedding everything including keywords | Wasted computation | Only embed semantic content (body, description) |
| Not normalizing vectors for dot_product | Wrong similarity scores | Use cosine similarity OR normalize vectors |
| RAG without source filtering | LLM gets irrelevant context | Filter by category/date before vector search |
| Large chunk size for embeddings | Diluted meaning | Chunk at ~512 tokens max |
| Not chunking large documents | Embedding model context limit | Split documents into semantic chunks |

## 💡 Key Principles

```
1. semantic_text field = simplest path to semantic search
   → Auto-handles embedding at index and query time

2. RRF > manual score boosting for hybrid search
   → No score normalization headaches

3. Cosine similarity for text embeddings (default choice)
   → Works correctly for unnormalized vectors

4. num_candidates = 10 * k minimum
   → Lower = worse recall, higher = more compute

5. int8_hnsw for memory efficiency
   → 4x memory savings, ~1-2% recall loss

6. Chunk documents before embedding
   → Models have context limits (~512 tokens)
   → Smaller chunks = more precise retrieval

7. Filter before KNN when possible
   → Reduces search space → faster + more relevant

8. RAG context quality > LLM quality
   → Best LLM with bad context = bad answer
   → Good retrieval = good answers regardless of LLM

9. Always combine BM25 + vector for production
   → Pure vector misses exact matches
   → Pure BM25 misses semantic matches
   → Hybrid = best recall

10. m=16, ef_construction=100 is safe default
    → Tune only when recall measurements show it's needed
```
