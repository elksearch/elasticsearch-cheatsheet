## Node Roles & Cluster Architecture
### Dedicated Masters, Data Tiers, Coordinator, ML, ECE/ECK Deployment Patterns

> The single most impactful architectural decision in Elasticsearch is assigning
> the right roles to the right nodes. A misconfigured role assignment causes
> instability, poor performance, and outages that are hard to diagnose.

## 🧠 All Node Roles — Complete Reference

```yaml
# Every node role in Elasticsearch 9.x
node.roles:
  - master          # cluster management, metadata
  - data            # stores data (all tiers — dev only)
  - data_content    # long-lived content (not time-series)
  - data_hot        # active indexing, recent data
  - data_warm       # less frequent access, no indexing
  - data_cold       # infrequent access, searchable snapshots
  - data_frozen     # archive — on-demand S3 access
  - ingest          # runs ingest pipelines
  - ml              # machine learning jobs
  - remote_cluster_client  # participates in CCS
  - transform       # runs transform jobs
  - voting_only     # participates in master election (no master duties)
  - coordinating    # (implicit) — all nodes are coordinators
```

## 🏗️ Part 1 — Master Node

### What Master Nodes Do

```
Master node manages CLUSTER STATE:
  → Index creation / deletion
  → Shard allocation decisions
  → Node join / leave
  → ILM policy execution
  → Snapshot coordination
  → Template management

Cluster state is replicated to ALL nodes
Master applies changes → broadcasts to all

Master does NOT:
  → Store data (on dedicated master)
  → Handle search queries
  → Run ingest pipelines
```

### Master Election (Raft-based in ES 7+)

```
ES 7+ uses Raft consensus — no split brain possible
Requires majority (quorum) to elect master:

  3 master-eligible nodes → quorum = 2
  5 master-eligible nodes → quorum = 3
  7 master-eligible nodes → quorum = 4

Minimum recommended: 3 dedicated master nodes
  → Can lose 1 node and still have quorum (2 of 3)
  → NEVER use even numbers (4, 6) — no advantage, harder quorum

For very large clusters (50+ nodes): still just 3 dedicated masters
  → Master load scales with NUMBER of shards, not number of data nodes
  → 1 GB heap per ~3000 indices rule of thumb
```

### Dedicated Master Configuration

```yaml
# elasticsearch.yml — dedicated master node
node.roles: [master]

# Hardware for master nodes:
# CPU:  4-8 cores (not CPU-intensive)
# RAM:  8-16 GB (heap = 4-8 GB)
# Disk: SSD preferred, small (only stores cluster state)
# Network: low latency between masters critical
```

### Voting-Only Master Node

```yaml
# Participates in voting but never becomes elected master
# Use case: 4th tiebreaker node without full master overhead
node.roles: [master, voting_only]

# Example: 2 full masters + 1 voting-only = quorum of 2
# Cheaper than 3 full masters for cost-sensitive setups
```

### Check Master Health

```bash
# Who is current master?
GET _cat/master?v

# Master node stats
GET _nodes/master/stats

# Cluster state version (how often it changes)
GET _cluster/state/_version

# Pending tasks (master processes these)
GET _cluster/pending_tasks

# Master node heap usage
GET _nodes/master/stats/jvm?filter_path=nodes.*.jvm.mem.heap_used_percent

# Voting configuration
GET _cluster/voting_config_exclusions
```

## 🔥 Part 2 — Data Nodes & Tiers

### Data Tier Architecture

```
HOT TIER (data_hot)
  → Active writes + frequent reads
  → Best hardware: NVMe SSD, high RAM, high CPU
  → ILM: rollover at 50GB or 1d
  → Replica: 1 (for HA)

WARM TIER (data_warm)
  → No writes, occasional reads
  → Good hardware: SSD or fast HDD, medium RAM
  → ILM: forcemerge to 1 segment, shrink to 1 shard
  → Replica: 1 (can reduce to 0 if snapshots exist)

COLD TIER (data_cold)
  → Rare reads, searchable snapshots (full copy)
  → Cheaper hardware: HDD, less RAM
  → ILM: mount as searchable snapshot
  → Replica: 0 (snapshot = backup)

FROZEN TIER (data_frozen)
  → Archive access, shared cache searchable snapshots
  → Cheapest: any hardware with shared cache configured
  → ILM: mount as frozen searchable snapshot
  → Replica: 0
  → Queries fetch from S3 on demand (slow but cheap)

CONTENT TIER (data_content)
  → Non-time-series data: products, users, config
  → Treated like hot (fast access) but not time-based
  → Example: Kibana indices, Fleet config
```

### Tier Configuration

```yaml
# Hot node — elasticsearch.yml
node.roles: [data_hot, data_content, ingest]

# Warm node
node.roles: [data_warm]

# Cold node
node.roles: [data_cold]

# Frozen node
node.roles: [data_frozen]

# Frozen node — MUST configure shared cache
# elasticsearch.yml
xpack.searchable.snapshot.shared_cache.size: 100gb
# or:
xpack.searchable.snapshot.shared_cache.size: 90%
```

### Hardware Sizing Per Tier

```
HOT TIER:
  CPU:    16-64 cores
  RAM:    64-256 GB (heap = 30 GB max, rest = OS cache)
  Disk:   NVMe SSD, 1-4 TB per node
  Ratio:  1:30 memory:data

WARM TIER:
  CPU:    8-16 cores
  RAM:    32-128 GB
  Disk:   SSD or HDD, 4-16 TB per node
  Ratio:  1:100 to 1:160 memory:data

COLD TIER:
  CPU:    4-8 cores
  RAM:    16-32 GB
  Disk:   HDD or object storage cache
  Ratio:  1:500+ memory:data

FROZEN TIER:
  CPU:    4-8 cores
  RAM:    8-16 GB (just for shared cache)
  Disk:   100-500 GB local (shared cache only — data in S3)
  Ratio:  1:1000+ effectively
```

### Force Shard Allocation to Specific Tier

```bash
# Manually assign index to specific tier
PUT my-index/_settings
{
  "index.routing.allocation.require._tier_preference": "data_warm"
}

# ILM does this automatically via migrate action
# Check where an index lives:
GET my-index/_settings?filter_path=**.routing.allocation
```

## 📡 Part 3 — Coordinating Node

### What Coordinating Does

```
ALL nodes are coordinating nodes by default.
A DEDICATED coordinating node has NO other roles.

Coordinating responsibilities:
  → Receive client requests
  → Route to correct shards
  → Scatter search to all shards
  → Gather + merge results
  → Return response to client

Why dedicated coordinators?
  → Offloads scatter-gather work from data nodes
  → Especially important for:
    - Heavy aggregation workloads
    - Kibana instances (each Kibana = its own coordinator)
    - High search concurrency
```

### Dedicated Coordinator Configuration

```yaml
# elasticsearch.yml — coordinating only
node.roles: []   # empty = coordinating only

# Hardware for coordinator:
# CPU:  16-32 cores (merges results from all shards)
# RAM:  32-64 GB (result merging can be memory intensive)
# Disk: Small SSD (no data stored)
# Network: High bandwidth — receives from all data nodes
```

### When to Add Dedicated Coordinators

```
Add dedicated coordinators when:
  ✅ Kibana shows slow response times but data nodes are fine
  ✅ High search fan-out (many shards × many concurrent queries)
  ✅ Large aggregation result sets (many buckets)
  ✅ Kibana deployed as dedicated coordinator is common pattern

Pattern: 1 coordinator per Kibana instance
  Kibana → Coordinator → Data nodes
  (Kibana never talks to data nodes directly)
```

## ⚙️ Part 4 — Ingest Node

### What Ingest Nodes Do

```
Ingest nodes execute ingest pipelines before indexing.

Heavy processors (CPU-intensive):
  → GROK pattern matching
  → GeoIP lookups
  → ML inference
  → User agent parsing
  → Script processor (Painless)

Why dedicated ingest nodes?
  → Don't compete with data nodes for CPU
  → Scale ingest independently from storage
  → Logstash → Ingest node → Data nodes is common pattern
```

### Ingest Node Configuration

```yaml
# elasticsearch.yml — dedicated ingest node
node.roles: [ingest]

# Hardware for ingest:
# CPU:  16-32 cores (pipeline processing is CPU-bound)
# RAM:  32-64 GB
# Disk: Small SSD (no data stored)
```

### Check Ingest Performance

```bash
# Ingest pipeline stats
GET _nodes/stats/ingest

# Per-pipeline stats
GET _nodes/stats/ingest?filter_path=nodes.*.ingest.pipelines

# Response shows:
# count: total docs processed
# failed: pipeline failures
# time_in_millis: total processing time
# current: in-flight right now
```

## 🤖 Part 5 — ML Node

### What ML Nodes Do

```
ML nodes run:
  → Anomaly detection jobs
  → Data frame analytics
  → NLP/inference models (ELSER, E5, custom)
  → Transform jobs (optionally)

Why dedicated ML nodes?
  → ML jobs are extremely CPU + memory intensive
  → Model loading consumes significant heap
  → MUST isolate from data/master nodes
```

### ML Node Configuration

```yaml
# elasticsearch.yml — dedicated ML node
node.roles: [ml, remote_cluster_client]

# Hardware for ML:
# CPU:    32-64 cores (inference = CPU bound without GPU)
# RAM:    64-256 GB (model loading is memory intensive)
# GPU:    Optional but massively speeds up inference (NVIDIA)
# Disk:   NVMe SSD for model storage
```

### ML Node Settings

```bash
# Set ML memory limit (default: 30% of JVM heap)
PUT _cluster/settings
{
  "persistent": {
    "xpack.ml.max_machine_memory_percent": 30,
    "xpack.ml.max_model_memory_limit": "20gb"
  }
}

# Check ML node info
GET _ml/info

# Check anomaly detection jobs
GET _ml/anomaly_detectors?allow_no_match=true

# Check inference models loaded
GET _ml/trained_models
GET _ml/trained_models/_stats
```

## 🏭 Part 7 — Production Cluster Architectures

### Architecture 1: Small Production (8 nodes)

```
┌─────────────────────────────────────────────────────────┐
│                  Small Production Cluster                 │
│                                                           │
│  Masters (3):           Data Hot (3):    Data Warm (2):  │
│  ┌─────────┐           ┌─────────┐      ┌─────────┐     │
│  │ master  │           │data_hot │      │data_warm│     │
│  │ 8 cores │           │ ingest  │      │ 32 cores│     │
│  │ 16 GB   │  × 3     │ 32 cores│ × 3  │ 64 GB   │ × 2 │
│  │ 500 GB  │           │ 64 GB   │      │ 8 TB HDD│     │
│  │  SSD    │           │ 2 TB SSD│      └─────────┘     │
│  └─────────┘           └─────────┘                       │
└─────────────────────────────────────────────────────────┘

Total: 3 masters + 3 hot + 2 warm = 8 nodes
Good for: 1-5 TB/day ingest, 90d retention
```

### Architecture 2: Large Production (20+ nodes)

```
┌──────────────────────────────────────────────────────────────┐
│                   Large Production Cluster                    │
│                                                               │
│ Masters(3)  Coord(2)  Hot(6)    Warm(4)   Cold(3)  Frozen(2) │
│ ┌───────┐  ┌───────┐ ┌───────┐ ┌───────┐ ┌──────┐ ┌──────┐ │
│ │master │  │coord  │ │data_  │ │data_  │ │data_ │ │data_ │ │
│ │       │  │       │ │hot    │ │warm   │ │cold  │ │frozen│ │
│ │16GB   │  │64GB   │ │ingest │ │       │ │      │ │+     │ │
│ │       │  │       │ │128GB  │ │128GB  │ │64GB  │ │cache │ │
│ │       │  │       │ │NVMe   │ │SSD    │ │HDD   │ │      │ │
│ └───────┘  └───────┘ └───────┘ └───────┘ └──────┘ └──────┘ │
│   × 3        × 2       × 6       × 4       × 3       × 2    │
└──────────────────────────────────────────────────────────────┘

Also: 2 ML nodes, 1 Transform node, 3 Kibana (on coordinators)
Good for: 50-500 TB/day, 1 year retention
```

## 🌐 Part 8 — Shard Allocation Awareness (Rack/Zone Awareness)

### Why Rack Awareness?

```
Without awareness:
  Primary shard → Node A (Zone 1)
  Replica shard → Node B (Zone 1)  ← SAME ZONE!
  Zone 1 fails → BOTH primary + replica gone → RED cluster!

With rack/zone awareness:
  Primary shard → Node A (Zone 1)
  Replica shard → Node C (Zone 2)  ← DIFFERENT ZONE
  Zone 1 fails → Replica in Zone 2 → cluster stays GREEN!
```

### Configure Zone Awareness

```yaml
# elasticsearch.yml — on each node, set its zone
node.attr.zone: zone-1     # or zone-2, zone-3

# On master nodes — set cluster-level awareness
cluster.routing.allocation.awareness.attributes: zone

# Force primaries and replicas to different zones:
cluster.routing.allocation.awareness.force.zone.values: zone-1,zone-2,zone-3
```

```bash
# Or via API:
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.awareness.attributes": "zone",
    "cluster.routing.allocation.awareness.force.zone.values": "zone-1,zone-2,zone-3"
  }
}

# Check node attributes
GET _cat/nodeattrs?v

# Check shard distribution across zones
GET _cat/shards?v&h=index,shard,prirep,node&s=index
```

## ❌ Part 9 — Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Mixing master + data roles in production | Master instability under load | Dedicate 3 nodes as master-only |
| Using 2 or 4 master-eligible nodes | Split brain or quorum issues | Always odd number: 3, 5, 7 |
| No dedicated ingest nodes for heavy pipelines | Pipeline CPU kills search/indexing | Separate ingest nodes |
| ML models on data nodes | OOM kills data node | Always dedicated ML nodes |
| Coordinating role on master nodes | Master too busy for cluster management | Masters should only be masters |
| No zone awareness in multi-AZ | Single AZ failure → RED cluster | Always configure zone awareness |
| Frozen nodes without shared cache config | Frozen indices don't work | Set `xpack.searchable.snapshot.shared_cache.size` |
| `data` role (all-in-one) in production | All workloads compete on same nodes | Use specific tier roles |
| Too many master-eligible nodes | Slower elections | Max 3 dedicated masters (5 for huge clusters) |
| No `voting_only` for cost optimization | 3rd full master wasteful for small clusters | Use voting_only for tiebreaker |

## 💡 Key Principles

```
1. 3 dedicated master nodes — always, in every production cluster
   → Never mix master + data roles in production

2. Odd number of masters — always
   → 3 > 2 or 4 for quorum reasons

3. Use specific tier roles — not generic "data"
   → data_hot, data_warm, data_cold, data_frozen, data_content

4. Zone awareness — mandatory in multi-AZ deployments
   → Without it, single AZ failure = RED cluster

5. ML nodes must be isolated
   → Model loading can OOM kill a data node

6. Coordinator nodes for heavy Kibana
   → 1 coordinator per Kibana instance is best practice

7. Ingest nodes for CPU-heavy pipelines
   → GeoIP, ML inference, script processors need dedicated nodes

8. Frozen tier = 90% cost saving vs hot
   → Use it aggressively for data older than 90 days

9. Heap = 50% of RAM, max 30 GB per node
   → Applies to ALL node types

10. ECK on Kubernetes = modern deployment standard
    → Operator handles upgrades, scaling, cert rotation automatically
```
