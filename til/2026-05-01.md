## 🧠 Core Concepts

```
THREE TYPES:
  BUCKET    → Group documents into buckets (like GROUP BY in SQL)
  METRIC    → Calculate statistics within a bucket (like SUM, AVG, COUNT)
  PIPELINE  → Calculate on the OUTPUT of other aggregations (derivative, moving avg)

NESTING:
  Aggregations can be nested infinitely:
  Bucket → Sub-bucket → Sub-sub-bucket → Metric

  e.g.:
    Per-service (bucket)
      → Per-hour (sub-bucket)
        → Error rate (metric)
          → Derivative of error rate (pipeline)

RESPONSE STRUCTURE:
  "aggregations": {
    "my_agg_name": {        ← you name it
      "buckets": [...],     ← bucket agg result
      "value": 42.5         ← metric agg result
    }
  }

KEY RULE:
  Always use size: 0 when you only want aggregations (no documents)
  → Saves massive bandwidth and processing
```

### Scripted Metric (custom metric with Painless)

```bash

  "aggs": {
    "error_rate_percent": {
      "scripted_metric": {
        "init_script": "state.errors = 0; state.total = 0;",
        "map_script": """
          state.total++;
          if (doc['http.response.status_code'].value >= 500) {
            state.errors++;
          }
        """,
        "combine_script": "return state;",
        "reduce_script": """
          long totalErrors = 0;
          long totalRequests = 0;
          for (s in states) {
```

## 🪣 Part 2 — Bucket Aggregations

### Terms (GROUP BY a field)

```bash
GET logs-nginx-production/_search
{
  "size": 0,
  "aggs": {
    "by_service": {
      "terms": {
        "field": "service.name",
        "size": 10,
        "order": { "_count": "desc" },
        "min_doc_count": 1,
        "shard_size": 25,
        "show_term_doc_count_error": true,
        "missing": "unknown-service"
      },
      "aggs": {
        "error_count": {
          "filter": { "term": { "log.level": "ERROR" } }
        },
        "avg_duration": {
          "avg": { "field": "event.duration" }
        }
      }
    }
  }
}

# IMPORTANT: shard_size should be >> size for accuracy
# shard_size = size * 1.5 + 10 (default) — increase for better accuracy
# show_term_doc_count_error → shows per-term error bound
```

### Why Terms Accuracy Can Be Wrong

```
Problem: Each shard returns top 10 terms independently.
         A term ranked 15th on shard A + 11th on shard B
         could be #2 globally — but coordinator never sees it!

Fix:
  "shard_size": 100   → each shard returns 100 terms (not 10)
  → More data at coordinator → better accuracy
  → Cost: more memory, more network

Rule: shard_size = size * 3 minimum for accurate results
```

## 🔗 Part 3 — Pipeline Aggregations

### What Are Pipeline Aggregations?

```
Pipeline aggs take the OUTPUT of other aggs as input.
They calculate derivatives, moving averages, cumulative sums.
They don't process raw documents — only aggregation results.

Two types:
  PARENT: output added to parent bucket
  SIBLING: output is a new sibling aggregation
```

### Derivative (rate of change)

```bash
GET logs-nginx-production/_search
{
  "size": 0,
  "aggs": {
    "requests_per_hour": {
      "date_histogram": {
        "field": "@timestamp",
        "calendar_interval": "1h"
      },
      "aggs": {
        "error_count": {
          "filter": { "term": { "log.level": "ERROR" } }
        },
        "error_rate_change": {
          "derivative": {
            "buckets_path": "error_count"
          }
        }
      }
    }
  }
}
# derivative: rate of change between buckets
# positive = increasing, negative = decreasing
```

### Apdex Score Calculation

```bash
# Apdex = (Satisfied + Tolerating/2) / Total
# Satisfied: < 500ms, Tolerating: 500ms-2000ms, Frustrated: > 2000ms

GET logs-nginx-production/_search
{
  "size": 0,
  "aggs": {
    "by_service": {
      "terms": { "field": "service.name", "size": 20 },
      "aggs": {
        "total":      { "value_count": { "field": "event.duration" } },
        "satisfied":  { "filter": { "range": { "event.duration": { "lt": 500 } } } },
        "tolerating": { "filter": { "range": { "event.duration": { "gte": 500, "lt": 2000 } } } },
        "apdex": {
          "bucket_script": {
            "buckets_path": {
              "total": "total",
              "satisfied": "satisfied",
              "tolerating": "tolerating"
            },
            "script": """
              if (params.total == 0) return 1.0;
              return (params.satisfied + params.tolerating / 2.0) / params.total;
            """
          }
        }
      }
    }
  }
}
```

## ❌ Part 5 — Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| `size > 0` with aggregations | Returns documents + agg results (wasteful) | Always `"size": 0` for pure analytics |
| Small `shard_size` for terms agg | Inaccurate top-N results | Set `shard_size` to `size * 3` minimum |
| Terms agg on high-cardinality `text` field | Exception — fielddata required | Use `.keyword` subfield instead |
| Missing `min_doc_count: 0` in date_histogram | Empty time buckets missing | Set `min_doc_count: 0` + `extended_bounds` |
| Deep nesting without `size: 0` on sub-aggs | Exponential result size | Control sizes at each level |
| Cardinality without `precision_threshold` | Low accuracy for large sets | Set `precision_threshold: 40000` |
| Using scripted metric for simple math | Slow — scripts don't use doc values | Use bucket_script pipeline agg instead |
| No `extended_bounds` in time series | Chart shows only buckets with data | Add `extended_bounds` for full range |
| Aggregating on `text` fields | Fielddata heap pressure | Map as `keyword` or use `.keyword` |
| Using `terms` for very high cardinality | Memory + accuracy issues | Use `composite` agg with pagination |

## 💡 Key Principles — Summary

```
1. Always size: 0 for pure aggregation queries
   → No documents needed → massive bandwidth saving

2. shard_size must be >> size for terms accuracy
   → shard_size = size * 3 minimum

3. Use .keyword not .text for terms/cardinality aggregations
   → text fields require expensive fielddata

4. min_doc_count: 0 + extended_bounds for time series
   → Without these, empty time periods disappear from charts

5. Composite aggregation for high-cardinality multi-level grouping
   → Terms has memory limits; composite paginates safely

6. bucket_script for computed metrics within buckets
   → Don't use scripted_metric unless absolutely necessary

7. Significant terms for anomaly detection
   → Finds what's UNUSUALLY common in filtered set vs background

8. Pipeline aggs operate on other aggs' output
   → Use for trends (derivative), smoothing (moving_fn), filtering (bucket_selector)

9. Filter before aggregating always
   → Push date range to query context, not agg filter

10. Nested aggregations are powerful but expensive
    → Each nesting level multiplies computation
    → Keep nesting shallow (max 3-4 levels)
```
