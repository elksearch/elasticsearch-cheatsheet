## Performance Tuning - Search
### Shard Sizing, OS Cache, Forcemerge, Query Cache, Async Search, Search Optimization

> Search performance is measured in milliseconds. Every query touches every relevant shard.
> Optimizing search means optimizing at three layers: hardware, index design, and query design.
> This document covers all three comprehensively.

## 🧠 Search Execution - Internal Flow

```
Client Query
    │
    ▼
Coordinating Node
    │ (Query Phase — scatter)
    ├──────────────────────────────────┐
    │                                  │
    ▼                                  ▼
Shard 0 (Primary or Replica)    Shard 1 (Primary or Replica)
    │ Search local segment             │ Search local segment
    │ Return: top-N doc IDs + scores   │ Return: top-N doc IDs + scores
    │                                  │
    └──────────────┬───────────────────┘
                   │ (Collect, sort, merge)
                   ▼
           Coordinating Node
                   │ (Fetch Phase — gather)
                   │ Fetch _source for top docs from their shards
                   ▼
           Return to Client

KEY: Query Phase = all shards in parallel
     Fetch Phase = only top-N shards
     → size: 0 skips Fetch Phase entirely!
```

## 🖥️ Part 1 - Hardware for Search

### OS File System Cache (Most Important)

```
Elasticsearch relies heavily on the OS file system cache.
When data is in OS cache → no disk I/O → sub-millisecond reads.
When data is not in cache → disk read → 10-100x slower.

Rule: RAM - heap = OS file system cache

Example:
  Node: 128 GB RAM
  Heap: 30 GB
  OS Cache: 128 - 30 = 98 GB available for OS cache

  Index size: 80 GB → fits in cache → all queries fast!
  Index size: 200 GB → doesn't fit → cache misses → slow queries!

Memory:data ratio:
  Hot: 1:30 → 30 GB RAM per 1 TB data
       (enough OS cache for frequently accessed data)
```

### Pre-load Data into OS Cache

```bash
# Warm up OS cache after restart (run representative queries)
# Or use index preloading:

PUT my-index/_settings
{
  "index.store.preload": ["nvd", "dvd"]
}
# "nvd" = norm values (for scoring)
# "dvd" = doc values (for sorting/aggregating)
# "*"   = all files (preload everything — use carefully)

# WARNING: preloading large indices takes time on restart
# Only use for truly hot, frequently accessed indices
```

### Filesystem & I/O

```bash
# Check I/O wait (high = disk is bottleneck)
iostat -x 2

# Check if data is in OS cache
# Use vmstat to check cache hit ratio
vmstat 2

# Recommended filesystem: ext4 or xfs with noatime
# Mount options: noatime,nodiratime,data=writeback

# NVMe SSD recommended for hot tier
# Measured: NVMe = 3-5 GB/s sequential, NFS = 100-500 MB/s
# Avoid NAS for search-heavy workloads
```

## 🧮 Part 2 — Caching Layers

### Query Cache (Node-Level)

```bash
# Caches the RESULT of filter queries (not full queries)
# Applies to: term, range, geo, exists — anything in filter context
# Key: query clause hash → doc bitmap (which docs match)
# Invalidated: on segment refresh (new documents)

# Check query cache stats
GET _nodes/stats/indices/query_cache

# Configure size
PUT _cluster/settings
{
  "persistent": {
    "indices.queries.cache.size": "10%"
  }
}
# Default: 10% of heap
# Range: 1-25% (don't go higher — competes with other caches)

# Disable per-query (for debugging)
GET my-index/_search
{
  "query": {
    "bool": {
      "filter": [
        {
          "term": {
            "status": {
              "value": "active",
              "_cache": false
            }
          }
        }
      ]
    }
  }
}

# Clear query cache
POST my-index/_cache/clear?query=true
POST _cache/clear?query=true  # all indices
```

### Shard Request Cache (Per-Shard)

```bash
# Caches full aggregation results for size: 0 queries
# Very powerful for Kibana dashboards!
# Invalidated: when shard is refreshed (new data)

# Requirements for cache to be used:
# 1. size: 0 (no document hits)
# 2. Query uses "now" with rounding (now/d, now/h — not exact now)

# Example that WILL be cached:
GET logs-*/_search
{
  "size": 0,
  "query": {
    "range": {
      "@timestamp": {
        "gte": "now-1d/d",    ← /d rounds to day → cacheable
        "lte": "now/d"        ← /d rounds to day → cacheable
      }
    }
  },
  "aggs": {
    "count": { "value_count": { "field": "@timestamp" } }
  }
}

# Example that will NOT be cached:
# "gte": "now-1h"   ← exact, changes every millisecond

# Check request cache stats
GET _nodes/stats/indices/request_cache

# Cache size
PUT _cluster/settings
{
  "persistent": {
    "indices.requests.cache.size": "2%"
  }
}

# Clear request cache
POST logs-*/_cache/clear?request=true
```

### Fielddata Cache (Avoid!)

```bash
# Fielddata = inverted index loaded into heap for text field aggs
# VERY expensive — avoid by using keyword fields instead

# Check fielddata usage
GET _nodes/stats/indices/fielddata

# Set limit
PUT _cluster/settings
{
  "persistent": {
    "indices.fielddata.cache.size": "20%"
  }
}

# Clear fielddata cache
POST _cache/clear?fielddata=true

# REAL FIX: Use .keyword subfield instead of fielddata
# BAD:  { "terms": { "field": "message" } }  ← requires fielddata
# GOOD: { "terms": { "field": "message.keyword" } }  ← uses doc_values
```

## 🗜️ Part 3 — Segment Management & Forcemerge

### Why Segments Matter for Search

```
Each index = multiple segments
Query = search ALL segments + merge results
More segments = more work per query

NEW INDEX: many small segments (created during ingestion)
AFTER FORCEMERGE: 1 large segment → fastest possible search

1 segment = minimum overhead (Lucene can use SIMD on single segment)
```

### When to Forcemerge

```bash
# ONLY forcemerge READ-ONLY indices (old rolled-over backing indices)
# NEVER forcemerge actively-written indices (endless merges)

# Identify read-only indices (after ILM rollover)
GET _cat/indices?v&h=index,status,docs.count&s=index
# Indices moved to warm/cold phase are read-only

# Forcemerge to 1 segment (maximum search speed)
POST .ds-logs-nginx-production-2026.04.01-000001/_forcemerge?max_num_segments=1

# Check segment count before/after
GET _cat/segments/.ds-logs-nginx-production-2026.04.01-000001?v&h=segment,size,docs.count

# Forcemerge ALL warm indices (production pattern)
POST logs-*/_forcemerge?max_num_segments=1&only_expunge_deletes=false
# WARNING: Very CPU and I/O intensive — run during off-peak hours

# Monitor forcemerge progress
GET _tasks?actions=*forcemerge&detailed=true

# Only expunge deleted docs (lighter than full forcemerge)
POST my-index/_forcemerge?only_expunge_deletes=true
```

### ILM Integration (Auto-Forcemerge in Warm Phase)

```bash
PUT _ilm/policy/logs-policy
{
  "policy": {
    "phases": {
      "warm": {
        "min_age": "3d",
        "actions": {
          "forcemerge": {
            "max_num_segments": 1
          },
          "shrink": {
            "number_of_shards": 1
          }
        }
      }
    }
  }
}
# ILM runs forcemerge automatically in warm phase
# This is the PREFERRED way — not manual forcemerge in production
```

## 🎯 Part 4 - Query Optimization Patterns

### Use Filter Context Aggressively

```bash
# Every clause in filter context:
# ✅ Cached (query cache)
# ✅ No score calculation
# ✅ Faster execution

# Pattern: query (full-text) + filter (structured)
GET logs-nginx-production/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "message": "connection timeout" } }
      ],
      "filter": [
        { "term":  { "log.level": "ERROR" } },
        { "term":  { "service.name": "api-service" } },
        { "range": { "@timestamp": { "gte": "now-1h/m", "lte": "now/m" } } }
      ]
    }
  }
}
# The /m rounding makes the range cacheable!
```

### Reduce Fan-Out (Fewer Shards Searched)

```bash
# 1. Use routing to search specific shards
GET logs-nginx-production/_search?routing=service-a
{
  "query": { "term": { "service.name": "service-a" } }
}
# Searches ONLY the shard(s) for service-a — not all shards

# 2. Use index routing (search specific indices)
GET logs-nginx-production,logs-api-production/_search
# Not: GET logs-*/_search  ← searches all matching indices

# 3. Use index pattern with date math
GET logs-nginx-production-2026.05.*/_search   ← only May indices
# Not: GET logs-nginx-production-*/_search    ← all time

# 4. Limit number of shards per request
GET _cluster/settings
PUT _cluster/settings
{
  "persistent": {
    "action.search.shard_count.limit": 1000
  }
}
```

### Search Preference (Adaptive Replica Selection)

```bash
# By default: Adaptive Replica Selection (ARS)
# ARS routes each query to the replica with best estimated response time
# No configuration needed — automatic since ES 6.x

# For session affinity (same shard for same user):
GET my-index/_search?preference=_shards:0,1
GET my-index/_search?preference=user-session-abc123

# For benchmarking (always use primary):
GET my-index/_search?preference=_primary

# For warm-up (hit all shards):
GET my-index/_search?preference=_shards:0
GET my-index/_search?preference=_shards:1
# ... repeat for each shard
```

### Avoid Expensive Operations

```bash
# ❌ SLOW: Wildcard query with leading wildcard (full scan)
{ "wildcard": { "url.path": "*payment*" } }

# ✅ FAST: Match on analyzed field
{ "match": { "url.path": "payment" } }

# ❌ SLOW: Script in query (per-document computation)
{ "script": { "source": "doc['price'].value * 1.18 > 1000" } }

# ✅ FAST: Compute at index time, filter on stored value
{ "range": { "price_with_tax": { "gt": 1000 } } }

# ❌ SLOW: Deep pagination
{ "from": 50000, "size": 10 }

# ✅ FAST: search_after
{ "size": 10, "sort": [{"@timestamp": "desc"}, {"_id": "asc"}], "search_after": [...] }

# ❌ SLOW: sorting by script
{ "sort": { "_script": { "script": "...", "type": "number" } } }

# ✅ FAST: sort by indexed field (uses doc_values)
{ "sort": [{ "@timestamp": { "order": "desc" } }] }

# ❌ SLOW: Large result set (size: 10000)
# ✅ FAST: Aggregations or scroll/search_after for large exports
```

### Source Filtering (Reduce Fetch Phase Overhead)

```bash
# Fetch only needed fields (reduces network + deserialization)
GET logs-nginx-production/_search
{
  "_source": ["@timestamp", "message", "log.level", "service.name"],
  "query": { "match": { "message": "error" } }
}

# Exclude large fields
GET logs-nginx-production/_search
{
  "_source": {
    "excludes": ["payload", "raw_message", "debug_info"]
  }
}

# Use fields API instead of _source for specific fields
GET logs-nginx-production/_search
{
  "_source": false,
  "fields": ["@timestamp", "message", "log.level"],
  "query": { "match_all": {} }
}
```

## ⏱️ Part 5 - Async Search

### When to Use Async Search

```
Async search = run long query in background, poll for results

Use when:
  ✅ Query expected to take > 1-5 seconds
  ✅ Cross-cluster search spanning many indices
  ✅ Heavy aggregations on large datasets
  ✅ Don't want to block HTTP connection for minutes

Use cases:
  - Kibana "Run in background" feature
  - Reporting queries on months of data
  - Complex pipeline aggregations
```

### Async Search API

```bash
# Submit async search
POST logs-nginx-production/_async_search?wait_for_completion_timeout=5s&size=0
{
  "aggs": {
    "by_service": {
      "terms": { "field": "service.name", "size": 100 },
      "aggs": {
        "hourly": {
          "date_histogram": {
            "field": "@timestamp",
            "calendar_interval": "1h"
          }
        }
      }
    }
  }
}

# Response:
# {
#   "id": "FmRldE8zREVEUyWMGQAK-AAAAAAAABS...",
#   "is_partial": true,
#   "is_running": true,
#   "response": { ... partial results ... }
# }

# Poll for results (partial results returned while running)
GET _async_search/FmRldE8zREVEUyWMGQAK-AAAAAAAABS...?wait_for_completion_timeout=1s

# Get results (wait max 10s more)
GET _async_search/FmRldE8zREVEUyWMGQAK-AAAAAAAABS...?wait_for_completion_timeout=10s

# Delete when done
DELETE _async_search/FmRldE8zREVEUyWMGQAK-AAAAAAAABS...

# List running async searches
GET _async_search/status/FmRldE8zREVEUyWMGQAK-AAAAAAAABS...
```

## 📊 Part 6 - Profile API

### Use Profile API to Diagnose Slow Queries

```bash
GET logs-nginx-production/_search
{
  "profile": true,
  "query": {
    "bool": {
      "must": [{ "match": { "message": "timeout" } }],
      "filter": [{ "term": { "log.level": "ERROR" } }]
    }
  },
  "aggs": {
    "by_service": { "terms": { "field": "service.name" } }
  }
}

# Profile response structure:
# shards[].searches[].query[]
#   → type: BooleanQuery / TermQuery / MatchQuery etc
#   → time_in_nanos → where time is spent
#   → breakdown → advance, score, next_doc, match breakdown
#
# shards[].aggregations[]
#   → type: GlobalOrdinalsStringTermsAggregator etc
#   → time_in_nanos

# Key things to look for:
# 1. Which query clause is slowest?
# 2. Is aggregation slower than query?
# 3. Any "advance" time = missing index optimization
```

### Profile + Explain Together

```bash
# Profile at shard level
GET logs-nginx-production/_search
{
  "profile": true,
  "explain": true,
  "size": 1,
  "query": { "match": { "message": "connection timeout" } }
}
# Use rarely — profile=true + explain=true = very verbose
```

## 🏭 Part 7 - Production Search Patterns

### Pattern 1: Kibana Dashboard Optimization

```bash
# Kibana sends many concurrent search requests
# Key optimizations:

# 1. Round now to reduce cache misses
# Kibana should use: now/m or now/5m or now/h not exact now

# 2. Coordinator nodes dedicated to Kibana
# Kibana → Coordinator → Data Nodes
# Set Kibana to use coordinator's address

# 3. Increase search thread pool queue
PUT _cluster/settings
{
  "transient": {
    "thread_pool.search.queue_size": 10000
  }
}

# 4. Enable request cache for aggregate queries
# (automatic when size: 0 + rounded time range)

# 5. Add coordinator nodes before adding data nodes
# for search-bound workloads
```

### Pattern 2: Point-in-Time (PIT) Search

```bash
# For consistent pagination (snapshot of index state)
# Better than scroll for interactive pagination

# Open PIT
POST logs-nginx-production/_pit?keep_alive=5m
# Returns: { "id": "pit-id" }

# Search with PIT + search_after
GET _search
{
  "size": 10,
  "query": { "match": { "message": "error" } },
  "pit": {
    "id": "pit-id",
    "keep_alive": "5m"
  },
  "sort": [
    { "@timestamp": { "order": "desc" } },
    { "_shard_doc": "asc" }
  ]
}

# Next page: use sort values from last hit as search_after
GET _search
{
  "size": 10,
  "query": { "match": { "message": "error" } },
  "pit": { "id": "pit-id", "keep_alive": "5m" },
  "sort": [{ "@timestamp": "desc" }, { "_shard_doc": "asc" }],
  "search_after": ["2026-05-06T10:30:00Z", 1234]
}

# Close PIT when done
DELETE /_pit
{ "id": "pit-id" }
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Using exact `now` in filter | Not cached | Use `now/m`, `now/h`, `now/d` rounding |
| All queries in `must` context | No filter caching | Move structured filters to `filter` context |
| `size: 10000` for large exports | Deep pagination OOM | Use scroll or search_after |
| No `_source` filtering | Large network payload | Filter to only needed fields |
| Forcemerge on active indices | Constant re-merge, I/O storm | Only forcemerge read-only indices |
| Wildcard with leading `*` | Full index scan | Use match query instead |
| All fields in `_source` with scripts | Network overhead | Disable `_source`, use `fields` API |
| Search across all `*` indices | Unnecessary fan-out | Use specific index patterns |
| Large `shard_size` in terms agg | Memory pressure | Tune to actual cardinality |
| No async search for long queries | HTTP timeout | Use `_async_search` for > 5s queries |

## 💡 Key Principles

```
1. OS file system cache = primary search accelerator
   → More RAM → more cache → faster searches

2. Filter context = cached, query context = not cached
   → Move all structured filters to filter context always

3. Round "now" for Kibana dashboards
   → now/m or now/h → enables request cache → 100x faster repeat queries

4. Forcemerge read-only indices to 1 segment
   → 1 segment = fastest possible search, no merge overhead

5. Reduce fan-out with routing and specific index patterns
   → Don't search 100 shards if 2 shards have the data

6. search_after > scroll > from+size for pagination
   → from+size is O(n) — catastrophic at page 1000

7. Async search for anything > 5 seconds
   → Don't block HTTP connections for long queries

8. Source filtering reduces network payload
   → Fetch only fields you need in the UI

9. ARS (Adaptive Replica Selection) handles load balancing
   → No manual configuration needed for replica selection

10. Profile before optimizing
    → Always measure where time is actually spent
```
