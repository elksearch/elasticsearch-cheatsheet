## 🧠 ML Capabilities Overview

```
ELASTIC ML - THREE PILLARS:

1. ANOMALY DETECTION (Unsupervised)
   → Time-series anomaly detection
   → No labelled data needed
   → Uses Bayesian statistics + decomposition
   → Use case: detect unusual patterns in metrics/logs

2. DATA FRAME ANALYTICS (Supervised + Unsupervised)
   → Outlier detection
   → Classification (binary + multi-class)
   → Regression (predict numeric values)
   → Requires labelled training data (classification/regression)

3. NLP & INFERENCE
   → Text classification
   → Named entity recognition (NER)
   → Sentiment analysis
   → Zero-shot classification
   → Semantic text embedding (ELSER, E5)
   → LLM integration (inference API)
```

## 🔍 Part 1 - Anomaly Detection

### How Anomaly Detection Works

```
1. ES ML analyzes time-series data
2. Builds a model of "normal" behavior (baseline)
3. Detects deviations from baseline
4. Assigns anomaly scores (0-100):
   → 0-25: Low (informational)
   → 25-50: Warning
   → 50-75: Minor anomaly
   → 75-100: Major anomaly

Key concepts:
  DETECTOR  → what to measure (metric + field + function)
  BUCKET    → time interval analyzed (e.g., 15m)
  INFLUENCER → field that correlates with anomaly (e.g., host.name)
  MODEL     → learned baseline (automatically updated)
```

### Create Anomaly Detection Job

```bash
# Single metric job (simple — one time series)
PUT _ml/anomaly_detectors/nginx-request-rate
{
  "description": "Detect unusual nginx request rates",
  "analysis_config": {
    "bucket_span": "15m",
    "detectors": [
      {
        "function": "high_count",
        "detector_description": "High request count"
      }
    ],
    "influencers": ["host.name", "service.name"]
  },
  "data_description": {
    "time_field": "@timestamp",
    "time_format": "epoch_ms"
  },
  "datafeed_config": {
    "datafeed_id": "datafeed-nginx-request-rate",
    "indices": ["logs-nginx-production"],
    "query": {
      "bool": {
        "filter": [
          { "term": { "service.name": "nginx" } }
        ]
      }
    }
  }
}
```

```bash
  },

```

### Detector Functions Reference

```
count           → total event count
high_count      → unusually HIGH count
low_count       → unusually LOW count

mean            → average of field
high_mean       → unusually HIGH average
low_mean        → unusually LOW average

sum             → sum of field
high_sum        → unusually HIGH sum
low_sum         → unusually LOW sum

min             → minimum value (unusually low)
max             → maximum value (unusually high)

distinct_count  → unique values count
high_distinct_count → unusually HIGH unique count
low_distinct_count  → unusually LOW unique count

rare            → unusually rare value in by_field
freq_rare       → value appearing rarely in partition

non_zero_count  → count ignoring zero-count buckets
low_non_zero_count → unusually LOW non-zero count

lat_long        → geographic anomaly (requires lat/lon field)
```

## 📊 Part 2 - Data Frame Analytics

### Outlier Detection (Unsupervised)

```bash
# Find unusual data points without labeled data
PUT _ml/data_frame/analytics/payment-outlier-detection
{
  "description": "Find unusual payment transactions",
  "source": {
    "index": ["logs-payment-production"],
    "query": {
      "range": { "@timestamp": { "gte": "now-30d" } }
    }
  },
  "dest": {
    "index": "payment-outliers-results"
  },
  "analysis": {
    "outlier_detection": {
      "n_neighbors": 50,
      "method": "ensemble",
      "feature_influence_threshold": 0.1,
      "compute_feature_influence": true,
      "outlier_fraction": 0.05,
      "standardization_enabled": true
    }
  },
  "analyzed_fields": {
    "includes": [
      "payment.amount",
      "event.duration",
      "http.response.status_code"
    ]
  },
  "model_memory_limit": "512mb",
  "max_num_threads": 4
}

# Start analysis
POST _ml/data_frame/analytics/payment-outlier-detection/_start

# Monitor progress
GET _ml/data_frame/analytics/payment-outlier-detection/_stats

# Results in dest index:
# ml.outlier_score: 0.0-1.0 (higher = more unusual)
# ml.feature_influence.*: which feature caused the anomaly

# Query outliers
GET payment-outliers-results/_search
{
  "query": {
    "range": { "ml.outlier_score": { "gte": 0.9 } }
  },
  "sort": [{ "ml.outlier_score": { "order": "desc" } }]
}
```

## 🔤 Part 4 - ELSER (Semantic Search)

### What is ELSER?

```
ELSER = Elastic Learned Sparse EncodeR
  → Elastic's proprietary sparse embedding model
  → Transforms text → sparse vector (token weights)
  → Enables semantic search without dense vectors
  → Better than BM25 for meaning-based search
  → No GPU required (sparse = efficient)
  → Available out-of-box (no HuggingFace import needed)

ELSER vs BM25:
  BM25:  "elastic" matches only documents with word "elastic"
  ELSER: "elastic" also matches "flexible", "stretch", "resilient"
         (semantic neighbors in embedding space)
```

### Deploy ELSER

```bash
# Deploy ELSER v2 (latest)
PUT _inference/sparse_embedding/my-elser-endpoint
{
  "service": "elser",
  "service_settings": {
    "num_allocations": 1,
    "num_threads": 1,
    "model_id": ".elser_model_2_linux-x86_64"
  }
}

# Check status
GET _inference/sparse_embedding/my-elser-endpoint
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| ML nodes not isolated | Model loading OOM kills data nodes | Always dedicate ML nodes |
| Bucket span too small | Noisy results, too many anomalies | Start with 15m, tune based on data frequency |
| No influencers set | Can't identify root cause | Always set relevant influencers |
| Model memory limit too low | Job fails with memory error | Set to at least 2x estimated model size |
| ELSER on data nodes | CPU competition with indexing | Use dedicated ML nodes for ELSER |
| Not setting num_allocations | Single inference thread, slow | Set based on expected concurrency |
| Running DFA on all fields | Slow + noisy features | Carefully select analyzed_fields |
| Not evaluating classification model | Unknown model quality | Always run _evaluate after training |
| ELSER without hybrid search | Misses exact keyword matches | Combine ELSER + BM25 with RRF |
| Anomaly job without calendar | Alerts on known events (deployments) | Create ML calendars for planned events |

## 💡 Key Principles

```
1. Anomaly detection needs no labeled data
   → Start with count + high_mean detectors, tune from there

2. Bucket span = granularity of detection
   → Too small = noisy, too large = misses short spikes
   → Match to your data's natural frequency

3. ELSER > BM25 for semantic/intent search
   → Use hybrid (BM25 + ELSER via RRF) for best results

4. semantic_text field = simplest semantic search
   → Handles embedding at both index and query time automatically

5. DFA outlier detection = anomaly detection for non-time-series
   → Great for finding unusual transactions, users, patterns

6. Always isolate ML workloads on dedicated nodes
   → Inference models consume significant CPU + memory

7. Use inference API for LLM integration
   → Connects ES to OpenAI, Cohere, Anthropic, Bedrock seamlessly

8. Train classification/regression with 80% of data
   → Evaluate on remaining 20% to measure real accuracy

9. Forecast only makes sense for seasonal data
   → Not useful for purely random/noisy time series

10. Calendars prevent false anomalies during planned events
    → Add deployment windows, maintenance periods to ML calendar
```
