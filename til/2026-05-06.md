## 🧠 Indexing Flow - Internal Path

```
Client → Bulk Request
           │
           ▼
    Coordinating Node
    (parses, routes by shard)
           │
     ┌─────┴─────┐
     ▼           ▼
  Shard 0     Shard 1
  Primary     Primary
     │           │
  Translog    Translog  ← written first (WAL)
     │           │
  In-memory   In-memory ← buffered (not searchable yet)
  Buffer      Buffer
     │           │
  Replica     Replica   ← parallel write
     │
  REFRESH (1s) → searchable
     │
  FLUSH (512mb) → durable on disk
     │
  MERGE → segments consolidated
```

## ⚡ Part 1 - Bulk API Optimization

### Bulk API Basics

```bash
# Single bulk request format (NDJSON — newline delimited)
POST _bulk
{ "index": { "_index": "logs-nginx-production" } }
{ "@timestamp": "2026-05-06T10:00:00Z", "message": "GET /api/v1", "status": 200 }
{ "index": { "_index": "logs-nginx-production" } }
{ "@timestamp": "2026-05-06T10:00:01Z", "message": "POST /api/v2", "status": 500 }
{ "delete": { "_index": "logs-nginx-production", "_id": "old-doc-123" } }
{ "update": { "_index": "logs-nginx-production", "_id": "doc-456" } }
{ "doc": { "status": "resolved" } }

# Check bulk response for errors
# Response: { "errors": false, "took": 10, "items": [...] }
# If errors: true → check items[].*.error for failed docs
```

### Optimal Bulk Request Size

```
Target: 5 MB – 15 MB per bulk request
        1,000 – 5,000 documents per request

Too small → too many HTTP overhead / round trips
Too large → GC pressure, timeout risk, memory spikes

ALWAYS test with your data:
  Start at 1,000 docs → measure throughput
  Double to 2,000 → measure again
  Continue until throughput stops improving (diminishing returns)

Rule: measure bytes, not just doc count
  Small docs (100B): 10,000 per request may be fine
  Large docs (10KB): 500 per request may be better
```

### Bulk API Best Practices

```bash
# 1. Use auto-generated IDs (faster — no check for existing doc)
# BAD: { "index": { "_id": "my-custom-id" } }   ← ES must check if exists
# GOOD: { "index": {} }                           ← ES generates UUID (no check)

# 2. Set pipeline at request level
POST logs-nginx-production/_bulk?pipeline=prod-enrichment-pipeline
{ "index": {} }
{ "@timestamp": "...", "message": "..." }

# 3. Set routing at request level
POST logs-nginx-production/_bulk?routing=service-a
{ "index": {} }
{ "@timestamp": "...", "service.name": "service-a" }

# 4. Refresh only when needed (not after every bulk)
POST logs-nginx-production/_bulk?refresh=false    # default — fastest
POST logs-nginx-production/_bulk?refresh=wait_for  # wait for refresh (slower)
POST logs-nginx-production/_bulk?refresh=true      # force refresh (SLOWEST — avoid!)

# 5. Handle partial failures
POST _bulk
# Response: check errors field
# Retry ONLY failed items (not full batch)
```

### Parallel Bulk Requests

```
Single thread → limited by single connection throughput

Optimal parallelism: number_of_data_nodes * number_of_hot_shards / 5
  Example: 6 hot nodes × 3 shards each = 18 primary shards
  Optimal concurrent bulk requests ≈ 18 / 5 ≈ 4

Too many concurrent requests → write thread pool queue fills → rejections
Too few concurrent requests → network + disk underutilized

Start with 2-4 concurrent bulk requests
Increase until rejections start → back off by 1
```

## 🔧 Part 2 - Index Settings for Bulk Load

### Temporary Bulk Load Settings

```bash
# Apply before bulk load
PUT logs-nginx-production/_settings
{
  "index": {
    "refresh_interval": "-1",
    "number_of_replicas": 0,
    "translog.durability": "async",
    "translog.flush_threshold_size": "1gb",
    "translog.sync_interval": "60s"
  }
}

# Run bulk load...

# Restore after bulk load
PUT logs-nginx-production/_settings
{
  "index": {
    "refresh_interval": "1s",
    "number_of_replicas": 1,
    "translog.durability": "request",
    "translog.flush_threshold_size": "512mb",
    "translog.sync_interval": "5s"
  }
}

# Force merge after bulk load (optional — only for static indices)
POST logs-nginx-production/_forcemerge?max_num_segments=1
```

### Index Buffer Size

```yaml
# elasticsearch.yml
# Default: 10% of heap for indexing buffer (shared across all shards)
indices.memory.index_buffer_size: 30%
# or absolute:
indices.memory.index_buffer_size: 2gb

# Per-shard minimum:
indices.memory.min_index_buffer_size: 48mb

# Increase for write-heavy clusters:
# 30% is safe for pure indexing nodes
# 15-20% for mixed read/write nodes
```

## 📝 Part 3 - Translog Tuning

### Translog Settings Deep Dive

```bash
PUT logs-nginx-production/_settings
{
  "index": {

    # DURABILITY
    # "request" = fsync after every index operation (SAFE, SLOWER)
    # "async"   = fsync every sync_interval (FAST, small data loss risk)
    "translog.durability": "request",

    # SYNC INTERVAL (only when durability=async)
    # Flush translog to disk every N seconds
    "translog.sync_interval": "5s",

    # FLUSH THRESHOLD
    # Flush translog + create new segment when translog reaches this size
    "translog.flush_threshold_size": "512mb",

    # RETENTION (how long to keep old translog for replicas)
    "translog.retention.size": "512mb",
    "translog.retention.age": "12h"
  }
}
```

### When to Use async Durability

```
translog.durability: async → use when:
  ✅ High write throughput is priority
  ✅ Can tolerate data loss of up to sync_interval duration
  ✅ Have other durability mechanisms (replicas, snapshots)
  ✅ Bulk historical data load

translog.durability: request → use when:
  ✅ Zero data loss is requirement
  ✅ Financial/compliance data
  ✅ Small clusters without replicas
  ✅ Production default — always safer
```

## 🧵 Part 4 - Thread Pool Tuning

### Write Thread Pool

```yaml
# elasticsearch.yml
# write thread pool: handles index/bulk/delete operations
# Default: min(# CPUs, 32) threads, queue size = 200

thread_pool.write.size: 8          # = number of CPU cores
thread_pool.write.queue_size: 1000 # increase if rejections happen

# search thread pool
thread_pool.search.size: 13        # int((# cores * 3) / 2) + 1
thread_pool.search.queue_size: 1000
```

### Monitor Thread Pool

```bash
# Check all thread pools
GET _cat/thread_pool?v&h=name,type,active,rejected,queue,completed,largest&s=rejected:desc

# Rejections > 0 means write thread pool is overwhelmed
# Solutions:
#   1. Reduce bulk request rate
#   2. Increase queue_size (masks problem temporarily)
#   3. Add more nodes
#   4. Optimize bulk request size

# Node-level thread pool detail
GET _nodes/stats/thread_pool
```

## 🗃️ Part 5 - Shard Routing Optimization

### Default Routing

```
Default: shard = hash(document_id) % number_of_shards

Problem: All documents go to ALL shards
  → Coordinating node must ask all shards for every request
  → High fan-out = high network overhead
```

### Custom Routing (route by field value)

```bash
# Index with custom routing
PUT logs-nginx-production/_doc/1?routing=service-a
{
  "@timestamp": "2026-05-06T10:00:00Z",
  "service.name": "service-a",
  "message": "Request received"
}

# Bulk with routing
POST logs-nginx-production/_bulk
{ "index": { "routing": "service-a" } }
{ "@timestamp": "...", "service.name": "service-a" }
{ "index": { "routing": "service-b" } }
{ "@timestamp": "...", "service.name": "service-b" }

# Search with routing (HUGE speed improvement!)
GET logs-nginx-production/_search?routing=service-a
{
  "query": { "term": { "service.name": "service-a" } }
}
# → Only searches the shard(s) for service-a, not ALL shards!

# Require routing at mapping level (enforce correct usage)
PUT logs-nginx-production
{
  "mappings": {
    "_routing": { "required": true }
  }
}
```

### Routing Partition Count (reduce hotspots)

```bash
# When routing by low-cardinality field (e.g., 5 services, 10 shards)
# Without partition: each service goes to exactly 1 shard → hotspot
# With partition: each service routes to multiple shards → balanced

PUT logs-nginx-production
{
  "settings": {
    "number_of_shards": 10,
    "routing_partition_size": 3   # each routing key → 3 shards
  }
}
```

## 💪 Part 6 - Indexing Pressure

### What is Indexing Pressure?

```
Indexing pressure = mechanism to protect cluster from being overwhelmed
                    by too many in-flight indexing requests

When coordinating + primary + replica all processing:
  → Each uses heap memory for in-flight data
  → If too much in-flight → cluster becomes unstable → OOM

ES monitors indexing memory usage:
  → primary_operations + coordinating operations + replica operations
  → If exceeds limit → new requests REJECTED (HTTP 429)
```

### Configure Indexing Pressure

```bash
# View current indexing pressure
GET _nodes/stats/indexing_pressure

# Response:
# current.coordinating_in_bytes
# current.primary_in_bytes
# current.replica_in_bytes
# current.all_in_bytes
# limit_in_bytes (= 10% of heap by default)

# Configure limit
PUT _cluster/settings
{
  "persistent": {
    "indexing_pressure.memory.limit": "15%"
  }
}
# Default: 10% of heap
# Increase carefully — higher = more in-flight = OOM risk

# Monitor rejections
GET _nodes/stats/indexing_pressure?filter_path=nodes.*.indexing_pressure.current,nodes.*.indexing_pressure.total.rejections
```

## 🔢 Part 7 - Shard Count Optimization

### How Many Shards?

```
RULE OF THUMB (2024+):
  Hot indices: 1 shard per 50 GB of data
  Max shard size: 50 GB
  Min shard size: 10 GB (smaller = overhead not worth it)

Formula:
  number_of_shards = ceil(expected_index_size_gb / 50)

Examples:
  Expected 30 GB → 1 shard
  Expected 150 GB → 3 shards
  Expected 500 GB → 10 shards

For write throughput:
  More shards = more parallelism = higher write throughput
  But more shards = more overhead on master

Balance: start with 1-2 shards, scale out if write becomes bottleneck
```

### Check Shard Size Distribution

```bash
# Check actual shard sizes
GET _cat/shards?v&h=index,shard,prirep,store,node&s=store:desc&bytes=gb

# Check index-level store size
GET _cat/indices?v&h=index,pri,rep,docs.count,store.size,pri.store.size&s=pri.store.size:desc&bytes=gb

# Alert: shards > 50GB need attention
# Alert: shards < 1GB may be too many
```

## 📊 Part 8 - Mapping Optimizations for Indexing Speed

```bash
# 1. Disable _source for pure-agg use cases (saves disk I/O)
PUT _index_template/agg-only-template
{
  "template": {
    "mappings": {
      "_source": { "enabled": false }
    }
  }
}
# WARNING: Cannot reindex or update without _source!

# 2. Disable norms for non-scoring fields
{
  "properties": {
    "status": { "type": "keyword", "norms": false },
    "host.name": { "type": "keyword", "norms": false }
  }
}

# 3. Disable doc_values for fields you'll never sort/aggregate
{
  "properties": {
    "raw_log_line": { "type": "text", "doc_values": false }
  }
}

# 4. Disable index for fields you'll never search
{
  "properties": {
    "payload_bytes": { "type": "binary", "index": false }
  }
}

# 5. Use best_compression codec
PUT logs-nginx-production/_settings
{
  "index.codec": "best_compression"
}
# Reduces disk by 20-30% — slight CPU cost during indexing

# 6. Use half_float for low-precision metrics
{
  "properties": {
    "cpu_percent": { "type": "half_float" }
  }
}
```

## 🖥️ Part 9 - OS & Hardware Tuning

```bash
# 1. Disable swapping (CRITICAL)
sudo swapoff -a
# Permanent: comment out swap in /etc/fstab

# In elasticsearch.yml:
bootstrap.memory_lock: true

# 2. Increase file descriptors
echo "elasticsearch soft nofile 65535" >> /etc/security/limits.conf
echo "elasticsearch hard nofile 65535" >> /etc/security/limits.conf

# 3. Virtual memory for Elasticsearch
echo "vm.max_map_count=262144" >> /etc/sysctl.conf
sysctl -p

# 4. Filesystem: use noatime mount option
# /etc/fstab: /data ext4 defaults,noatime 0 0

# 5. I/O scheduler: deadline or noop for SSDs
echo deadline > /sys/block/sda/queue/scheduler
# For SSDs:
echo noop > /sys/block/nvme0n1/queue/scheduler

# 6. Disable transparent huge pages
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag

# 7. Use local storage (DAS) not NAS for hot nodes
# NAS introduces latency and has consistency risks with ES
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| `refresh=true` on every bulk | 10-100x slower | Use `refresh=false` (default) |
| Small bulk requests (10-50 docs) | HTTP overhead dominates | Target 5-15MB per request |
| Too many concurrent bulk requests | Thread pool rejections | Start with 4 threads, tune up |
| replicas=1 during bulk load | 2x write amplification | Set to 0 during load, restore after |
| refresh_interval=1s during bulk load | Constant segment creation | Set to -1 during load |
| Using custom IDs for all docs | ID lookup overhead | Use auto-generated IDs when possible |
| Translog durability=request for high-throughput | fsync bottleneck | Use async with replicas for safety net |
| Too many shards (>50 per node) | Master overhead, GC pressure | Consolidate, shrink, or delete indices |
| NAS/NFS for hot tier storage | High latency, consistency issues | Always use local DAS SSD |
| No indexing pressure limits | Cluster OOM under load spike | Set indexing_pressure.memory.limit |

## 💡 Key Principles

```
1. Bulk API is mandatory for production indexing
   → Never index one document at a time at scale

2. 5-15 MB per bulk request is the sweet spot
   → Measure and tune for your specific document size

3. Disable refresh + replicas during large bulk loads
   → 10-100x throughput improvement possible

4. Auto-generated IDs are faster than custom IDs
   → Skip the "does this document exist?" check

5. translog.durability=async + replicas = safe high throughput
   → Async + 1 replica gives durability without fsync overhead

6. OS tuning is as important as ES settings
   → swapoff, vm.max_map_count, file descriptors — non-negotiable

7. Local SSD (DAS) only for hot tier
   → NAS latency will bottleneck writes before ES can

8. Measure before optimizing
   → Use Rally or simple curl timing to establish baseline

9. Indexing pressure = auto protection
   → Don't raise the limit without understanding why it's hitting

10. Shard count = write parallelism
    → More shards = more concurrent writes = higher throughput
    → But more overhead — find the balance
```
