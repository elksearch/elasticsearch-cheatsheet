## Downsampling & Data Lifecycle Management (DLM)
### Metrics Compression, DLM vs ILM, Time-Series Data, Cost Optimization

> Downsampling reduces metrics data volume by aggregating time-series values into larger intervals.
> DLM (Data Lifecycle Management) is the modern successor to ILM specifically for data streams.
> Together they slash storage costs for metrics by 90%+ without losing analytical value.

## 🧠 Core Concepts

```
DOWNSAMPLING:
  Problem: 1 metric every 30 seconds × 1000 hosts × 365 days = HUGE data
  Solution: Compress old metrics into larger time buckets

  30-second intervals → 5-minute intervals (10x reduction)
  5-minute intervals → 1-hour intervals (12x reduction)
  1-hour intervals → 1-day intervals (24x reduction)

  TOTAL: 2880x reduction with 3-tier downsampling!

  What is kept per bucket:
    → min, max, sum, value_count (to compute avg)
    → All labels/dimensions (unchanged)
    → Timestamp = start of bucket

DLM vs ILM:
  ILM (Index Lifecycle Management):
    → Works on ANY index type
    → Complex phase configuration
    → Requires rollover aliases
    → More flexible but more complex

  DLM (Data Lifecycle Management):
    → Works ONLY on data streams
    → Simpler configuration
    → Built-in downsampling support
    → Recommended for new deployments (ES 8.11+)

TSDS (Time Series Data Stream):
  → Special data stream type optimized for metrics
  → Required for downsampling
  → Dimensions (labels) + metrics stored separately
  → Automatic deduplication of same-time same-dimension docs
```

## 📊 Part 1 - Time Series Data Stream (TSDS)

### What is TSDS?

```
Standard data stream: any documents, any fields
TSDS: optimized for metrics with dimensions + metrics

KEY FIELDS:
  Dimensions: identifying fields (host.name, service.name, region)
              → Define unique time series
              → Stored efficiently (columnar)

  Metrics:    measured values (cpu.percent, memory.used, requests.count)
              → Support downsampling
              → Pre-compute min/max/sum/count

BENEFITS:
  → 40-70% storage reduction vs standard data streams
  → Faster aggregations (columnar storage)
  → Required for downsampling
  → Automatic _tsid (time series ID) generation
```

### Create TSDS Index Template

```bash
PUT _index_template/metrics-system-template
{
  "index_patterns": ["metrics-system-*"],
  "data_stream": {},
  "priority": 500,
  "template": {
    "settings": {
      "index": {
        "mode": "time_series",            # ← Enable TSDS
        "routing_path": ["host.name", "service.name"],  # dimensions for routing
        "time_series": {
          "start_time": "2026-01-01T00:00:00Z",
          "end_time": "2027-01-01T00:00:00Z"   # or use rolling window
        }
      }
    },
    "mappings": {
      "properties": {

        "@timestamp": { "type": "date" },

        # DIMENSIONS (identifying labels)
        "host.name": {
          "type": "keyword",
          "time_series_dimension": true   # ← marks as dimension
        },
        "service.name": {
          "type": "keyword",
          "time_series_dimension": true
        },
        "cloud.region": {
          "type": "keyword",
          "time_series_dimension": true
        },

        # METRICS (measured values)
        "system.cpu.percent": {
          "type": "float",
          "time_series_metric": "gauge"   # gauge, counter, summary, histogram
        },
        "system.memory.used.bytes": {
          "type": "long",
          "time_series_metric": "gauge"
        },
        "http.requests.total": {
          "type": "long",
          "time_series_metric": "counter"  # monotonically increasing
        },
        "http.request.duration.ms": {
          "type": "double",
          "time_series_metric": "gauge"
        }
      }
    }
  }
}
```

### Metric Types

```
gauge:   → can go up or down (CPU%, memory usage)
          → downsampled: min, max, sum, value_count
          → avg = sum / value_count

counter: → monotonically increasing (request count, bytes received)
          → downsampled: last value only (rate computed on query)
          → never decreases (resets to 0 on restart)

histogram: → pre-aggregated distribution (latency percentiles)
            → stored as values[] + counts[] arrays
            → downsampled: merged histograms

summary:  → pre-computed quantiles
```

## ⬇️ Part 2 - Downsampling

### Manual Downsampling

```bash
# Downsample a TSDS backing index to 1-hour intervals
POST metrics-system-production/_downsample/metrics-system-production-1h
{
  "fixed_interval": "1h"
}

# Check the downsampled index
GET metrics-system-production-1h/_count

# Query downsampled index
GET metrics-system-production-1h/_search
{
  "size": 0,
  "aggs": {
    "avg_cpu": {
      "avg": { "field": "system.cpu.percent" }
    }
  }
}
# avg computed as: sum / value_count (pre-aggregated values used)
```

### Downsampling via ILM (Automated)

```bash
PUT _ilm/policy/metrics-with-downsampling
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": {
            "max_age": "1d",
            "max_primary_shard_size": "50gb"
          },
          "set_priority": { "priority": 100 }
        }
      },
      "warm": {
        "min_age": "1d",
        "actions": {
          "downsample": {
            "fixed_interval": "5m"   # ← 30s → 5m (10x reduction)
          },
          "set_priority": { "priority": 50 }
        }
      },
      "cold": {
        "min_age": "7d",
        "actions": {
          "downsample": {
            "fixed_interval": "1h"   # ← 5m → 1h (12x additional)
          },
          "set_priority": { "priority": 0 }
        }
      },
      "frozen": {
        "min_age": "30d",
        "actions": {
          "downsample": {
            "fixed_interval": "1d"   # ← 1h → 1d (24x additional)
          },
          "searchable_snapshot": {
            "snapshot_repository": "s3-repo"
          }
        }
      },
      "delete": {
        "min_age": "365d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

### Storage Savings Calculation

```
Original: 30-second intervals for 1 year
  1 year = 31,536,000 seconds / 30 = 1,051,200 data points per series
  1000 hosts × 10 metrics = 10,000 series
  Total: 10,512,000,000 data points

After 3-tier downsampling:
  Hot (0-1d):     30s intervals → keep as is      =  2,880 points/series
  Warm (1-7d):    5m intervals                     =  2,016 points/series
  Cold (7-30d):   1h intervals                     =    552 points/series
  Frozen (30-365d): 1d intervals                   =    335 points/series

Total: ~5,783 points/series (vs 1,051,200 original)
Reduction: 99.4%!

Cost impact:
  Original: 100 GB/day × 365 = 36.5 TB → $10,000/month
  With downsampling: ~0.6 GB/day equivalent → $60/month
```

## 🔄 Part 3 - Data Lifecycle Management (DLM)

### DLM vs ILM Comparison

```
ILM:
  → Works on: any index type
  → Config location: ILM policy (separate resource)
  → Assignment: per index template
  → Rollover: requires alias setup
  → Downsampling: supported (ES 8.7+)
  → Status: mature, feature-rich

DLM:
  → Works on: data streams ONLY
  → Config location: directly on data stream / template
  → Assignment: inline in data stream lifecycle
  → Rollover: automatic (no alias needed)
  → Downsampling: built-in support
  → Status: newer, simpler, recommended for data streams
  → Available: ES 8.11+

WHEN TO USE WHAT:
  New metrics data streams → DLM
  Existing ILM setup → keep ILM (no need to migrate)
  Log data streams → either works (ILM for complex rules)
  Non-data-stream indices → ILM only
```

### Create Data Stream with DLM

```bash
# Method 1: Lifecycle in index template
PUT _index_template/metrics-dlm-template
{
  "index_patterns": ["metrics-dlm-*"],
  "data_stream": {},
  "priority": 500,
  "template": {
    "settings": {
      "index.mode": "time_series"
    },
    "lifecycle": {
      "data_retention": "90d",        # delete after 90 days
      "downsampling": [
        {
          "after": "1d",              # downsample after 1 day
          "fixed_interval": "5m"
        },
        {
          "after": "7d",
          "fixed_interval": "1h"
        },
        {
          "after": "30d",
          "fixed_interval": "1d"
        }
      ]
    },
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "host.name": { "type": "keyword", "time_series_dimension": true },
        "cpu.percent": { "type": "float", "time_series_metric": "gauge" }
      }
    }
  }
}
```

### Manage DLM on Existing Data Streams

```bash
# Set lifecycle on existing data stream
PUT _data_stream/metrics-system-production/_lifecycle
{
  "data_retention": "90d",
  "downsampling": [
    {
      "after": "1d",
      "fixed_interval": "5m"
    },
    {
      "after": "7d",
      "fixed_interval": "1h"
    }
  ]
}

# Get lifecycle status
GET _data_stream/metrics-system-production/_lifecycle

# Get detailed lifecycle stats
GET _data_stream/metrics-system-production/_lifecycle/explain

# Remove lifecycle (disable DLM)
DELETE _data_stream/metrics-system-production/_lifecycle

# Global DLM settings
PUT _cluster/settings
{
  "persistent": {
    "data_streams.lifecycle.poll_interval": "5m",   # how often DLM runs
    "cluster.lifecycle.default.rollover": "max_age=1d,max_primary_shard_size=50gb"
  }
}
```

## 🔍 Part 4 - Querying Downsampled Data

### Transparent Query (Same API)

```bash
# Search works the same whether data is original or downsampled
# ES automatically uses aggregated values when querying downsampled indices

GET metrics-system-production/_search
{
  "size": 0,
  "aggs": {
    "avg_cpu": {
      "avg": { "field": "system.cpu.percent" }
    },
    "max_cpu": {
      "max": { "field": "system.cpu.percent" }
    },
    "hourly_avg": {
      "date_histogram": {
        "field": "@timestamp",
        "fixed_interval": "1h"
      },
      "aggs": {
        "avg_cpu": { "avg": { "field": "system.cpu.percent" } }
      }
    }
  }
}
```

### Cross-Tier Search (All Tiers Together)

```bash
# Search across all tiers simultaneously
GET metrics-system-production,.ds-metrics-system-production-1h-*,.ds-metrics-system-production-1d-*/_search
{
  "size": 0,
  "query": {
    "range": {
      "@timestamp": {
        "gte": "now-90d",
        "lte": "now"
      }
    }
  },
  "aggs": {
    "daily_avg_cpu": {
      "date_histogram": {
        "field": "@timestamp",
        "calendar_interval": "1d"
      },
      "aggs": {
        "avg_cpu": { "avg": { "field": "system.cpu.percent" } }
      }
    }
  }
}
# Recent data: from 30s original data
# Week-old data: from 5m downsampled
# Month-old data: from 1h downsampled
# Year-old data: from 1d downsampled
# All transparent to the query!
```

## 🏭 Part 5 - Production Setup

### Complete Metrics Stack with DLM + Downsampling

```bash
# Step 1: ILM policy for downsampling schedule
PUT _ilm/policy/metrics-production-policy
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": { "max_age": "1d", "max_primary_shard_size": "20gb" }
        }
      },
      "warm": {
        "min_age": "1d",
        "actions": {
          "downsample": { "fixed_interval": "5m" },
          "shrink": { "number_of_shards": 1 }
        }
      },
      "cold": {
        "min_age": "7d",
        "actions": {
          "downsample": { "fixed_interval": "1h" }
        }
      },
      "delete": {
        "min_age": "365d",
        "actions": { "delete": {} }
      }
    }
  }
}

# Step 2: TSDS index template
PUT _index_template/metrics-production-template
{
  "index_patterns": ["metrics-*-production"],
  "data_stream": {},
  "priority": 500,
  "template": {
    "settings": {
      "index.mode": "time_series",
      "index.lifecycle.name": "metrics-production-policy",
      "number_of_shards": 1,
      "number_of_replicas": 1
    },
    "mappings": {
      "properties": {
        "@timestamp":       { "type": "date" },
        "host.name":        { "type": "keyword", "time_series_dimension": true },
        "service.name":     { "type": "keyword", "time_series_dimension": true },
        "cloud.region":     { "type": "keyword", "time_series_dimension": true },
        "cpu.percent":      { "type": "float",  "time_series_metric": "gauge" },
        "memory.used":      { "type": "long",   "time_series_metric": "gauge" },

        "errors.total":     { "type": "long",   "time_series_metric": "counter" },
        "latency.ms":       { "type": "double", "time_series_metric": "gauge" }

}
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Using downsampling on non-TSDS | Error — not supported | Set `index.mode: time_series` first |
| Downsampling before data is complete | Partial data in downsampled index | Use min_age to ensure all data is written |
| Not setting `time_series_dimension` | Documents not deduplicated | Mark all identifier fields as dimension |
| Using `counter` type for gauge metrics | Wrong aggregation behavior | gauge = anything, counter = monotonic only |
| Querying downsampled with percentiles | Inaccurate results (pre-agg data) | Percentiles not accurate on downsampled data |
| Not accounting for counter resets | Wrong rate calculations | Handle counter resets in queries |
| DLM + ILM both on same data stream | Conflict | Use only one lifecycle management system |
| Downsampling interval smaller than data | Empty buckets | Ensure interval > original collection frequency |
| No cross-tier search setup | Missing historical data | Include all backing indices in searches |
| Short retention for compliance data | Data deleted before audit | Override retention per data stream as needed |

## 💡 Key Principles

```
1. TSDS = prerequisite for downsampling
   → index.mode: time_series must be set

2. Dimensions identify time series
   → host.name + service.name = unique series

3. Gauge vs Counter matters
   → Gauge: min/max/avg meaningful
   → Counter: only rate (delta) meaningful

4. DLM for new data streams, ILM for existing
   → Don't mix both on same data stream

5. Downsampling is one-way and irreversible
   → Original high-resolution data deleted after downsampling

6. Three-tier downsampling = 99%+ storage reduction
   → 30s → 5m → 1h → 1d for year-long retention

7. Query works the same on all tiers
   → ES transparently uses pre-aggregated values

8. Percentiles are approximate on downsampled data
   → Store histogram metric type for accurate percentiles

9. Counter metrics need rate calculation
   → Use derivative or rate aggregations, not raw values

10. DLM is simpler but newer
    → Less battle-tested than ILM — monitor closely in production
```
