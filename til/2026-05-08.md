## 🧠 The Four Pillars of Observability

```
LOGS      → What happened? (events, errors, transactions)
METRICS   → How is it performing? (CPU, memory, latency, error rate)
TRACES    → Where is it slow? (distributed request flow across services)
PROFILES  → Why is it slow? (CPU flamegraph, memory allocation)

ELASTIC STACK MAPPING:
  Logs    → Filebeat / Elastic Agent → Elasticsearch → Kibana Discover/Logs
  Metrics → Metricbeat / Elastic Agent → Elasticsearch → Kibana Metrics
  Traces  → APM Agents / OTel → APM Server → Elasticsearch → Kibana APM
  Profiles→ Universal Profiling Agent → Elasticsearch → Kibana Profiling
```

## 📦 Part 1 — Elastic Agent & Fleet

### Elastic Agent vs Individual Beats

```
BEATS (old approach):
  Filebeat  → logs
  Metricbeat → metrics
  Packetbeat → network
  Auditbeat → audit
  → Each installed separately, configured separately

ELASTIC AGENT (new approach):
  → Single agent replaces all beats
  → Policy-driven configuration via Fleet UI
  → 200+ integrations available
  → Auto-updates via Fleet
  → Tamper protection
  → One agent per host
```

### Fleet Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                        Fleet Server                          │
│    (manages policies, coordinates agent updates)             │
└───────────────────────────┬─────────────────────────────────┘
                            │ Policy distribution
              ┌─────────────┼─────────────┐
              │             │             │
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ Agent 1  │  │ Agent 2  │  │ Agent 3  │
        │ host-01  │  │ host-02  │  │ host-03  │
        └──────────┘  └──────────┘  └──────────┘
              │             │             │
              └─────────────┼─────────────┘
                            │ Data
                            ▼
                     Elasticsearch
```

### Install Elastic Agent

```bash
# Download
curl -L -O https://artifacts.elastic.co/downloads/beats/elastic-agent/elastic-agent-9.0.2-linux-x86_64.tar.gz
tar xzvf elastic-agent-9.0.2-linux-x86_64.tar.gz
cd elastic-agent-9.0.2-linux-x86_64

# Enroll in Fleet
sudo ./elastic-agent install \
  --fleet-server-es=https://my-es:9200 \
  --fleet-server-es-ca=/path/to/ca.crt \
  --fleet-server-service-token=AAEAAWVsYXN0aWMv... \
  --fleet-server-policy=fleet-server-policy

# OR enroll existing Fleet Server
sudo ./elastic-agent install \
  --url=https://fleet-server:8220 \
  --enrollment-token=your-enrollment-token \
  --certificate-authorities=/path/to/ca.crt

# Check status
sudo elastic-agent status

# Restart agent
sudo systemctl restart elastic-agent

# View logs
sudo journalctl -u elastic-agent -f
tail -f /var/log/elastic-agent/elastic-agent.log
```

## 📊 Part 2 — Metrics Collection

### System Metrics (via Elastic Agent)

```yaml
# Agent policy configuration (in Fleet UI or as YAML)
inputs:
  - type: logfile
    streams:
      - paths: [/var/log/syslog, /var/log/messages]
        tags: [system]

  - type: system/metrics
    streams:
      - metricsets: [cpu, memory, disk, network, filesystem, load]
        period: 30s

  - type: docker/metrics
    streams:
      - metricsets: [container, event, cpu, memory, network]
        period: 10s
        hosts: ["unix:///var/run/docker.sock"]
```

### Kubernetes Metrics

```yaml
# In agent policy for Kubernetes integration
inputs:
  - type: kubernetes/metrics
    streams:
      - metricsets: [node, pod, container, volume, system]
        period: 30s
        hosts: ["${env.NODE_NAME}:10250"]
        bearer_token_file: /var/run/secrets/kubernetes.io/serviceaccount/token
        ssl.verification_mode: none

  - type: kubernetes/metrics
    streams:
      - metricsets: [state_node, state_pod, state_container, state_deployment]
        hosts: ["kube-state-metrics:8080"]
        period: 30s
```

## 🔍 Part 3 — Log Collection & Management

### Structured Logging Best Practices

```json
// GOOD structured log (JSON):
{
  "@timestamp": "2026-05-08T10:30:00.123Z",
  "log.level": "ERROR",
  "service.name": "payment-service",
  "service.version": "2.1.4",
  "service.environment": "production",
  "trace.id": "abc123def456",
  "transaction.id": "xyz789",
  "message": "Payment processing failed",
  "error.type": "PaymentGatewayException",
  "error.message": "Connection timeout to gateway",
  "payment.id": "pay-456",
  "payment.amount": 1500.00,
  "payment.currency": "INR",
  "duration_ms": 30045,
  "host.name": "payment-server-01"
}

// BAD unstructured log:
// 2026-05-08 10:30:00 ERROR payment failed for user 123 - timeout
```

### Log Routing with Reroute Processor

```bash
PUT _ingest/pipeline/log-router
{
  "processors": [
    {
      "reroute": {
        "if": "ctx.service?.name == 'payment-service'",
        "dataset": "payment",
        "namespace": "production"
      }
    },
    {
      "reroute": {
        "if": "ctx.service?.name == 'nginx'",
        "dataset": "nginx",
        "namespace": "production"
      }
    }
  ]
}
# Routes to: logs-payment-production, logs-nginx-production
```

### Logs Stream UI Queries (ES|QL)

```sql
-- Find all errors in last hour by service
FROM logs-*-production
| WHERE @timestamp >= NOW() - 1 HOUR
| WHERE log.level == "ERROR"
| STATS count = COUNT(*), 
        services = VALUES(service.name) 
  BY service.name
| SORT count DESC
| LIMIT 20

-- Trace correlated logs
FROM logs-*-production
| WHERE trace.id == "abc123def456"
| SORT @timestamp ASC
| KEEP @timestamp, service.name, log.level, message

-- Error rate trend
FROM logs-*-production
| WHERE @timestamp >= NOW() - 6 HOURS
| STATS 
    total = COUNT(*),
    errors = COUNT(*) WHERE log.level == "ERROR"
  BY BUCKET(@timestamp, 5 minutes)
| EVAL error_rate = errors / total * 100
| SORT `BUCKET(@timestamp, 5 minutes)` ASC
```

## 🔗 Part 4 — APM & Distributed Tracing

### APM Architecture

```
Microservice A              Microservice B              Microservice C
    │                           │                           │
    │ APM Agent                 │ APM Agent                 │ APM Agent
    │ (Java/Python/Node/Go)     │                           │
    └───────────────────────────┴───────────────────────────┘
                                │
                                ▼
                         APM Server :8200
                                │
                                ▼
                         Elasticsearch
                    (traces-apm-*, metrics-apm-*)
                                │
                                ▼
                         Kibana APM UI
                    (Service Map, Traces, Errors)
```

### APM Key Concepts

```
TRACE     → Complete request lifecycle across all services
SPAN      → Single unit of work within a service
TRANSACTION → Entry point span (first span of a trace)
ERROR     → Exception captured with stack trace

Trace ID: unique per request, propagated via HTTP headers
  X-B3-TraceId, traceparent (W3C), elastic-apm-traceparent

Service Map: auto-generated from trace data
  Shows: which services call which, with error rates + latency
```

### APM Agent Configuration (Python Example)

```python
# Install
pip install elastic-apm

# Django settings.py
INSTALLED_APPS = ['elasticapm.contrib.django']

ELASTIC_APM = {
    'SERVICE_NAME': 'payment-service',
    'SECRET_TOKEN': 'your-apm-secret-token',
    'SERVER_URL': 'https://apm-server:8200',
    'ENVIRONMENT': 'production',
    'SERVICE_VERSION': '2.1.4',

    # Capture configuration
    'CAPTURE_HEADERS': True,
    'CAPTURE_BODY': 'errors',   # 'off', 'errors', 'transactions', 'all'
    'TRANSACTION_SAMPLE_RATE': 1.0,   # 1.0 = 100%, 0.1 = 10%
    'SPAN_FRAMES_MIN_DURATION': '5ms',

    # Performance
    'METRICS_INTERVAL': '30s',
    'SERVER_TIMEOUT': '5s',

    # Log correlation
    'LOG_CORRELATION': True,
    'LOG_LEVEL': 'WARNING',
}
```

### APM ES|QL Queries

```sql
-- P99 latency by service (last hour)
FROM traces-apm-*
| WHERE @timestamp >= NOW() - 1 HOUR
| WHERE transaction.type == "request"
| STATS 
    p99 = PERCENTILE(transaction.duration.us, 99),
    count = COUNT(*),
    error_count = COUNT(*) WHERE event.outcome == "failure"
  BY service.name
| EVAL p99_ms = p99 / 1000
| SORT p99_ms DESC

-- Slow transactions with trace correlation
FROM traces-apm-*
| WHERE @timestamp >= NOW() - 1 HOUR
| WHERE transaction.duration.us > 5000000  -- 5 seconds
| KEEP @timestamp, service.name, transaction.name, transaction.duration.us, trace.id
| SORT transaction.duration.us DESC
| LIMIT 20

-- Error rate by endpoint
FROM traces-apm-*
| WHERE @timestamp >= NOW() - 24 HOURS
| WHERE transaction.type == "request"
| STATS
    total = COUNT(*),
    errors = COUNT(*) WHERE event.outcome == "failure"
  BY transaction.name, service.name
| EVAL error_rate = errors / total * 100
| WHERE error_rate > 1
| SORT error_rate DESC
```

## 🌐 Part 5 — OpenTelemetry Integration

### OTel with Elastic

```
OTel Collector → APM Server / ES (OTLP)
OTel SDK → APM Agent compatibility

Why OTel?
  → Vendor-neutral instrumentation
  → One SDK for all observability backends
  → Growing ecosystem + standards

Elastic supports:
  → OTLP (OpenTelemetry Protocol) directly
  → OTel Collector → ES via OTLP exporter
  → Native OTel semantic conventions
```

### OTel Collector Configuration for Elastic

```yaml
# otel-collector.yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318
  
  prometheus:
    config:
      scrape_configs:
        - job_name: 'my-app'
          scrape_interval: 30s
          static_configs:
            - targets: ['my-app:8080']

processors:
  batch:
    timeout: 10s
    send_batch_size: 1000
  
  resource:
    attributes:
      - key: deployment.environment
        value: production
        action: insert

exporters:
  # Send to APM Server (OTLP)
  otlp/elastic:
    endpoint: "https://apm-server:8200"
    headers:
      Authorization: "Bearer your-apm-secret-token"
    tls:
      ca_file: /path/to/ca.crt

  # Send directly to Elasticsearch
  elasticsearch:
    endpoints: ["https://my-es:9200"]
    user: elastic
    password: "${ELASTIC_PASSWORD}"
    logs_index: "otel-logs"
    traces_index: "otel-traces"
    metrics_index: "otel-metrics"

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch, resource]
      exporters: [otlp/elastic]
    
    metrics:
      receivers: [otlp, prometheus]
      processors: [batch]
      exporters: [otlp/elastic]
    
    logs:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp/elastic]
```

## 🔥 Part 6 — Universal Profiling

### What is Universal Profiling?

```
Universal Profiling = continuous system-wide CPU profiling
  → No code instrumentation needed
  → eBPF-based (Linux kernel) — zero overhead
  → Profiles ALL processes on the host
  → Identifies CPU hotspots across entire fleet

Shows:
  → Which function calls consume most CPU
  → Flamegraph: visualizes call stack + time spent
  → Per-service, per-host, per-container breakdown
  → Correlate with APM traces + logs
```

### Deploy Universal Profiling Agent

```bash
# Download profiling host agent
curl -L -O https://artifacts.elastic.co/downloads/beats/elastic-universal-profiling-agent/...

# Install (requires Linux kernel 4.15+ with BPF enabled)
sudo ./pf-host-agent -project-id=my-project \
  -secret-token=your-secret-token \
  -collector-agent-addr=https://fleet-server:8220

# Via Elastic Agent policy (recommended):
# Fleet → Integrations → Universal Profiling Agent

# Requirements:
# ✅ Linux kernel >= 4.15
# ✅ BPF enabled in kernel
# ✅ CAP_SYS_ADMIN or equivalent capability
# ✅ Works with any language (compiled or interpreted)
```

### Universal Profiling Queries

```sql
-- Top CPU consumers
FROM profiling-*
| WHERE @timestamp >= NOW() - 1 HOUR
| STATS cpu_samples = COUNT(*) BY process.name, service.name
| SORT cpu_samples DESC
| LIMIT 20

-- Profiling hotspots by function
FROM profiling-stacktraces
| WHERE @timestamp >= NOW() - 1 HOUR
| STATS count = COUNT(*) BY Stacktrace.frame.function_name
| SORT count DESC
| LIMIT 50
```

## 📏 Part 7 — SLO & SLI

### What Are SLOs?

```
SLI (Service Level Indicator) = metric measuring service health
  Examples: error rate, latency, availability

SLO (Service Level Objective) = target value for an SLI
  Examples: 99.9% requests < 200ms, 99.95% availability

SLA (Service Level Agreement) = business contract based on SLO
  Example: if availability < 99.5% → customer credit

Error Budget = 100% - SLO target
  SLO = 99.9% → Error budget = 0.1% = 43.8 min/month
  When error budget exhausted → pause feature releases
```

### Create SLO in Kibana

```bash
# Via API
POST kbn:/api/observability/slos
{
  "name": "API Error Rate SLO",
  "description": "99.9% of API requests should succeed",
  "indicator": {
    "type": "sli.apm.transactionErrorRate",
    "params": {
      "service": "api-service",
      "environment": "production",
      "transactionType": "request",
      "transactionName": "GET /api/v2/*",
      "index": "metrics-apm.*-*"
    }
  },
  "timeWindow": {
    "duration": "30d",
    "type": "rolling"
  },
  "budgetingMethod": "occurrences",
  "objective": {
    "target": 0.999
  },
  "settings": {
    "syncDelay": "1m",
    "frequency": "1m"
  },
  "tags": ["api", "production", "critical"]
}

# Get SLO status
GET kbn:/api/observability/slos/slo-id

# List all SLOs
GET kbn:/api/observability/slos

# SLO burn rate alert (auto-created with SLO)
# Fast burn: 14.4x burn rate over 1h → page immediately
# Slow burn: 6x burn rate over 6h → page soon
```

### Custom SLO with ES|QL

## 🔔 Part 8 — Alerting

### Alert Types in Kibana

```
STACK RULES:
  → Elasticsearch query rule (ES|QL or DSL)
  → Index threshold rule
  → Metric threshold rule
  → Log threshold rule
  → Anomaly detection rule (ML)

OBSERVABILITY RULES:
  → APM anomaly rule
  → APM error count rule
  → Latency threshold rule
  → Uptime/monitor rule
  → SLO burn rate rule (auto-created)
```

### Create Alert via API

```bash
# Log threshold alert (Kibana alerting API)
POST kbn:/api/alerting/rule
{
  "name": "High Error Rate Alert",
  "rule_type_id": "observability.logs.alert.document.count",
  "consumer": "logs",
  "schedule": { "interval": "1m" },
  "params": {
    "logView": {
      "type": "log-view-reference",
      "logViewId": "default"
    },
    "count": {
      "comparator": "more than",
      "value": 100
    },
    "timeSize": 5,
    "timeUnit": "m",
    "criteria": [
      {
        "field": "log.level",
        "comparator": "equals",
        "value": "ERROR"
      }
    ]
  },
  "actions": [
    {
      "id": "pagerduty-connector-id",
      "group": "threshold met",
      "params": {
        "severity": "critical",
        "eventAction": "trigger",
        "summary": "High error rate detected: {{context.matchingDocuments}} errors in 5 minutes"
      }
    }
  ]
}

# ES|QL-based alert
POST kbn:/api/alerting/rule
{
  "name": "P99 Latency Alert",
  "rule_type_id": "observability.rules.custom_threshold",
  "params": {
    "criteria": [
      {
        "metrics": [
          {
            "name": "p99_latency",
            "aggType": "p99",
            "field": "transaction.duration.us"
          }
        ],
        "comparator": "GT",
        "threshold": [5000000],
        "timeSize": 5,
        "timeUnit": "m"
      }
    ],
    "searchConfiguration": {
      "index": { "title": "traces-apm-*" },
      "query": {
        "language": "kuery",
        "query": "service.name: api-service"
      }
    }
  }
}
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Unstructured logs (plain text) | Can't filter, aggregate, alert | Implement structured JSON logging |
| Not using ECS field names | Integrations break, dashboards wrong | Always use ECS: `log.level`, `service.name` etc |
| 100% trace sampling in production | Storage explosion | Use sampling: 0.1-0.5 for high-traffic services |
| APM agent on wrong version | Compatibility issues | APM agent version = APM server version |
| No trace ID in logs | Can't correlate logs with traces | Enable log correlation in APM agent |
| Storing raw metrics at full resolution forever | Cost explosion | Use downsampling in ILM warm phase |
| Alert on noisy metrics | Alert fatigue | Use anomaly detection not static thresholds |
| SLO on wrong timewindow | Misleading error budget | Match timewindow to business reporting period |
| Fleet server as single point of failure | Agent management down | Deploy 3 Fleet Server instances |
| Not testing OTel collector config | Silent data loss | Test with debug exporter first |

## 💡 Key Principles

```
1. Elastic Agent > individual Beats for new deployments
   → Single agent, Fleet management, 200+ integrations

2. Structured JSON logs are mandatory
   → Unstructured logs = lost observability value

3. ECS field naming everywhere
   → service.name, log.level, trace.id — always ECS

4. Trace sampling strategy matters
   → 100% sampling for < 100 req/s, reduce for high traffic

5. Correlate logs + metrics + traces via trace.id
   → This is the power of the Elastic stack — unified context

6. SLOs are the bridge between tech and business
   → Define SLOs before incidents, not after

7. OTel = vendor-neutral future
   → Instrument with OTel, export to Elastic

8. Alert on SLO burn rate, not individual metrics
   → Burn rate alerts reduce alert fatigue

9. Universal Profiling needs no code changes
   → eBPF captures everything at kernel level

10. Fleet + Policy = centralized agent management
    → Push config changes to thousands of agents in seconds
```
