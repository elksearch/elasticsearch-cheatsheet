## 🧠 Security Architecture — Layers

```
REQUEST FLOW:
Client → [1. Network] → [2. TLS/Transport] → [3. Authentication] → [4. Authorization] → Data

1. NETWORK LAYER
   → Firewall: only expose :9200 to trusted IPs
   → Never expose :9300 (transport port) to public internet

2. TLS/TRANSPORT LAYER
   → HTTP SSL: encrypts client↔ES communication
   → Transport SSL: encrypts node↔node communication
   → Both REQUIRED in production

3. AUTHENTICATION (Who are you?)
   → Native realm (users stored in ES)
   → LDAP/Active Directory realm
   → SAML/OIDC (Kibana SSO)
   → PKI (certificate-based)
   → API Keys

4. AUTHORIZATION (What can you do?)
   → Roles → Privileges → Indices/Fields/Documents
   → Role-Based Access Control (RBAC)
   → Field-Level Security (FLS)
   → Document-Level Security (DLS)
```

## 🔐 Part 1 — TLS Setup

### Enable TLS (Required in Production)

```bash
# Step 1: Generate CA and certificates
bin/elasticsearch-certutil ca --out elastic-stack-ca.p12
bin/elasticsearch-certutil cert --ca elastic-stack-ca.p12 --out elastic-certificates.p12

# For multiple nodes (recommended):
bin/elasticsearch-certutil ca --silent --pem -out ca.zip
unzip ca.zip

# Create instances.yml
cat > instances.yml << EOF
instances:
  - name: es01
    dns: [es01, localhost]
    ip: [127.0.0.1, 10.0.0.1]
  - name: es02
    dns: [es02, localhost]
    ip: [127.0.0.1, 10.0.0.2]
  - name: kibana
    dns: [kibana, localhost]
    ip: [127.0.0.1]
EOF

bin/elasticsearch-certutil cert --silent --pem \
  --in instances.yml --ca-cert ca/ca.crt --ca-key ca/ca.key \
  -out certs.zip

# Step 2: elasticsearch.yml
xpack.security.enabled: true
xpack.security.http.ssl:
  enabled: true
  keystore.path: certs/es01/es01.p12
  truststore.path: certs/ca/ca.p12
xpack.security.transport.ssl:
  enabled: true
  verification_mode: certificate
  keystore.path: certs/es01/es01.p12
  truststore.path: certs/ca/ca.p12

# Step 3: Add to keystore
bin/elasticsearch-keystore add xpack.security.http.ssl.keystore.secure_password
bin/elasticsearch-keystore add xpack.security.transport.ssl.keystore.secure_password
```

### Check TLS Status

```bash
# Verify TLS is active
curl -k https://localhost:9200 -u elastic:password

# Check certificate details
openssl s_client -connect localhost:9200 -showcerts 2>/dev/null | openssl x509 -noout -dates

# Verify transport SSL
GET _nodes?filter_path=nodes.*.transport_address,nodes.*.settings.xpack.security.transport
```

### Built-in Users Overview

```
elastic          → Superuser — full access to everything
kibana_system    → Kibana internal user — manages Kibana indices
logstash_system  → Logstash monitoring user (deprecated — use API keys)
beats_system     → Beats monitoring user (deprecated — use API keys)
apm_system       → APM server internal user

```

### Reset Built-in User Passwords

```bash
# Interactive password reset
bin/elasticsearch-reset-password -u elastic
bin/elasticsearch-reset-password -u kibana_system

# Auto-generate password
bin/elasticsearch-reset-password -u elastic --auto

# Set specific password
bin/elasticsearch-reset-password -u elastic -i
# (then enter password interactively)

# Via API (when cluster is running)
POST _security/user/kibana_system/_password
{
  "password": "NewKibanaPassword123!"
}
```

## 🎭 Part 4 — Roles & Privileges

### Privilege Types

```
CLUSTER PRIVILEGES:
  all                 → everything
  monitor             → read-only cluster monitoring
  manage             → cluster management (no security)
  manage_ilm         → manage ILM policies
  manage_index_templates → manage templates
  manage_ingest_pipelines → manage pipelines
  manage_slm         → manage SLM policies
  read_slm           → read SLM policies
  manage_security    → manage users/roles (not superuser)
  manage_api_key     → manage API keys

INDEX PRIVILEGES:
  all                → everything on index
  read               → search + get documents
  write              → index + update + delete documents
  create             → create new documents only
  create_index       → create new indices
  delete             → delete documents
  delete_index       → delete indices
  manage             → manage index settings/mappings
  manage_ilm         → manage ILM on index
  monitor            → index stats
  view_index_metadata → view mappings/aliases (not data)
  read_cross_cluster → for CCS
```

### Production Role — Logstash Writer

```bash
PUT _security/role/logstash-writer-role
{
  "cluster": [
    "monitor",
    "manage_index_templates",
    "manage_ingest_pipelines",
    "manage_ilm"
  ],
  "indices": [
    {
      "names": ["logs-*", "metrics-*", "traces-*"],
      "privileges": ["write", "create", "create_index", "manage", "manage_ilm"],
      "allow_restricted_indices": false
    }
  ],
  "applications": [],
  "run_as": [],
  "metadata": {
    "description": "Logstash pipeline writer role"
  }
}
```

## 🔒 Part 5 — Field-Level Security (FLS)

### What is FLS?

```
FLS controls which FIELDS a user can see in documents.

Use case:
  logs-payment index has: @timestamp, amount, card_number, user_id, status

  Analyst role → can see: @timestamp, status, user_id
  Analyst role → CANNOT see: amount, card_number  (PII/sensitive)
```

### Grant Specific Fields (Allowlist)

```bash
PUT _security/role/payment-analyst-role
{
  "indices": [
    {
      "names": ["logs-payment-*"],
      "privileges": ["read"],
      "field_security": {
        "grant": [
          "@timestamp",
          "service.*",
          "payment.status",
          "payment.currency",
          "event.*",
          "host.name"
        ]
      }
    }
  ]
}
# User can ONLY see the granted fields
# payment.amount, payment.card_number → NOT visible
```

### Deny Specific Fields (Denylist)

```bash
PUT _security/role/senior-analyst-role
{
  "indices": [
    {
      "names": ["logs-payment-*"],
      "privileges": ["read"],
      "field_security": {
        "grant": ["*"],
        "except": [
          "payment.card_number",
          "payment.cvv",
          "user.ssn",
          "user.password"
        ]
      }
    }
  ]
}
# User can see ALL fields EXCEPT the denied ones
```

### FLS + Wildcard Fields

```bash
# Grant all fields in a nested object
"field_security": {
  "grant": ["@timestamp", "message", "service.*", "host.*"]
}

# Mix grant and except
"field_security": {
  "grant": ["payment.*"],
  "except": ["payment.card_number", "payment.cvv"]
}
```

## 📄 Part 6 — Document-Level Security (DLS)

### What is DLS?

```
DLS controls which DOCUMENTS a user can see.

Use case:
  logs-app index has logs from multiple tenants
  Tenant A → should only see their own logs
  Tenant B → should only see their own logs
  Admin → can see all logs
```

### Basic DLS with Term Query

```bash
PUT _security/role/tenant-a-role
{
  "indices": [
    {
      "names": ["logs-*"],
      "privileges": ["read"],
      "query": {
        "term": {
          "tenant.id": "tenant-a"
        }
      }
    }
  ]
}
```

### DLS with Environment Filter

```bash
PUT _security/role/staging-reader-role
{
  "indices": [
    {
      "names": ["logs-*"],
      "privileges": ["read"],
      "query": {
        "term": {
          "service.environment": "staging"
        }
      }
    }
  ]
}
```

### DLS with Date Range

```bash
PUT _security/role/recent-logs-role
{
  "indices": [
    {
      "names": ["logs-*"],
      "privileges": ["read"],
      "query": {
        "range": {
          "@timestamp": {
            "gte": "now-30d"
          }
        }
      }
    }
  ]
}
```

### DLS with Username Template (Dynamic — Per-User Filter)

```bash
PUT _security/role/own-logs-only-role
{
  "indices": [
    {
      "names": ["logs-*"],
      "privileges": ["read"],
      "query": {
        "template": {
          "source": {
            "term": {
              "user.username": "{{_user.username}}"
            }
          }
        }
      }
    }
  ]
}
# Each user only sees documents where user.username matches their login name
# Dynamic — same role, different filter per user
```

### FLS + DLS Combined

```bash
PUT _security/role/tenant-a-restricted-role
{
  "indices": [
    {
      "names": ["logs-payment-*"],
      "privileges": ["read"],
      "query": {
        "term": { "tenant.id": "tenant-a" }
      },
      "field_security": {
        "grant": ["@timestamp", "service.*", "payment.status"],
        "except": ["payment.card_number", "payment.amount"]
      }
    }
  ]
}
# User sees ONLY tenant-a documents AND ONLY allowed fields
```

## 🔑 Part 7 — API Keys

### What Are API Keys?

```
API Keys = long-lived credentials for programmatic access
  → Better than username/password for services/applications
  → Can be scoped (restricted privileges)
  → Can expire
  → Can be revoked individually
  → Audit trail per key
```

### Create API Key

```bash
# Basic API key (inherits current user's permissions)
POST _security/api_key
{
  "name": "logstash-production-key",
  "expiration": "365d",
  "metadata": {
    "application": "logstash",
    "environment": "production",
    "created_by": "vinay"
  }
}

# Response (SAVE THIS — only shown once!)
# {
#   "id": "abc123",
#   "name": "logstash-production-key",
#   "api_key": "xyz789secret",
#   "encoded": "base64encodedstring=="  ← use this in Authorization header
# }
```

### Create Scoped API Key (Recommended — Least Privilege)

```bash
POST _security/api_key
{
  "name": "filebeat-shipper-key",
  "expiration": "90d",
  "role_descriptors": {
    "filebeat-writer": {
      "cluster": ["monitor", "manage_index_templates", "manage_ingest_pipelines"],
      "indices": [
        {
          "names": ["logs-filebeat-*", "filebeat-*"],
          "privileges": ["write", "create", "create_index", "manage"]
        }
      ]
    }
  },
  "metadata": {
    "host": "prod-server-01",
    "team": "ops"
  }
}
```

### Use API Key in Requests

```bash
# Use encoded value in Authorization header
curl -H "Authorization: ApiKey base64encodedstring==" \
  https://localhost:9200/_cluster/health

# In Logstash output:
output {
  elasticsearch {
    hosts => ["https://es:9200"]
    api_key => "id:api_key_value"
  }
}

# In Filebeat:
output.elasticsearch:
  hosts: ["https://es:9200"]
  api_key: "id:api_key_value"
```

### Manage API Keys

```bash
# Get API key info (by id)
GET _security/api_key?id=abc123

# Get all API keys for current user
GET _security/api_key?owner=true

# Get all API keys (requires manage_api_key privilege)
GET _security/api_key

# Get by name
GET _security/api_key?name=logstash-production-key

# Invalidate (revoke) specific key
DELETE _security/api_key
{
  "ids": ["abc123"]
}

# Invalidate all keys for a user
DELETE _security/api_key
{
  "username": "logstash-writer"
}

# Invalidate all keys with specific name
DELETE _security/api_key
{
  "name": "old-key"
}

# Update API key (extend expiry, change metadata)
PUT _security/api_key/abc123
{
  "metadata": {
    "environment": "production",
    "renewed": "2026-04-29"
  }
}
```

## 📊 Part 8 — Audit Logging

### Enable Audit Logging

```yaml
# elasticsearch.yml
xpack.security.audit.enabled: true

# Events to audit (choose carefully — high volume!)
xpack.security.audit.logfile.events.include:
  - access_denied
  - access_granted
  - anonymous_access_denied
  - authentication_failed
  - connection_denied
  - tampered_request
  - run_as_denied
  - run_as_granted

# Exclude noisy events
xpack.security.audit.logfile.events.exclude:
  - access_granted   # very noisy — every successful request logged

# Filter by index (only audit sensitive indices)
xpack.security.audit.logfile.events.include: ["access_denied", "authentication_failed"]
xpack.security.audit.logfile.emit_node_name: true
xpack.security.audit.logfile.emit_node_id: true
```

### Audit Log Format

```json
{
  "@timestamp": "2026-04-29T10:30:00.000Z",
  "event.type": "access_denied",
  "event.action": "indices:data/read/search",
  "user.name": "analyst-vinay",
  "user.roles": ["logs-analyst-role"],
  "request.id": "abc123",
  "network.client.ip": "10.0.0.5",
  "url.path": "/logs-payment-*/_search",
  "request.method": "GET"
}
```

## ❌ Part 10 — Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Using `elastic` superuser for applications | One compromised app = full breach | Create scoped service users + API keys |
| Passwords in config files / code | Credentials exposure | Use keystore, env vars, secrets manager |
| No TLS on HTTP | Data in cleartext on network | Always enable `xpack.security.http.ssl` |
| No TLS on transport | Node-to-node data exposed | Always enable `xpack.security.transport.ssl` |
| Using `*` index privilege for analysts | Analysts can read all data | Restrict to specific index patterns |
| No field-level security on PII | PII accessible to all users | Always add FLS for sensitive fields |
| API keys never expire | Stale keys if stolen = long-lived breach | Always set expiration on API keys |
| Sharing API keys across services | Can't revoke one without breaking others | One API key per service/host |
| Not auditing `access_denied` events | Security incidents invisible | Always audit denied events |
| Not testing DLS/FLS after role change | Assumed security may be broken | Always verify with `_has_privileges` |
| Hardcoding credentials in Logstash/Beats config | Exposed in version control | Use keystore or env vars |

## 💡 Key Principles — Summary

```
1. Never use elastic superuser for applications
   → Create scoped service users with minimum required privileges

2. API Keys over passwords for programmatic access
   → Scoped, expirable, revocable individually

3. One API key per service per host
   → Granular revocation without blast radius

4. FLS for all PII fields
   → payment.card_number, user.ssn, user.password always excluded

5. DLS for multi-tenant data
   → Same index, different views per tenant/user

6. TLS everywhere — HTTP and transport
   → No plaintext data on wire ever

7. Audit denied events always
   → access_denied + authentication_failed minimum

8. Test security after every role change
   → POST _security/user/_has_privileges

9. Disable unused built-in users
   → logstash_system, beats_system — use API keys instead

10. Credentials never in config files or code
    → Elasticsearch keystore / Vault / AWS Secrets Manager
```
