## 🧠 Part 1 — How Elasticsearch Search Works Internally

```
QUERY EXECUTION PHASES:

Phase 1: QUERY PHASE (scatter)
  Coordinator node receives query
  → Broadcasts to all relevant shards (primary OR replica)
  → Each shard searches locally, returns top-N doc IDs + scores
  → Coordinator collects results from all shards

Phase 2: FETCH PHASE (gather)
  Coordinator has final sorted list of doc IDs
  → Fetches actual document sources from their shards
  → Merges, returns to client

WHY THIS MATTERS:
  Aggregations run during QUERY phase (on all shards)
  _source is fetched in FETCH phase (only top-N docs)
  → size: 0 skips fetch phase entirely → much faster
```

### Inverted Index — Core Data Structure

```
TEXT: "Elasticsearch is fast and reliable"

INVERTED INDEX:
  "elasticsearch" → [doc_1, doc_5, doc_23]
  "fast"          → [doc_1, doc_8, doc_15]
  "reliable"      → [doc_1, doc_3]
  "is"            → (stopword — ignored)
  "and"           → (stopword — ignored)

WHEN SEARCHING for "fast elasticsearch":
  1. Tokenize query: ["fast", "elasticsearch"]
  2. Look up each term in inverted index
  3. Find docs containing both (intersection): [doc_1]
  4. Score doc_1 using BM25
  5. Return scored results
```

### Text Analysis Pipeline

```
Raw text: "The QUICK brown Fox JUMPED over the lazy dog."
                    │
                    ▼ Character Filter (optional)
                    │  → e.g., strip HTML
                    │
                    ▼ Tokenizer
                    │  → splits into tokens: ["The","QUICK","brown","Fox","JUMPED","over","the","lazy","dog"]
                    │
                    ▼ Token Filters (chain)
                    │  → lowercase:   ["the","quick","brown","fox","jumped","over","the","lazy","dog"]
                    │  → stop words:  ["quick","brown","fox","jumped","lazy","dog"]
                    │  → stemming:    ["quick","brown","fox","jump","lazi","dog"]
                    │
                    ▼ Stored in Inverted Index
                    "quick" → [doc_1]
                    "brown" → [doc_1]
                    "jump"  → [doc_1]   ← "jumped" becomes "jump" after stemming
```

## 📐 Part 2 — BM25 Scoring Algorithm

### What is BM25?

```
BM25 (Best Match 25) = Elasticsearch's default relevance scoring algorithm
Replaced TF-IDF in ES 5.0

Score = Σ IDF(term) × TF_norm(term, document)

Two components:
  IDF = Inverse Document Frequency (how rare/important is this term?)
  TF  = Term Frequency (how often does this term appear in the doc?)
```

### IDF — Inverse Document Frequency

```
IDF measures term RARITY across ALL documents in an index.

Formula:
  IDF = log(1 + (N - df + 0.5) / (df + 0.5))

Where:
  N  = total number of documents in index
  df = number of documents containing this term

Intuition:
  "elasticsearch" appears in 10 of 1,000,000 docs → HIGH IDF (rare term, high weight)
  "error"         appears in 800,000 of 1,000,000 docs → LOW IDF (common term, low weight)
  "the"           appears in 999,999 of 1,000,000 docs → VERY LOW IDF (stopword)

Key insight:
  IDF is calculated PER SHARD (not across all shards!)
  → Results can differ between shards if data is unevenly distributed
  → Use dfs_query_then_fetch for accurate IDF across all shards
```

### TF — Term Frequency (BM25 Normalized)

```
BM25 TF_norm = tf × (k1 + 1) / (tf + k1 × (1 - b + b × fieldLen/avgFieldLen))

Where:
  tf        = raw count of term in document
  k1        = term saturation parameter (default: 1.2)
  b         = field length normalization (default: 0.75)
  fieldLen  = length of this field in this document
  avgFieldLen = average field length across all documents

k1 effect (saturation):
  BM25: repeated terms give DIMINISHING returns
  k1=0: TF doesn't matter at all
  k1=1.2: diminishing returns kick in after ~2-3 occurrences (default)
  k1=100: almost linear TF (like old TF-IDF)

b effect (field length normalization):
  b=0: field length doesn't matter
  b=1: fully normalize by field length
  b=0.75: balance (default) — shorter docs ranked slightly higher
  
  Why? A doc saying "elasticsearch" once in 3 words
       is more relevant than saying it once in 3000 words
```

### BM25 Parameters — Tuning

```bash
# Change BM25 parameters per field (in mapping)
PUT my-index
{
  "settings": {
    "similarity": {
      "my_bm25": {
        "type": "BM25",
        "k1": 1.5,
        "b": 0.75,
        "discount_overlaps": true
      }
    }
  },
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "similarity": "my_bm25"
      },
      "body": {
        "type": "text",
        "similarity": "BM25"
      }
    }
  }
}

# When to tune k1:
#   Increase k1 (>1.2): when term frequency matters more (long product descriptions)
#   Decrease k1 (<1.2): when you want more diversity in results

# When to tune b:
#   Increase b (>0.75): penalize long docs more (short precise answers desired)
#   Decrease b (<0.75): field length doesn't matter much (all docs similar length)
#   b=0: completely disable length normalization
```

## 🔍 Part 3 — Query vs Filter Context

### The Critical Difference

```
QUERY CONTEXT → Calculates relevance score
  → "How well does this document match?"
  → Results are scored and sorted by _score
  → NOT cached
  → Use for: full-text search, relevance ranking

FILTER CONTEXT → Binary yes/no
  → "Does this document match?"
  → No score calculated → faster
  → Results ARE cached (filter cache)
  → Use for: date ranges, term matches, numeric ranges, geo filters
```

```bash
# CORRECT: Query context for full-text, filter for structured
GET logs-nginx-production/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "message": "connection timeout"
          }
        }
      ],
      "filter": [
        { "term": { "log.level": "ERROR" } },
        { "range": { "@timestamp": { "gte": "now-1h" } } },
        { "term": { "service.name": "api-service" } }
      ]
    }
  }
}

# The filter clauses are:
# ✅ Cached
# ✅ No score impact
# ✅ Applied BEFORE scoring (reduces docs to score)
# The must clause → scores remaining documents
```

## ⚡ Part 5 — Query Types & When to Use Each

### Match Queries (full-text)

```bash
# match: standard full-text search (analyzed)
GET logs-nginx-production/_search
{
  "query": {
    "match": {
      "message": {
        "query": "connection timeout error",
        "operator": "and",
        "fuzziness": "AUTO",
        "minimum_should_match": "75%",
        "boost": 1.5
      }
    }
  }
}

# match_phrase: exact phrase (terms in order)
{
  "match_phrase": {
    "message": {
      "query": "connection refused",
      "slop": 2
    }
  }
}
# slop: how many positions terms can be shifted

# match_phrase_prefix: autocomplete-style (last term = prefix)
{
  "match_phrase_prefix": {
    "message": "connection time"
  }
}

# multi_match: search multiple fields
{
  "multi_match": {
    "query": "elasticsearch timeout",
    "fields": ["message^2", "error.message", "log.logger"],
    "type": "best_fields",
    "tie_breaker": 0.3
  }
}
# ^2 = boost message field 2x
# tie_breaker: how much secondary field matches contribute

# multi_match types:
# best_fields: score from best matching field (default)
# most_fields: score combined from all matching fields
# cross_fields: treat all fields as one big field
# phrase: phrase match across fields
# phrase_prefix: phrase prefix across fields
```

### Term Queries (exact/structured — use in filter context)

```bash
# term: exact keyword match (not analyzed!)
{ "term": { "status": { "value": "active", "boost": 2.0 } } }

# terms: match any of these values
{ "terms": { "log.level": ["ERROR", "WARN"] } }

# terms lookup (from another index)
{
  "terms": {
    "user.id": {
      "index": "vip-users",
      "id": "1",
      "path": "user_ids"
    }
  }
}

# range: numeric/date ranges
{
  "range": {
    "@timestamp": {
      "gte": "now-1h",
      "lte": "now",
      "boost": 1.0
    }
  }
}

# exists: document has field
{ "exists": { "field": "error.message" } }

# ids: specific document IDs
{ "ids": { "values": ["1", "2", "3"] } }

# prefix: starts with (keyword field only!)
{ "prefix": { "url.path": "/api/v2" } }

# wildcard: glob pattern (slow — avoid in production)
{ "wildcard": { "url.path": { "value": "/api/*/payment", "boost": 1.0 } } }

# regexp: regex (very slow — avoid in production)
{ "regexp": { "url.path": ".*payment.*" } }

# fuzzy: typo-tolerant exact match
{ "fuzzy": { "service.name": { "value": "apii-servise", "fuzziness": "AUTO" } } }
```

### Bool Query (combine queries)

```bash
GET logs-nginx-production/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "message": "timeout" } }
      ],
      "should": [
        { "match": { "message": "connection" } },
        { "term":  { "service.name": "api-service" } }
      ],
      "filter": [
        { "term":  { "log.level": "ERROR" } },
        { "range": { "@timestamp": { "gte": "now-1h" } } }
      ],
      "must_not": [
        { "term": { "service.environment": "staging" } }
      ],
      "minimum_should_match": 1,
      "boost": 1.0
    }
  }
}

# must:     MUST match + contributes to score
# should:   SHOULD match + contributes to score (optional unless min_should_match set)
# filter:   MUST match + NO score (cached, fast)
# must_not: MUST NOT match + NO score
```

## 🚀 Part 6 — Boosting & Relevance Tuning

### Field-Level Boosting

```bash
# Boost at index time (permanent — affects IDF too)
PUT my-index/_mapping
{
  "properties": {
    "title": { "type": "text", "boost": 2.0 }
  }
}
# Note: index-time boost is deprecated — use query-time boost instead

# Boost at query time (preferred)
{
  "multi_match": {
    "query": "elasticsearch performance",
    "fields": [
      "title^3",
      "description^2",
      "body^1"
    ]
  }
}
```

### Function Score Query (custom scoring logic)

```bash
GET logs-nginx-production/_search
{
  "query": {
    "function_score": {
      "query": {
        "match": { "message": "connection timeout" }
      },
      "functions": [
        {
          "gauss": {
            "@timestamp": {
              "origin": "now",
              "scale": "1h",
              "offset": "10m",
              "decay": 0.5
            }
          },
          "weight": 2
        },
        {
          "filter": { "term": { "service.name": "payment-service" } },
          "weight": 3
        },
        {
          "field_value_factor": {
            "field": "http.response.body.bytes",
            "factor": 0.001,
            "modifier": "log1p",
            "missing": 1
          }
        }
      ],
      "score_mode": "sum",
      "boost_mode": "multiply",
      "max_boost": 10
    }
  }
}

# score_mode: how to combine function scores
#   multiply, sum, avg, first, max, min

# boost_mode: how to combine function score with query score
#   multiply (default), replace, sum, avg, max, min

# Decay functions: gauss, exp, linear
#   origin: "center" of decay
#   scale:  distance where score = decay value
#   offset: no decay within this range
#   decay:  score at scale distance (default 0.5 = half score)
```

### Script Score (fully custom)

```bash
GET logs-nginx-production/_search
{
  "query": {
    "script_score": {
      "query": {
        "match": { "message": "timeout" }
      },
      "script": {
        "source": """
          double score = _score;
          
          // Boost recent documents
          long ageMs = new Date().getTime() - doc['@timestamp'].value.getMillis();
          double ageDays = ageMs / 86400000.0;
          double recencyBoost = Math.exp(-0.1 * ageDays);
          
          // Boost errors from critical services
          if (doc['service.name'].value == 'payment-service') {
            score *= 3.0;
          }
          
          return score * recencyBoost;
        """
      }
    }
  }
}
```

```bash

      "ids": ["critical-doc-1", "critical-doc-2"],
```

## ⚙️ Part 7 — Search Performance Optimization

### Query Optimization

```bash
# 1. Filter before scoring (use filter context)
# BAD:
{ "must": [{ "term": { "status": "active" } }, { "match": { "message": "error" } }] }
# GOOD:
{ "must": [{ "match": { "message": "error" } }], "filter": [{ "term": { "status": "active" } }] }

# 2. Avoid leading wildcards
# BAD: (requires full index scan)
{ "wildcard": { "url.path": "*payment*" } }
# GOOD: (uses inverted index)
{ "match": { "url.path": "payment" } }

# 3. Use keyword for exact matching
# BAD: (analyzed field for exact match)
{ "match": { "service.name": "api-service" } }
# GOOD: (keyword field, cached)
{ "term": { "service.name": "api-service" } }

# 4. Prefer filter over query for structured data
# BAD: (calculates score for date range)
{ "must": [{ "range": { "@timestamp": { "gte": "now-1h" } } }] }
# GOOD: (cached, no score)
{ "filter": [{ "range": { "@timestamp": { "gte": "now-1h" } } }] }
```

### Index Optimization for Search

```bash
# 1. Force merge old/read-only indices (fewer segments = faster search)
POST old-logs-2024.01._forcemerge?max_num_segments=1
# Note: CPU intensive — only on read-only indices

# 2. Disable _source for pure log aggregation indices (saves disk, NOT for recovery)
PUT _index_template/agg-only-template
{
  "template": {
    "mappings": {
      "_source": { "enabled": false }
    }
  }
}

# 3. Use doc_values for sorting/agg (already default for keyword/numeric)
# Disable for fields you never sort/agg on:
{
  "properties": {
    "full_log_line": { "type": "text", "doc_values": false }
  }
}

# 4. Index only what you need to search
# If you only aggregate on a field — disable index (full-text)
{
  "properties": {
    "metrics.value": { "type": "double", "index": false }
  }
}

# 5. Warm up the shard (pre-load field data)
GET _cat/indices
# After restore/forcemerge, run representative queries to warm OS cache
```

### Request Caching

```bash
# Request cache caches aggregation results of size: 0 queries
# Auto-enabled when:
# 1. size: 0
# 2. Query uses "now" with rounding (now/d, not now-1h exactly)

# Check cache stats
GET _cat/nodes?v&h=name,query_cache.memory_size,query_cache.hit_count,query_cache.miss_count

GET _nodes/stats/indices/request_cache

# Invalidated automatically on index refresh
# Can manually clear:
POST _cache/clear?request=true
```

### DFS Query Then Fetch (accurate IDF)

```bash
# Problem: IDF calculated per-shard → scores can be inconsistent
# across shards with different document distributions

# Solution: dfs_query_then_fetch (extra round-trip to collect global IDF)
GET logs-nginx-production/_search?search_type=dfs_query_then_fetch
{
  "query": { "match": { "message": "timeout" } }
}

# When to use:
#   Small indices with uneven shard distribution
#   When relevance accuracy matters more than speed
#   When number of shards is large and data is uneven

# When NOT to use:
#   Large indices with well-distributed data (IDF will be accurate anyway)
#   Logging/analytics use cases (relevance less critical)
```

## ❌ Part 9 — Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Date range in must (not filter) | Score calculated for dates (wasteful) | Move to filter context |
| Wildcard on text field | Full index scan, very slow | Use match query or map as keyword |
| Term query on text field | Never matches (text is analyzed, term is not) | Use match or .keyword subfield |
| Not understanding IDF per-shard | Inconsistent relevance in small indices | Use dfs_query_then_fetch |
| Ignoring filter caching | Repeated expensive filters | Use filter context for reused conditions |
| High `from` + `size` for pagination | Deep pagination = memory + time | Use search_after instead |
| Aggressive fuzzy on all queries | Slow + irrelevant results | Only fuzzy on specific fields, use AUTO |
| High `minimum_should_match` | Misses relevant docs | Tune based on query quality |
| Script in query context on all docs | Very slow — no index usage | Pre-compute values at index time |
| Not using explain to debug | Guessing at relevance issues | Always use _explain when scores seem wrong |

## 💡 Key Principles — Summary

```
1. BM25 = IDF × TF_normalized
   → IDF rewards rare terms, TF has diminishing returns

2. Query context = score, Filter context = cache
   → ALWAYS put date ranges, term filters in filter context

3. BM25 IDF is per-shard, not global
   → Small indices with uneven distribution → use dfs_query_then_fetch

4. Text fields are analyzed, keyword fields are not
   → term query on text field = never matches
   → match query on keyword field = analyzed query vs exact stored value

5. Explain is your best friend for scoring issues
   → GET index/_explain/ID always before optimizing

6. Wildcards and scripts = full index scans
   → Avoid in production, use match/term instead

7. search_after > scroll > from+size for pagination
   → from+size is O(n) — gets worse as pages get deeper

8. Force merge read-only indices
   → 1 segment per shard = maximum search speed

9. Field length normalization (b=0.75)
   → Short exact matches rank higher than long docs with same term count

10. Boost strategically — not everywhere
    → Boosting everything = boosting nothing
    → Use function_score for business logic (recency, popularity, tier)
```
