## Cross Cluster Search (CCS) & Cross Cluster Replication (CCR)
### Multi-Cluster Architecture, Setup, Use Cases, Production Patterns

> CCS and CCR solve two different problems in multi-cluster Elasticsearch.
> CCS = Search across multiple clusters simultaneously.
> CCR = Replicate indices from one cluster to another.
> Together they power geo-distributed, high-availability, multi-tenant architectures.

## 🧠 CCS vs CCR — Know The Difference

```
CROSS CLUSTER SEARCH (CCS):
  ┌──────────┐     search query      ┌──────────┐
  │ Cluster A│ ───────────────────▶  │ Cluster B│
  │ (local)  │ ◀───────────────────  │ (remote) │
  └──────────┘    merged results     └──────────┘

  → Data STAYS in each cluster
  → Query runs on both, coordinator merges results
  → No data movement — just query federation
  → Use case: search across regions, environments, tenants

CROSS CLUSTER REPLICATION (CCR):
  ┌──────────┐    replicate index    ┌──────────┐
  │ Cluster A│ ───────────────────▶  │ Cluster B│
  │ (leader) │                       │(follower)│
  └──────────┘                       └──────────┘

  → Data IS COPIED to follower cluster
  → Follower index is READ-ONLY replica
  → Near real-time replication (sub-second lag)
  → Use case: DR, geo-distribution, local read offloading
```

## 🔍 Part 1 — Cross Cluster Search (CCS)

### Architecture

```
         User/Kibana Query: "search logs-* on all clusters"
                    │
                    ▼
        ┌───────────────────────┐
        │   Coordinating Node   │  ← local cluster (cluster-mumbai)
        │   (query coordinator) │
        └───────────┬───────────┘
                    │
          ┌─────────┼─────────┐
          │         │         │
          ▼         ▼         ▼
    ┌──────────┐ ┌──────────┐ ┌──────────┐
    │cluster-  │ │cluster-  │ │cluster-  │
    │mumbai    │ │singapore │ │london    │
    │(local)   │ │(remote)  │ │(remote)  │
    └──────────┘ └──────────┘ └──────────┘
          │         │         │
          └─────────┼─────────┘
                    │
                    ▼
           Merged & Sorted Results
                returned to user
```

### Configure Remote Clusters (Two Methods)

#### Method 1: Static Configuration (elasticsearch.yml) — Simple

```yaml
# On the LOCAL cluster (the one that will search)
# elasticsearch.yml
cluster.remote:
  cluster-singapore:
    seeds:
      - "singapore-node1:9300"
      - "singapore-node2:9300"
    transport.ping_schedule: "30s"
    transport.compress: true
    skip_unavailable: true

  cluster-london:
    seeds:
      - "london-node1:9300"
    skip_unavailable: true
```

#### Method 2: Dynamic Configuration (API) — Recommended for Production

```bash
# Add remote cluster via API (no restart needed!)
PUT _cluster/settings
{
  "persistent": {
    "cluster.remote.cluster-singapore": {
      "seeds": [
        "singapore-node1:9300",
        "singapore-node2:9300",
        "singapore-node3:9300"
      ],
      "transport.ping_schedule": "30s",
      "transport.compress": true,
      "skip_unavailable": true,
      "transport.initial_connect_timeout": "30s"
    },
    "cluster.remote.cluster-london": {
      "seeds": ["london-node1:9300"],
      "skip_unavailable": true
    }
  }
}
```

#### Method 3: Proxy Mode (for cloud/Kubernetes — no direct transport access)

```bash
PUT _cluster/settings
{
  "persistent": {
    "cluster.remote.cluster-singapore": {
      "mode": "proxy",
      "proxy_address": "singapore-proxy.mycompany.com:9300",
      "proxy_socket_connections": 18,
      "server_name": "singapore.mycompany.com"
    }
  }
}
```

### CCS Queries

```bash
# Search local + all remote clusters
GET *:logs-*,logs-*/_search
{
  "query": {
    "match": { "level": "ERROR" }
  }
}

# Search specific remote cluster only
GET cluster-singapore:logs-nginx-production/_search
{
  "query": { "match_all": {} }
}

# Search two specific remote clusters
GET cluster-singapore:logs-*,cluster-london:logs-*/_search
{
  "query": {
    "range": {
      "@timestamp": { "gte": "now-1h" }
    }
  }
}

# Search ALL remotes + local with aggregation
GET *:logs-*,logs-*/_search
{
  "size": 0,
  "aggs": {
    "by_cluster": {
      "terms": {
        "field": "_index",
        "size": 20
      }
    },
    "errors_by_region": {
      "filter": { "term": { "log.level": "ERROR" } },
      "aggs": {
        "count": { "value_count": { "field": "@timestamp" } }
      }
    }
  }
}
```

### CCS with minimize_roundtrips

```bash
# Default: 2 roundtrips (DFS + query+fetch)
# minimize_roundtrips=true: 1 roundtrip (faster for small result sets)
GET cluster-singapore:logs-*/_search?ccs_minimize_roundtrips=true
{
  "size": 10,
  "query": { "match": { "level": "ERROR" } }
}

# minimize_roundtrips=false: better for scroll/aggregations
GET *:logs-*/_search?ccs_minimize_roundtrips=false
{
  "size": 0,
  "aggs": { "count": { "value_count": { "field": "@timestamp" } } }
}
```

### Identify Which Cluster Results Come From

```bash
GET *:logs-*,logs-*/_search
{
  "query": { "match": { "level": "ERROR" } }
}

# Response includes:
# hits._index = "cluster-singapore:logs-nginx-production"
#            OR ".ds-logs-nginx-production-2026.04.27-000001" (local)
# _clusters.total = 3
# _clusters.successful = 3
# _clusters.skipped = 0
```

### CCS Security Setup

```bash
# On REMOTE cluster: create role for CCS access
PUT _security/role/ccs-reader-role
{
  "cluster": ["read_cross_cluster"],
  "indices": [
    {
      "names": ["logs-*", "metrics-*"],
      "privileges": ["read", "read_cross_cluster", "view_index_metadata"]
    }
  ]
}

# Create user on remote cluster
POST _security/user/ccs-service-user
{
  "password": "CcsPassword123!",
  "roles": ["ccs-reader-role"]
}

# On LOCAL cluster: add remote cluster with credentials
PUT _cluster/settings
{
  "persistent": {
    "cluster.remote.cluster-singapore": {
      "seeds": ["singapore-node1:9300"],
      "skip_unavailable": true
    }
  }
}
```

### skip_unavailable — Critical Setting

```bash
# skip_unavailable: true  → if remote is down, query still returns local results
# skip_unavailable: false → if remote is down, ENTIRE query fails

# Production: always true for non-critical remotes
# Exception: when you need ALL cluster data (compliance, billing)

PUT _cluster/settings
{
  "persistent": {
    "cluster.remote.cluster-singapore.skip_unavailable": true
  }
}
```

## 🔄 Part 2 — Cross Cluster Replication (CCR)

### Architecture

```
LEADER CLUSTER                      FOLLOWER CLUSTER
(source — writes happen here)       (destination — reads only)

┌─────────────────────┐             ┌─────────────────────┐
│  logs-nginx-prod    │  replicate  │  logs-nginx-prod    │
│  (write index)      │ ──────────▶ │  (read-only copy)   │
│                     │             │                      │
│  .ds-logs-nginx-    │  replicate  │  .ds-logs-nginx-    │
│  prod-000001        │ ──────────▶ │  prod-000001        │
│  .ds-logs-nginx-    │  replicate  │  .ds-logs-nginx-    │
│  prod-000002        │ ──────────▶ │  prod-000002        │
└─────────────────────┘             └─────────────────────┘

  Mumbai (ap-south-1)                 Singapore (ap-southeast-1)
  PRIMARY                             DR / LOCAL READ
```

### CCR Use Cases

```
1. DISASTER RECOVERY
   Primary: Mumbai cluster
   Replica: Singapore cluster
   On failover: promote follower to leader

2. GEO-DISTRIBUTED READ
   Global app → users read from nearest cluster
   Writes always go to primary → replicated to all regions

3. REPORTING / ANALYTICS OFFLOAD
   Production cluster: writes + real-time queries
   Analytics cluster: follower reads, heavy aggregations
   → Protects production from analytics queries

4. DEV/STAGING FROM PRODUCTION DATA
   Production: leader
   Staging: follower (read-only production data)
```

### Prerequisites for CCR

```bash
# 1. License: CCR requires Platinum or Enterprise license
GET _license

# 2. Remote cluster must be configured first
GET _remote/info

# 3. Leader index must exist
GET logs-nginx-production

# 4. Follower cluster must connect to leader
# (configure remote cluster on FOLLOWER cluster pointing to LEADER)
```

### Configure Remote Cluster on Follower

```bash
# Run this on the FOLLOWER cluster
PUT _cluster/settings
{
  "persistent": {
    "cluster.remote.leader-mumbai": {
      "seeds": ["mumbai-node1:9300", "mumbai-node2:9300"],
      "skip_unavailable": false
    }
  }
}

# Verify connection
GET _remote/info
```

### Create Follower Index (Manual)

```bash
# Run on FOLLOWER cluster
PUT /logs-nginx-production/_ccr/follow
{
  "remote_cluster": "leader-mumbai",
  "leader_index": "logs-nginx-production",
  "settings": {
    "index.number_of_replicas": 1
  },
  "max_read_request_operation_count": 5120,
  "max_outstanding_read_requests": 12,
  "max_read_request_size": "32mb",
  "max_write_request_operation_count": 5120,
  "max_write_request_size": "9223372036854775807b",
  "max_outstanding_write_requests": 9,
  "max_write_buffer_count": 2147483647,
  "max_write_buffer_size": "512mb",
  "max_retry_delay": "500ms",
  "read_poll_timeout": "1m"
}
```

### Auto-Follow Patterns (Most Important for Data Streams!)

```bash
# Without auto-follow: each new rollover creates new backing index
# which you'd have to manually set up as follower
# Auto-follow: automatically follows new indices matching a pattern

PUT _ccr/auto_follow/logs-auto-follow
{
  "remote_cluster": "leader-mumbai",
  "leader_index_patterns": [
    "logs-*",
    ".ds-logs-*"
  ],
  "leader_index_exclusion_patterns": [
    ".ds-logs-audit-*"
  ],
  "follow_index_pattern": "{{leader_index}}",
  "settings": {
    "index.number_of_replicas": 1
  },
  "max_read_request_operation_count": 5120,
  "max_outstanding_read_requests": 12
}
```

### Monitor CCR Status

```bash
# Overall CCR stats
GET _ccr/stats

# Specific follower index stats
GET logs-nginx-production/_ccr/stats

# Response shows:
# leader_global_checkpoint
# follower_global_checkpoint
# leader_max_seq_no
# follower_max_seq_no
# operations_received
# bytes_read
# failed_read_requests
# failed_write_requests
# lag: (leader - follower checkpoint = replication lag)

# Check auto-follow patterns
GET _ccr/auto_follow

# Check specific pattern
GET _ccr/auto_follow/logs-auto-follow

# Follower index status
GET logs-nginx-production/_ccr/info
```

### Pause & Resume Replication

```bash
# Pause (e.g., during maintenance)
POST logs-nginx-production/_ccr/pause_follow

# Resume
POST logs-nginx-production/_ccr/resume_follow
{
  "max_read_request_operation_count": 5120,
  "max_outstanding_read_requests": 12
}

# Pause auto-follow pattern
POST _ccr/auto_follow/logs-auto-follow/pause

# Resume auto-follow pattern
POST _ccr/auto_follow/logs-auto-follow/resume
```

### Unfollow (Promote Follower to Regular Index)

```bash
# Step 1: Pause replication
POST logs-nginx-production/_ccr/pause_follow

# Step 2: Close follower index
POST logs-nginx-production/_close

# Step 3: Unfollow (converts to regular writable index)
POST logs-nginx-production/_ccr/unfollow

# Step 4: Re-open index
POST logs-nginx-production/_open

# Index is now a regular writable index — DR promotion complete!
```

## 🏭 Part 3 — Production Patterns

### Pattern 1: Active-Passive DR Setup

```
Normal operation:
  All writes → Mumbai (primary)
  Mumbai → Singapore (follower via CCR)
  All reads → Mumbai (or via CCS from Singapore)

DR scenario (Mumbai down):
  Step 1: Unfollow all indices on Singapore
  Step 2: Point applications to Singapore
  Step 3: Singapore becomes primary
  Step 4: When Mumbai recovers → it becomes the follower
```

```bash
# DR Runbook — Mumbai cluster down

# On Singapore cluster:
# Step 1: Unfollow all follower indices
POST logs-nginx-production/_ccr/pause_follow
POST logs-nginx-production/_close
POST logs-nginx-production/_ccr/unfollow
POST logs-nginx-production/_open

# Repeat for all indices (or script it)
for index in logs-nginx-production logs-api-production logs-payment-production; do
  POST ${index}/_ccr/pause_follow
  POST ${index}/_close
  POST ${index}/_ccr/unfollow
  POST ${index}/_open
done

# Step 2: Verify all indices are writable
GET logs-nginx-production
# blocks.write should be null

# Step 3: Update DNS/load balancer to point to Singapore
# Step 4: Applications resume writing to Singapore
```

### Pattern 2: Geo-Distributed Reads

```
Write path: All writes → US-East (primary)

US-East      → CCR →    EU-West
US-East      → CCR →    AP-South

Read path:
  US users   → read from US-East (local)
  EU users   → read from EU-West (local)
  AP users   → read from AP-South (local)
  → Sub-millisecond local reads vs 200ms cross-region reads
```

### Pattern 3: Analytics Offload

```bash
# Production cluster: handles writes + real-time queries
# Analytics cluster: follower, handles heavy aggregations

# Set up auto-follow on analytics cluster
PUT _ccr/auto_follow/production-data
{
  "remote_cluster": "production",
  "leader_index_patterns": ["logs-*", "metrics-*"],
  "follow_index_pattern": "analytics-{{leader_index}}"
}

# Now analytics cluster has all production data as read-only
# Run heavy aggregations here without impacting production
GET analytics-logs-nginx-production/_search
{
  "size": 0,
  "aggs": {
    "hourly_errors": {
      "date_histogram": {
        "field": "@timestamp",
        "calendar_interval": "hour"
      },
      "aggs": {
        "error_count": {
          "filter": { "term": { "log.level": "ERROR" } }
        }
      }
    }
  }
}
```

## 🔐 Part 4 — Security for CCS & CCR

### CCS Security — TLS Required

```bash
# Remote cluster connection uses transport port (9300)
# TLS must be enabled on transport layer

# Leader cluster must trust follower's CA (and vice versa)
# Add remote CA to each cluster's truststore

# Option 1: Same CA for all clusters (simplest)
# Option 2: Cross-trust different CAs
```

### CCR Security — Leader Index Privileges

```bash
# On LEADER cluster: create role for follower access
PUT _security/role/ccr-leader-role
{
  "cluster": ["read_ccr"],
  "indices": [
    {
      "names": ["logs-*", "metrics-*"],
      "privileges": [
        "monitor",
        "read",
        "read_cross_cluster",
        "view_index_metadata"
      ]
    }
  ]
}

# Create user on leader cluster
POST _security/user/ccr-follower-user
{
  "password": "CcrPassword123!",
  "roles": ["ccr-leader-role"]
}

# On FOLLOWER cluster: create role for managing CCR
PUT _security/role/ccr-follower-role
{
  "cluster": ["manage_ccr"],
  "indices": [
    {
      "names": ["logs-*", "metrics-*"],
      "privileges": ["monitor", "read", "write", "manage_follow_index"]
    }
  ]
}
```

## ❌ Part 5 — Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| `skip_unavailable: false` for all remotes | Query fails if any remote is down | Use `true` unless 100% consistency required |
| Not configuring remote cluster before CCS query | Query fails | `PUT _cluster/settings` first, verify with `GET _remote/info` |
| Forgetting `read_cross_cluster` privilege on remote | CCS permission denied | Add to remote cluster role |
| Manual follower index creation for data streams | New backing indices not replicated | Always use auto-follow patterns for data streams |
| Unfollow without pausing first | Data inconsistency | Always pause → close → unfollow → open |
| CCR without Platinum license | CCR APIs unavailable | Check `GET _license` before planning CCR |
| No monitoring of replication lag | Silent data loss risk | Set up alerting on `follower_global_checkpoint` lag |
| Using CCS for write operations | Writes only go to local cluster | CCS is READ-ONLY — writes always go to local |
| Different Elasticsearch versions on leader/follower | CCR may fail | Leader version must be ≤ follower version |
| Not testing DR failover procedure | False confidence in DR | Run quarterly DR drills |


## 💡 Key Principles — Summary

```
1. CCS = federated search (data stays put)
   CCR = data replication (data is copied)
   → Use CCS for query federation, CCR for DR/geo-distribution

2. skip_unavailable: true in production CCS
   → Partial results > failed queries when remote is down

3. Auto-follow patterns for data streams
   → Manual follower creation misses new rollover indices

4. Always: pause → close → unfollow → open
   → Never unfollow a running follower directly

5. CCR lag = leader_global_checkpoint - follower_global_checkpoint
   → Alert when lag > threshold (your RPO requirement)

6. CCS is read-only
   → Writes always go to local cluster

7. Test DR failover quarterly
   → Document the runbook, practice it

8. TLS on transport is required for both CCS and CCR
   → Not optional — clusters won't connect without it

9. Different use cases for each pattern:
   → DR: CCR active-passive
   → Analytics offload: CCR with separate analytics cluster
   → Multi-region search: CCS across regions
   → Local reads: CCR with geo-distribution

10. Version compatibility: leader ≤ follower
    → Upgrade follower first, then leader
```
