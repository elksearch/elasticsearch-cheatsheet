## ✅ Part 1 — Production Readiness Checklist

### Infrastructure

```
HARDWARE:
  □ Hot nodes: NVMe SSD (local DAS, never NAS)
  □ Warm nodes: SSD or fast HDD
  □ RAM: heap = 50% of RAM, max 30GB
  □ CPU: 16+ cores for data nodes
  □ Network: 10Gbps between nodes
  □ 3 dedicated master nodes (odd number)
  □ Multi-AZ deployment for HA

OS:
  □ vm.max_map_count = 262144 (permanent)
  □ swapoff -a (swap disabled)
  □ ulimit nofile = 65535
  □ ulimit nproc = 4096
  □ Transparent huge pages disabled
  □ noatime mount option for data disk
  □ I/O scheduler: noop/deadline for SSDs
  □ NTP synchronized on all nodes

JVM:
  □ Xms = Xmx (prevent heap resizing)
  □ Max heap: 30GB (G1GC default is fine for 9.x)
  □ GC logging enabled
  □ Heap dumps on OOM enabled (-XX:+HeapDumpOnOutOfMemoryError)
```

### Elasticsearch Configuration

```
SECURITY:
  □ xpack.security.enabled = true
  □ TLS on HTTP layer (xpack.security.http.ssl)
  □ TLS on transport layer (xpack.security.transport.ssl)
  □ No default passwords (changed from defaults)
  □ elastic superuser NOT used by applications
  □ Audit logging enabled (at minimum: access_denied, auth_failed)
  □ API keys for all service accounts (not passwords)
  □ Network access restricted (firewall rules)

CLUSTER:
  □ cluster.name set (unique per environment)
  □ node.name set (unique per node)
  □ discovery.seed_hosts set correctly
  □ cluster.initial_master_nodes set (bootstrap only)
  □ node.roles explicitly set (not default all-in-one)
  □ path.data on correct volume
  □ path.logs on separate volume from data

PERFORMANCE:
  □ indices.memory.index_buffer_size = 30% (write-heavy clusters)
  □ bootstrap.memory_lock = true
  □ thread_pool.write.queue_size tuned
  □ Disk watermarks configured
  □ Network host set correctly (not localhost in production)

INDICES:
  □ ILM policies for all index patterns
  □ Index templates for all data streams
  □ Shard count: 1 shard per 20-50 GB
  □ Replica count: minimum 1 for HA
  □ total_fields.limit set explicitly
  □ No dynamic: true on unknown field patterns
```

### Operations

```
BACKUP & RECOVERY:
  □ Snapshot repository configured (S3/GCS)
  □ SLM policy: daily snapshots minimum
  □ Snapshot restore tested (quarterly)
  □ Cross-region snapshot copy for DR
  □ RTO/RPO documented and tested

MONITORING:
  □ Separate monitoring cluster
  □ Stack Monitoring or AutoOps enabled
  □ Alerting configured:
     → Cluster RED/YELLOW
     → Disk > 85%
     → Heap > 75%
     → CPU > 90% sustained
     → Indexing rejections
     → ILM errors
  □ Runbook for each alert

CAPACITY:
  □ 6-month capacity projection done
  □ Disk growth alerts at 70%, 80%, 90%
  □ Shard budget calculated
  □ Cost projection reviewed monthly

UPGRADES:
  □ Upgrade procedure documented
  □ Tested in staging first
  □ Rollback plan exists
  □ Breaking changes reviewed
```

## 🎯 Part 2 — Interview Questions & Answers

### Category 1: Architecture & Fundamentals

**Q: What happens when you index a document in Elasticsearch?**

```
Answer:
1. Client sends request to any node (coordinating node)
2. Coordinating node determines target primary shard:
   shard = hash(document_id) % number_of_shards
3. Request forwarded to node holding primary shard
4. Primary shard:
   a. Writes to in-memory buffer
   b. Writes to translog (WAL on disk) for durability
   c. Sends to replica shards in parallel
5. After replicas acknowledge → success returned to client
6. On refresh (default 1s): buffer converted to Lucene segment (searchable)
7. On flush (translog full/timeout): segment fsynced to disk, translog cleared
```

**Q: What is the difference between refresh and flush?**

```
Refresh:
  → Converts in-memory buffer to in-memory Lucene segment
  → Makes documents SEARCHABLE
  → Does NOT write to disk (not durable)
  → Default: every 1 second
  → Cost: medium (creates segments)

Flush:
  → Writes in-memory segments to DISK (fsync)
  → Clears the translog
  → Makes data DURABLE (survives crash)
  → Default: when translog reaches 512MB or 30 min
  → Cost: high (I/O intensive)

Key point: After refresh, document is searchable but could be lost on crash.
After flush, document is on disk and safe.
```

**Q: What is a split-brain and how does Elasticsearch prevent it?**

```
Split-brain: Two parts of a cluster each elect their own master
→ Both sides accept writes
→ Data diverges
→ Merging is impossible without data loss

Prevention (pre ES 7.x):
  discovery.zen.minimum_master_nodes = (N/2) + 1
  Where N = number of master-eligible nodes

Prevention (ES 7.x+ — current):
  Raft-based consensus algorithm
  → Requires majority (quorum) to elect master
  → 3 master-eligible nodes → quorum = 2
  → Split: each side has 1 node → neither has quorum → no master elected
  → Only one side can have majority → only one master

Always use ODD number of masters:
  3 masters → quorum = 2 → can lose 1
  5 masters → quorum = 3 → can lose 2
```

**Q: How does Elasticsearch score documents? Explain BM25.**

```
BM25 (Best Match 25) = default similarity algorithm

Score = Σ IDF(term) × TF_norm(term, document)

IDF (Inverse Document Frequency):
  → Measures term RARITY across all documents
  → Common terms ("the", "is") → low IDF → low weight
  → Rare terms ("elasticsearch") → high IDF → high weight
  → Formula: log(1 + (N - df + 0.5) / (df + 0.5))
  → N = total docs, df = docs containing term

TF_norm (Normalized Term Frequency):
  → Measures how often term appears in THIS document
  → With diminishing returns (BM25 vs TF-IDF)
  → Normalized by field length (shorter docs rank higher for same term)
  → k1 (default 1.2): controls saturation
  → b (default 0.75): controls length normalization

KEY POINT: BM25 IDF is calculated per-shard, not globally
→ Use dfs_query_then_fetch for accurate IDF across all shards
```

### Category 2: Performance & Optimization

**Q: A cluster is experiencing high indexing latency. How do you diagnose?**

```
Step 1: Check thread pool rejections
  GET _cat/thread_pool?v&h=name,active,rejected,queue&s=rejected:desc

Step 2: Check indexing pressure
  GET _nodes/stats/indexing_pressure

Step 3: Check disk I/O
  GET _nodes/stats/fs
  Check: io_stats.total.write_operations
  High write ops = disk saturation

Step 4: Check JVM
  GET _nodes/stats/jvm
  High old GC = heap pressure → memory issue

Step 5: Check hot threads
  GET _nodes/hot_threads

Step 6: Check merge stats
  GET _nodes/stats/indices/merges
  High merge time = too many segments

Root causes and fixes:
  Rejections → reduce bulk rate, increase queue_size (temp)
  Disk I/O → upgrade to NVMe SSD, reduce shard count
  GC pressure → increase heap (max 30GB), fix memory leak
  Too many merges → increase refresh_interval during bulk load
  Too many replicas → set replicas=0 during bulk, restore after
```

**Q: How would you optimize a slow aggregation query?**

```
Step 1: Profile the query
  GET index/_search { "profile": true, "aggs": {...} }
  → Identify which aggregation takes most time

Step 2: Check if filter context is used
  Move date ranges, term filters to "filter" context
  → Filter cached, aggregation runs on smaller set

Step 3: Check shard_size for terms aggregation
  → Increase shard_size for accuracy
  → Default shard_size = size * 1.5 + 10

Step 4: Consider composite aggregation
  → For high-cardinality multi-field grouping
  → Paginate instead of loading all buckets

Step 5: Use request cache
  → Round "now" to now/m or now/h
  → Use size: 0
  → Same query = cache hit after first execution

Step 6: Forcemerge old read-only indices
  → 1 segment per shard = fastest aggregation
  → POST old-index/_forcemerge?max_num_segments=1

Step 7: Pre-compute with transforms
  → For repeated expensive aggregations → run once, store results
```

**Q: What is the recommended shard size and why?**

```
Recommendation: 10 GB to 50 GB per shard

WHY:
  Too small (< 1 GB):
    → Master node overhead per shard (metadata, routing)
    → Network overhead (too many shards to query)
    → GC pressure (many small segments)

  Too large (> 50 GB):
    → Long recovery time when node fails
    → Slow search (large segment tree)
    → Cannot shrink if needed

  Sweet spot (10-50 GB):
    → Fast recovery (< 30 min typically)
    → Good search performance
    → Manageable master overhead

ILM rollover trigger:
  max_primary_shard_size: 50gb ← recommended

Formula:
  number_of_shards = ceil(expected_size_gb / 50)
  Example: 300 GB index → 6 shards
```

### Category 3: Data Modeling & Mappings

**Q: When should you use nested vs object field type?**

```
Use OBJECT when:
  → Single object (not array of objects)
  → Don't need to query combinations within same object
  → Performance critical (object queries faster)
  → Example: user.address = single address

Use NESTED when:
  → Array of objects
  → Need to query "tag X has weight 5" (not just "has tag X AND weight 5")
  → Order of fields within objects matters
  → Example: order.items = [{product: "ES", qty: 1}, {product: "Kibana", qty: 2}]

PERFORMANCE NOTE:
  Each nested object = separate hidden Lucene document
  100 nested objects = 101 documents stored
  Nested updates = full re-index of parent document
  → Use nested only when relationship query is required
```

**Q: What is mapping explosion and how do you prevent it?**

```
Mapping explosion = too many fields in mapping
  → Master node OOM (stores all mappings in memory)
  → Error: "Limit of total fields [1000] in index exceeded"

Common causes:
  → Dynamic mapping on user-generated keys
  → JSON logs with random field names
  → Metrics with label explosion

Prevention:
  1. Set total_fields.limit explicitly
     index.mapping.total_fields.limit: 2000

  2. Use flattened type for dynamic key-value data
     "labels": { "type": "flattened" }

  3. Use dynamic: false for catch-all objects
     "metadata": { "type": "object", "dynamic": false }

  4. Use dynamic: strict at index level
     prevents all unmapped fields (documents rejected)

  5. Runtime fields instead of mapping new fields
     → Computed at query time, not stored in mapping
```

**Q: Explain the difference between query and filter context.**

```
QUERY CONTEXT:
  → Calculates relevance score
  → Results sorted by _score (how well they match)
  → NOT cached
  → Use for: full-text search, relevance ranking
  → Example: "how relevant is this doc to 'connection timeout'?"

FILTER CONTEXT:
  → Binary yes/no (does it match or not)
  → No score calculation → faster
  → Results ARE cached (query cache)
  → Use for: structured data filtering
  → Example: "is log.level == ERROR?"

PRACTICAL RULE:
  Full-text match → must (query context)
  Date ranges → filter context
  Term/keyword → filter context
  Geo filters → filter context

# RIGHT:
{
  "query": {
    "bool": {
      "must": [{ "match": { "message": "timeout" } }],
      "filter": [{ "term": { "log.level": "ERROR" } }, { "range": { "@timestamp": {...} } }]
    }
  }
}
```

### Category 4: Operations & Troubleshooting

**Q: Cluster is RED. What steps do you take?**

```
STEP 1: Assess impact
  GET _cluster/health?pretty
  → Which indices are RED?
  GET _cluster/health?level=indices

STEP 2: Find unassigned shards
  GET _cat/shards?v&h=index,shard,prirep,state,node&s=state
  → Look for UNASSIGNED primary shards (prirep=p)

STEP 3: Understand WHY
  GET _cluster/allocation/explain
  → "no_valid_shard_copy" = node with data is gone
  → "disk_exceeded" = disk watermark
  → "max_retries_exceeded" = failed too many times

STEP 4: Fix based on cause
  a. Retry allocation:
     POST _cluster/reroute?retry_failed=true

  b. Disk issue:
     Free disk space or increase watermark temporarily

  c. Node gone permanently (DATA LOSS RISK):
     POST _cluster/reroute
     { "commands": [{ "allocate_stale_primary": { ... "accept_data_loss": true } }] }

STEP 5: Re-enable allocation
  PUT _cluster/settings
  { "persistent": { "cluster.routing.allocation.enable": "all" } }

STEP 6: Monitor recovery
  GET _cat/recovery?v&active_only=true
```

**Q: How do you perform a zero-downtime reindex?**

```
Scenario: Need to change a field type (e.g., string → integer)
Old index: logs-nginx-v1
New mapping needed: http.response.status_code as integer (was keyword)

STEP 1: Create new index with correct mapping
  PUT logs-nginx-v2 { "mappings": { "properties": { ... correct mapping ... } } }

STEP 2: Set up alias on old index (if not already)
  POST _aliases { "actions": [{ "add": { "index": "logs-nginx-v1", "alias": "logs-nginx" } }] }

STEP 3: Reindex async
  POST _reindex?wait_for_completion=false
  { "source": { "index": "logs-nginx-v1" }, "dest": { "index": "logs-nginx-v2" } }
  → Keep old index active during reindex

STEP 4: Monitor reindex
  GET _tasks?actions=*reindex

STEP 5: Verify counts match
  GET logs-nginx-v1/_count
  GET logs-nginx-v2/_count

STEP 6: Switch alias atomically
  POST _aliases
  {
    "actions": [
      { "remove": { "index": "logs-nginx-v1", "alias": "logs-nginx" } },
      { "add": { "index": "logs-nginx-v2", "alias": "logs-nginx" } }
    ]
  }
  → Zero downtime: switch happens in milliseconds

STEP 7: Verify and clean up
  GET logs-nginx/_search { "size": 1 }
  DELETE logs-nginx-v1
```

**Q: What is the hot-warm-cold architecture and when do you use it?**

```
HOT-WARM-COLD architecture = tiered storage for time-series data

HOT TIER:
  → Active indexing + frequent reads
  → Hardware: NVMe SSD, high RAM, high CPU
  → Memory:data ratio: 1:30
  → ILM: data stays 0-7 days

WARM TIER:
  → No active indexing, occasional reads
  → Hardware: SSD or HDD, less RAM
  → Memory:data ratio: 1:100-160
  → ILM: data stays 7-30 days
  → Operations: forcemerge to 1 segment, shrink to 1 shard

COLD TIER:
  → Rare reads (compliance, audit)
  → Hardware: cheap storage
  → Often: searchable snapshots (data stays in S3)
  → Memory:data ratio: 1:500+

WHEN TO USE:
  ✅ Time-series data (logs, metrics, traces)
  ✅ When query frequency decreases with age
  ✅ When storage cost is a concern
  ✅ When retention > 30 days

COST IMPACT (real numbers):
  All-hot (90 TB):      $28,000/month
  Hot+Warm+Cold+Frozen: $3,300/month (88% saving!)
```

### Category 5: Advanced Topics

**Q: How does Cross-Cluster Search work?**

```
CCS = federated search across multiple ES clusters

HOW IT WORKS:
  1. Configure remote clusters on local cluster:
     PUT _cluster/settings
     { "persistent": { "cluster.remote.remote-cluster": { "seeds": ["node:9300"] } } }

  2. Search using cluster prefix:
     GET remote-cluster:logs-*,logs-*/_search

  3. Execution:
     a. Local coordinating node receives query
     b. Sends query to remote cluster's coordinating node
     c. Remote cluster executes locally, returns top-N results
     d. Local coordinator merges all results
     e. Returns sorted, merged results to client

KEY CONCEPTS:
  → Data stays in each cluster (not copied)
  → Query runs in parallel across all clusters
  → skip_unavailable: true → partial results if remote is down
  → ccs_minimize_roundtrips: true/false → tradeoff speed vs accuracy

USE CASES:
  → Search across prod + staging environments
  → Multi-region search (users search nearest + global)
  → Multi-tenant with per-cluster isolation
  → Federated search across business units
```

**Q: Explain the difference between Elastic Agent and Beats.**

```
BEATS (older approach):
  → Single-purpose lightweight shippers
  → Filebeat: logs, Metricbeat: metrics, Packetbeat: network, etc.
  → Each configured separately via YAML
  → Updates require restarting each Beat
  → No central management

ELASTIC AGENT (newer approach):
  → Single agent replaces ALL Beats
  → Centrally managed via Fleet (Kibana UI)
  → Policy-based configuration (push config to agents)
  → Auto-updates via Fleet
  → 200+ built-in integrations
  → Tamper protection

RECOMMENDATION:
  → New deployments: always Elastic Agent
  → Existing Beats: migrate when convenient
  → Both coexist fine during transition

WHEN BEATS STILL MAKES SENSE:
  → Very constrained environments (tiny footprint)
  → Air-gapped without Fleet infrastructure
  → Legacy systems with existing Beats configuration
```

**Q: What is ELSER and how does it differ from dense vector search?**

```
ELSER (Elastic Learned Sparse EncodeR):
  → Elastic's semantic search model
  → Output: SPARSE vector (token weights)
  → No dimensions limit
  → More efficient than dense vectors
  → Better OOV (out-of-vocabulary) handling
  → Good for English text search

Dense Vector (e.g., E5, OpenAI embeddings):
  → Output: DENSE vector (fixed dimensions, e.g., 384)
  → Requires HNSW index
  → Universal (works for any content type)
  → Better for multilingual
  → Larger storage footprint

ELSER vs Dense:
  ELSER:  "connection timeout" matches "server not responding" → semantic
  Dense:  "connection timeout" close to "network issue" in vector space

HYBRID SEARCH (Best):
  RRF retriever combining:
  → BM25 (exact keyword matches)
  → ELSER/Dense (semantic matches)
  → Neither misses important results

WHEN TO USE ELSER:
  ✅ English enterprise search
  ✅ No GPU available (sparse = CPU efficient)
  ✅ Simple setup (no model training)

WHEN TO USE DENSE:
  ✅ Multilingual content
  ✅ Image/audio embeddings
  ✅ Custom fine-tuned models
  ✅ When cosine similarity is needed
```

## 📋 Part 3 — Scenario-Based Questions

**Q: You need to ingest 100 TB of historical data into a new cluster. How do you approach this?**

```
APPROACH:

1. PRE-INGEST SETUP:
   → Set replicas = 0 (no replication overhead)
   → Set refresh_interval = -1 (no refreshes during load)
   → Set translog.durability = async
   → Increase translog.flush_threshold_size = 1gb
   → Use index.codec = best_compression

2. INGEST STRATEGY:
   → Use Reindex API if source is Elasticsearch
   → Use custom Logstash/Spark job for external data
   → Bulk requests: 5-15 MB per request
   → 4-8 parallel bulk threads
   → Auto-generated IDs (no _id lookup)

3. MONITOR:
   → GET _cat/thread_pool?v → watch for rejections
   → GET _nodes/stats/indices/indexing → throughput
   → GET _nodes/stats/jvm → heap pressure

4. POST-INGEST:
   → Restore replicas = 1
   → Restore refresh_interval = 1s
   → Force merge: POST index/_forcemerge?max_num_segments=1
   → Wait for green before serving traffic

EXPECTED THROUGHPUT:
  6 hot nodes, NVMe SSD → 50-100 GB/hour
  100 TB → 1,000-2,000 hours → 40-80 days
  Use parallelism: 4-8 concurrent reindex processes → 10-20 days
```

## 💡 Key Principles (Final Summary)

```
ARCHITECTURE:
  1. 3 dedicated master nodes, always odd number
  2. Separate node roles: hot, warm, cold, frozen, ML, ingest, coordinating
  3. Zone/rack awareness for HA
  4. Local SSD (DAS) for hot tier — never NAS

PERFORMANCE:
  5. Heap = 50% RAM, max 30GB, Xms = Xmx
  6. Bulk API for all writes, 5-15 MB per request
  7. Filter context for structured data (cached)
  8. Forcemerge read-only indices to 1 segment

DATA:
  9. ILM for all indices — nothing unmanaged
  10. Shard size: 10-50 GB sweet spot
  11. ECS field names everywhere
  12. Mappings: text + keyword multi-field standard

OPERATIONS:
  13. Snapshots before ANY major operation
  14. Test upgrades in staging first
  15. Monitor: heap, disk, GC, rejections — always

SECURITY:
  16. TLS on HTTP and transport — always
  17. No elastic superuser in applications
  18. API keys over passwords for services
  19. DLS for multi-tenant data isolation

COST:
  20. Hot-warm-cold-frozen = 90% storage cost reduction
```
