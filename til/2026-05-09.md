## Elasticsearch Upgrade Guide
### Rolling Upgrade, Full Restart, Version Compatibility, Deprecation API, ECK Upgrade

> Upgrading Elasticsearch is one of the highest-risk operations in cluster management.
> Done right: zero downtime, no data loss. Done wrong: cluster RED, data corruption.
> This document covers every step, every check, every gotcha.

## 🧠 Core Upgrade Concepts

```
VERSION NUMBERING: Major.Minor.Patch
  8.x.y → 9.x.y = MAJOR (breaking changes possible)
  8.15.x → 8.16.x = MINOR (new features, compatible)
  8.15.1 → 8.15.2 = PATCH (bug fixes, fully compatible)

UPGRADE PATHS:
  ✅ One minor version at a time (8.15 → 8.16 → 9.0)
  ✅ Skip patch versions within same minor (8.15.1 → 8.15.5)
  ❌ Skip minor versions (8.15 → 9.0 directly — NOT supported)
  ❌ Downgrade (not supported — snapshot restore only)

INDEX COMPATIBILITY:
  Each major version can read indices created in previous MAJOR only
  ES 9.x reads: indices created in 8.x and 9.x
  ES 9.x CANNOT read: indices created in 7.x or older
  → Reindex old indices BEFORE upgrading

TWO UPGRADE METHODS:
  Rolling Upgrade → one node at a time, zero downtime
  Full Cluster Restart → all nodes stop, then restart → brief downtime
```

## 📋 Part 1 — Pre-Upgrade Checklist

### Step 1: Read Breaking Changes

```bash
# ALWAYS read breaking changes for target version
# URL: https://www.elastic.co/guide/en/elasticsearch/reference/[VERSION]/breaking-changes.html

# Key things to look for:
# - Removed settings
# - Changed defaults
# - Renamed fields
# - Removed APIs
# - Index compatibility changes
```

### Step 2: Check Deprecations

```bash
# Check ALL deprecations in current cluster (must fix before upgrade)
GET _migration/deprecations

# Response structure:
# {
#   "cluster_settings": [...],   ← cluster-level deprecated settings
#   "node_settings": [...],      ← node-level deprecated settings
#   "index_settings": {...},     ← per-index deprecated settings
#   "ml_settings": [...]         ← ML deprecated settings
# }

# Check specific index deprecations
GET /my-index/_migration/deprecations

# Check specific type
GET _migration/deprecations?include_defaults=true
```

### Step 3: Check Index Compatibility

```bash
# Find indices created before previous major version (too old to upgrade)
GET _cat/indices?v&h=index,creation.date.string,version.created&s=version.created

# OR check via field:
GET _all/_settings?filter_path=**.version.created

# Indices created in ES 7.x or older CANNOT be read by ES 9.x
# Must reindex these BEFORE upgrading to 9.x

# Check index version (format: major*1000000 + minor*10000 + patch)
# 7.17.0 = 7 * 1000000 + 17 * 10000 + 0 = 7170000
# If version.created starts with 7 → MUST reindex before upgrading to 9.x
```

### Step 4: Take a Snapshot

```bash
# MANDATORY before any upgrade
PUT _snapshot/s3-repo/pre-upgrade-snapshot-8.16.5
{
  "indices": "*",
  "include_global_state": true,
  "metadata": {
    "reason": "pre-upgrade-backup",
    "from_version": "8.16.5",
    "to_version": "9.0.2"
  }
}

# Wait for completion
GET _snapshot/s3-repo/pre-upgrade-snapshot-8.16.5

# Verify snapshot is SUCCESS before proceeding
```

### Step 5: Check Cluster Health

```bash
# Cluster must be GREEN before upgrade
GET _cluster/health?pretty

# No unassigned shards allowed
GET _cat/shards?v&h=index,shard,prirep,state&s=state | grep UNASSIGNED

# No pending tasks
GET _cluster/pending_tasks

# Check node versions (all should be same version)
GET _cat/nodes?v&h=name,version,node.role&s=name
```

### Step 6: Check Keystore & Security

```bash
# Verify keystore is consistent across all nodes
# All nodes should have same credentials

# Check existing security settings
GET _cluster/settings?filter_path=**.security
GET _nodes?filter_path=nodes.*.settings.xpack.security

# Verify enrollment tokens still valid (ECK)
# Verify API keys still work after upgrade
```

## 🔄 Part 2 — Rolling Upgrade (Zero Downtime)

### When to Use Rolling Upgrade

```
Rolling upgrade: ONE NODE AT A TIME
  ✅ Zero downtime
  ✅ Cluster stays available throughout
  ✅ Supported for: minor version upgrades (8.15 → 8.16)
  ✅ Supported for: major version upgrades IF no breaking changes affect you
  ⚠️  Takes longer (must wait for each node to rejoin)
  ⚠️  Mixed version cluster during upgrade (supported for one minor version)
```

### Rolling Upgrade Procedure

```bash
# STEP 1: Disable shard allocation
# (prevents ES from moving shards while node is offline)
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": "primaries"
  }
}
# "primaries" = only primary shard allocation (replicas wait)

# STEP 2: Perform a synced flush (ES < 7.6 only, deprecated after)
POST _flush/synced

# STEP 3: Stop the first node
# On the node:
sudo systemctl stop elasticsearch

# OR gracefully:
curl -X POST "localhost:9200/_cluster/nodes/_local/_shutdown"

# STEP 4: Upgrade the node
# Debian/Ubuntu:
sudo apt-get install elasticsearch=9.0.2

# RPM/RHEL:
sudo yum install elasticsearch-9.0.2

# Tar:
# Download new version, extract, copy config files, update paths

# STEP 5: Start upgraded node
sudo systemctl start elasticsearch

# Wait for node to join cluster
GET _cat/nodes?v&s=name
# Wait until upgraded node appears

# STEP 6: Re-enable shard allocation
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": "all"
  }
}

# STEP 7: Wait for cluster to turn GREEN
GET _cluster/health?wait_for_status=green&timeout=300s

# STEP 8: Repeat for next node
# IMPORTANT: Complete steps 1-7 for each node before moving to next
```

### Rolling Upgrade Order (Important!)

```
CORRECT ORDER:
  1. ML nodes (first — ML is backward compatible)
  2. Data nodes (warm, cold, frozen first — less critical)
  3. Data nodes (hot)
  4. Coordinating nodes
  5. Ingest nodes
  6. Master-eligible nodes (LAST — most critical)

WHY MASTERS LAST?
  → Upgraded master manages the cluster state
  → If upgraded master is elected prematurely → incompatibility
  → Keep old master until all data nodes are upgraded
```

### Verify After Each Node

```bash
# After each node upgrade, verify before proceeding:
GET _cluster/health?pretty
# Must be: status: "green"

GET _cat/nodes?v&h=name,version&s=name
# Mixed versions is expected during rolling upgrade

GET _cat/shards?v&h=state&s=state | grep -c STARTED
# All shards should be STARTED

GET _cat/recovery?v&active_only=true
# Wait for any recovery to complete before next node
```

## 🔃 Part 3 — Full Cluster Restart Upgrade

### When to Use Full Cluster Restart

```
Full cluster restart: ALL NODES STOP, then restart
  ✅ Required for: major version with breaking changes
  ✅ Simpler procedure (no mixed-version complexity)
  ✅ Faster than rolling upgrade for small clusters
  ❌ Downtime required (minutes to hours depending on cluster size)
  ❌ Not suitable for 24/7 availability requirements
```

### Full Cluster Restart Procedure

```bash
# STEP 1: Disable shard allocation
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": "none"
  }
}

# STEP 2: Flush all indices
POST _flush

# STEP 3: Stop all nodes simultaneously
# On each node:
sudo systemctl stop elasticsearch

# STEP 4: Upgrade all nodes
# Upgrade packages on ALL nodes (same version!)

# STEP 5: Update configuration files if needed
# Review elasticsearch.yml, jvm.options for deprecated settings

# STEP 6: Start master-eligible nodes FIRST
sudo systemctl start elasticsearch  # on master nodes only

# Wait for cluster to form (masters elect new master)
GET _cluster/health?wait_for_status=yellow&timeout=300s

# STEP 7: Start data nodes
sudo systemctl start elasticsearch  # on data nodes

# STEP 8: Start remaining nodes (ingest, coordinating, ML)
sudo systemctl start elasticsearch

# STEP 9: Re-enable shard allocation
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": "all"
  }
}

# STEP 10: Monitor recovery
GET _cluster/health?wait_for_status=green&timeout=600s
GET _cat/recovery?v&active_only=true
```

## 🗄️ Part 4 — Reindexing Old Indices

### Which Indices Need Reindexing?

```bash
# ES 9.x cannot read indices created in ES 7.x or older
# Check index creation version:
GET _all/_settings?filter_path=**.version.created

# If version.created < 8000000 (8.0.0) → MUST reindex before upgrading to 9.x

# Find all old indices:
GET _cat/indices?v&h=index,creation.date.string&s=creation.date
# Look at creation dates — pre-2022 indices may be ES 7.x
```

### Reindex Old Indices Before Upgrade

```bash
# Step 1: Create new index with fresh mapping
PUT my-old-index-reindexed
{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 1
  },
  "mappings": {
    "properties": {
      "@timestamp": { "type": "date" },
      "message": { "type": "text" }
    }
  }
}

# Step 2: Reindex (async for large indices)
POST _reindex?wait_for_completion=false&slices=auto
{
  "source": {
    "index": "my-old-index",
    "size": 5000
  },
  "dest": {
    "index": "my-old-index-reindexed"
  }
}
# Get task ID from response

# Step 3: Monitor reindex
GET _tasks/TASK_ID

# Step 4: Verify counts match
GET my-old-index/_count
GET my-old-index-reindexed/_count

# Step 5: Switch alias
POST _aliases
{
  "actions": [
    { "remove": { "index": "my-old-index",           "alias": "my-alias" } },
    { "add":    { "index": "my-old-index-reindexed", "alias": "my-alias" } }
  ]
}

# Step 6: Delete old index
DELETE my-old-index
```

## ☸️ Part 5 — ECK (Kubernetes) Upgrade

### ECK Operator Upgrade

```bash
# Step 1: Check current ECK version
kubectl get deployment elastic-operator -n elastic-system -o jsonpath='{.spec.template.spec.containers[0].image}'

# Step 2: Upgrade ECK operator (Helm)
helm upgrade elastic-operator elastic/eck-operator \
  --namespace elastic-system \
  --version 2.14.0 \
  --reuse-values

# Step 3: Verify operator is running
kubectl get pods -n elastic-system
kubectl logs -n elastic-system -l control-plane=elastic-operator

# Check ECK operator version
kubectl get deployment elastic-operator -n elastic-system -o jsonpath='{.spec.template.spec.containers[0].image}'
```

### ECK Elasticsearch Cluster Upgrade

```yaml
# ECK handles rolling upgrades automatically
# Just update the version field:
apiVersion: elasticsearch.k8s.elastic.co/v1
kind: Elasticsearch
metadata:
  name: production-es
spec:
  version: 9.0.2     # ← change from 8.16.5 to 9.0.2
  # ECK will automatically perform rolling upgrade
  # Each node upgraded one at a time
  # Monitors health between each node
```

```bash
# Apply the change
kubectl apply -f elasticsearch.yaml

# Monitor upgrade progress
kubectl get elasticsearch production-es -w

# Watch pods being restarted
kubectl get pods -l elasticsearch.k8s.elastic.co/cluster-name=production-es -w

# Check upgrade status
kubectl describe elasticsearch production-es

# View operator logs during upgrade
kubectl logs -n elastic-system -l control-plane=elastic-operator -f

# ES|QL to check node versions during rolling upgrade
GET _cat/nodes?v&h=name,version&s=name
```

## 🔧 Part 6 — Post-Upgrade Tasks

### Verify Upgrade Success

```bash
# Check all nodes on new version
GET _cat/nodes?v&h=name,version&s=name

# Cluster health GREEN
GET _cluster/health?pretty

# Run deprecation check on new version
GET _migration/deprecations

# Check ILM is running
GET _ilm/status

# Check SLM is running
GET _slm/status

# Verify APM and Fleet still working
# Kibana → Stack Management → Upgrade Assistant

# Run representative search queries
GET logs-nginx-production/_search { "size": 1 }

# Check index templates still valid
GET _index_template

# Verify ILM policies
GET _ilm/policy
```

### Update Clients & Agents

```bash
# After ES upgrade, update:
# 1. Kibana (must match ES major.minor version)
sudo apt-get install kibana=9.0.2

# 2. Logstash (one major version behind is OK)
sudo apt-get install logstash=9.0.2

# 3. Elastic Agent (update via Fleet policy)
# Fleet → Agent policies → Update to 9.0.2

# 4. Beats (update via package manager)
sudo apt-get install filebeat=9.0.2
sudo apt-get install metricbeat=9.0.2

# 5. APM clients (check compatibility matrix)
# Java: elastic-apm-agent-*.jar → update to latest 9.x compatible

# VERSION COMPATIBILITY RULE:
# Kibana must match ES version exactly
# Beats/Agent should match ES major.minor
# APM agents: check https://www.elastic.co/support/matrix
```

## ❌ Common Mistakes & Fixes

| Mistake | Impact | Fix |
|---|---|---|
| Skipping minor versions | Upgrade fails or corrupts cluster | Always upgrade one minor at a time |
| No snapshot before upgrade | No rollback option | MANDATORY snapshot + verify before any upgrade |
| Not reading breaking changes | Silent failures post-upgrade | Read breaking-changes doc for each version |
| Upgrading masters before data nodes | Master incompatibility issues | Always upgrade data nodes first, masters last |
| Mixed version > 1 minor | Unsupported configuration | Never run ES with > 1 minor version difference |
| Forgetting to re-enable allocation | Shards stuck after upgrade | Set allocation.enable back to "all" |
| Not checking deprecation API first | Upgrade blocked or failing | Run GET _migration/deprecations before upgrading |
| Upgrading Kibana before ES | Kibana incompatible with old ES | Always upgrade ES first, then Kibana |
| Old indices (7.x) not reindexed | 9.x cannot read 7.x indices | Reindex all 7.x indices before upgrading to 9.x |
| No post-upgrade verification | Silent issues go undetected | Run full checklist post-upgrade |

## ⚡ Quick Reference

```bash
# Pre-upgrade
GET _migration/deprecations           # check deprecations
GET _cluster/health                   # must be green
GET _cat/nodes?v&h=name,version      # current versions

# Take snapshot
PUT _snapshot/REPO/SNAPSHOT { "indices": "*", "include_global_state": true }

# Rolling upgrade
PUT _cluster/settings { "persistent": { "cluster.routing.allocation.enable": "primaries" } }
# ... upgrade node ...
PUT _cluster/settings { "persistent": { "cluster.routing.allocation.enable": "all" } }

# Full cluster restart
PUT _cluster/settings { "persistent": { "cluster.routing.allocation.enable": "none" } }
POST _flush
# ... stop all, upgrade all, start masters, start data nodes ...
PUT _cluster/settings { "persistent": { "cluster.routing.allocation.enable": "all" } }

# Post-upgrade
GET _cat/nodes?v&h=name,version      # all same version?
GET _cluster/health                   # green?
GET _migration/deprecations           # new deprecations?
```

## 💡 Key Principles

```
1. Snapshot first — always, no exceptions
   → Your only rollback option if upgrade goes wrong

2. Read breaking changes before every upgrade
   → Even minor versions can have important changes

3. Fix all deprecations before upgrading
   → GET _migration/deprecations → fix all → then upgrade

4. One minor version at a time
   → 8.14 → 8.15 → 8.16 → 9.0 NOT 8.14 → 9.0

5. Data nodes before master nodes (rolling upgrade)
   → Upgraded master should manage an upgraded cluster

6. Re-enable allocation after every node upgrade
   → Forgetting = shards stuck = cluster stays YELLOW

7. Reindex indices older than previous major version
   → 7.x indices MUST be reindexed before upgrading to 9.x

8. Upgrade ES → Kibana → Beats/Agent (in that order)
   → Kibana must match ES version exactly

9. Test in staging first
   → Upgrade staging cluster, run smoke tests, then production

10. ECK handles rolling upgrades automatically
    → Just change version field, ECK manages the rest
```
